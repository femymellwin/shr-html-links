01 / What the product does

A proposal-response and enterprise-knowledge platform described in the resume, covering RFI/RFP/RFQ lifecycles, proposal drafting, review/approval, versioning and knowledge access to documents, code repositories and databases using AI and MCP.

  • The business problem is reducing the time spent repeatedly collecting company facts, product specifications and previous response material for procurement submissions.
  • The system combines a business workflow for documents and approvals with a separate knowledge plane that can reach structured databases, repositories and enterprise documents.
  • The resume describes multi-tenant boundaries, collection-scoped MCP access and version-managed proposal review; those permissions need to be enforced before model context is constructed.

03 / End-to-end business and technical flow

  1. Start an RFI / RFP / RFQ. A proposal owner registers a procurement request and its response requirements, documents and due dates.
  2. Prepare sections/questions. The application organizes response sections and identifies the company/product facts needed; exact automatic parsing behavior is not confirmed by source code.
  3. Authorize knowledge scope. User identity, tenant and permitted collections restrict which knowledge the retrieval layer may access.
  4. Fetch and ground knowledge. A connector or MCP-compatible tool obtains relevant information from company databases, documents or GitHub; the specific retrieval ranking/indexing mechanism is unverified.
  5. Draft with an LLM. Ollama or Azure AI is used to help form a response from the question and authorized context. Human validation is needed for claims, pricing and commitments.
  6. Review and revise. Subject-matter owners edit responses; reviewers assess accuracy; versions and approval stages track progression.
  7. Generate proposal output. Approved sections become the response document, ready for business review and submission through the agreed external process.

05 / RAG: concept and evidence

RAG-style pattern is consistent with described retrieval; indexing not confirmed

The resume describes contextual knowledge retrieval and grounded question answering, which is compatible with RAG: (1) use the RFP question as a search/query, (2) retrieve tenant-authorized records or passages, (3) assemble them as evidence, (4) ask an LLM for a constrained answer and (5) review the result. The CV does not prove a vector DB, embeddings, hybrid search, citation generation, chunking strategy or a specific retriever. 06 / MCP: concept and evidence

Explicitly described in the resume; exact server not audited

MCP can connect an AI client to permitted enterprise knowledge tools/resources. The resume identifies an enterprise knowledge/MCP server and collection-scoped MCP authorization. For example, a tool might fetch a product record or an approved knowledge excerpt in the requester’s tenant scope. MCP is a protocol layer, not an LLM and not equivalent to RAG; information exposed via MCP may then be used in a RAG-style prompt.

07 / Data entities and access controls

Representative business data

  • RFP/RFQ/RFI records, deadlines, sections, owner and response status
  • Responses, versions, attachments and generated documents
  • Review/approval events and responsibilities
  • Knowledge collections, source connectors and sync records
  • Tenant/user/role assignments and MCP collection permissions
  • Retrieval results, drafts and human-reviewed answer evidence (logical data design, not audited schema)

Privacy, security and governance

  • Reject cross-tenant retrieval before any content reaches the model.
  • Scope MCP tools to approved collections and maintain read vs write permissions.
  • Never let generated pricing, certifications or contractual assurances bypass a human reviewer.
  • Treat imported documents and repository text as untrusted content, not as instructions to the assistant.

09 / How to explain it in an interview

60-second product narrative

This platform combines an RFP response workflow with enterprise knowledge access. React/FastAPI services manage response sections, approvals and versions; knowledge connectors expose approved database, GitHub and document content. LLMs assist with grounded proposal drafting. MCP defines how authorized knowledge tools are accessed, and a RAG-style pipeline may use retrieved facts as generation context; the exact retriever is not verified by the resume alone.

Why is the knowledge platform separate from the RFP workflow?

The proposal app owns review and submission states; the knowledge layer standardizes reusable facts, connectors, collection permissions and AI access.

Is MCP the same thing as RAG?

No. MCP standardizes access to tools/resources. RAG is the pattern of retrieving context and grounding model output in it.

Is a vector database confirmed?

No. Contextual retrieval is described, but embeddings, indexing and the vector search backend were not evidenced in the supplied CV.

What should happen before sending a proposal?

The business owner verifies sources, contract terms, pricing and compliance statements, then approves the final response.
