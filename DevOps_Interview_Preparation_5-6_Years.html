Production-grade workflow example

name: secure-ci
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
  id-token: write          # only when a job needs cloud OIDC
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@<full-commit-sha>
      - uses: actions/setup-python@<full-commit-sha>
        with: { python-version: '3.12', cache: 'pip' }
      - run: pip install --require-hashes -r requirements.txt
      - run: pytest --junitxml=report.xml
  deploy:
    if: github.ref == 'refs/heads/main'
    needs: test
    environment: production
    runs-on: ubuntu-latest
    permissions: { contents: read, id-token: write }
    steps:
      - name: Azure login with federated identity
        uses: azure/login@<full-commit-sha>
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
Security headline: default to read-only permissions, isolate privileged jobs, pin third-party actions to immutable commit SHAs, prefer OIDC short-lived cloud tokens over stored cloud secrets, protect environments, and never run untrusted PR code with privileged credentials.
BeginnerExplain workflow, job, step, action and runner.

A workflow is the YAML-defined automation. A job is a set of steps that normally shares a runner. A step runs a command or action. An action is reusable automation packaged for a step. A runner is the compute that executes a job. Jobs run in parallel unless linked with needs.

BeginnerHow do triggers and filters work?

Use on for events such as pull_request, push, workflow_dispatch, schedule and workflow_call. Narrow with branch/path filters. Mention the operational trap: over-broad triggers waste minutes; over-narrow path filters can accidentally skip required checks.

BeginnerArtifacts vs cache?

Cache accelerates repeated work and may be evicted; do not treat it as a release record. Artifacts are workflow outputs such as binaries, test reports and SBOMs with explicit retention. A production release should reference an immutable artifact in a registry, not rebuild source during deployment.

IntermediateReusable workflow vs composite action?

A reusable workflow is called at the job level with workflow_call and can contain multiple jobs, runners, permissions and environments. A composite action packages repeated steps and runs inside the caller’s job. Use reusable workflows for governed pipeline patterns; composite actions for small step-level behavior.

IntermediateHow would you authenticate GitHub Actions to Azure without a client secret?

Configure an Entra application or managed identity with a federated identity credential whose subject is narrowly bound to the repository, branch/tag or environment. Grant only required Azure RBAC. In the job, grant id-token: write and exchange GitHub’s OIDC token for a short-lived Azure token. Protect the deployment environment and restrict the audience/subject claim.

IntermediateHow do environments and approvals help?

An environment scopes deployment secrets/variables and can impose protection rules such as reviewers, branch restrictions and wait timers. Keep CI unprivileged; only the deployment job should reference the protected environment. Explain that an approval is one control—not a substitute for automated tests and policy.

IntermediateHow do you make workflows fast and stable?
  • Cancel superseded runs using concurrency.
  • Cache dependency downloads with a lockfile-based key; never cache secrets.
  • Parallelize independent jobs and use a matrix for supported versions.
  • Build once; fan out tests/scans; promote the same digest.
  • Measure queue time, execution time, cache hit rate, flake rate and failure cause.
AdvancedDesign a GitHub Actions platform for 100 repositories.

Answer outline: central reusable workflows in a controlled repository; versioned contracts; repository rulesets and CODEOWNERS; organization-level runner groups; ephemeral autoscaled self-hosted runners for private workloads; OIDC per environment; default read-only token; approved action allow-list; artifact/SBOM/signing standard; policy tests; central telemetry; migration path; exception process; semantic versioning and deprecation policy for workflow templates.

AdvancedWhy is pull_request_target dangerous?

It runs in the base repository context and can access privileged tokens/secrets. If the workflow checks out and executes attacker-controlled fork code, credentials may be exfiltrated. Use it only for trusted metadata operations; never execute untrusted head code with privileged context. Separate untrusted build from privileged promotion and pass only verified artifacts.

AdvancedA deployment workflow was compromised. What do you do?

Disable the workflow/runners, revoke active credentials and federated trust if necessary, quarantine artifacts, preserve audit logs, identify changed workflow/action SHAs and affected environments, rotate impacted secrets, validate artifact provenance, restore from a known-good commit, and communicate blast radius. Then prevent recurrence with SHA pinning, allow-lists, CODEOWNERS, isolated ephemeral runners and anomaly alerts.

BeginnerStage vs job vs step?

A stage is a logical boundary such as Build or Production; a job is the scheduling boundary that runs on an agent; a step is an individual task or script. Stages and jobs can express dependencies and conditions. A deployment job adds deployment history and environment integration.

IntermediateHow do templates improve governance?

Use step/job/stage templates for reuse, parameterize only safe variability, version templates, require template review and add policy checks. Prefer compile-time parameters for structure; use variables for runtime values. Avoid a “mega-template” that hides behavior and is impossible to test independently.

IntermediateWhere should production approvals live?

On protected resources such as environments, service connections or variable groups—not only inside editable YAML. Resource owners should control checks. Combine approvals with branch control, business hours, exclusive lock, policy evaluation and post-deployment health checks as appropriate.

AdvancedMicrosoft-hosted vs self-hosted agents?

Hosted agents reduce maintenance and provide clean ephemeral images, but offer less network/customization control. Self-hosted agents can reach private resources and use custom tooling, but require patching, isolation, autoscaling and cleanup. For sensitive workloads, use ephemeral agents, separate pools by trust zone, restrict capabilities and block cross-project access.

AdvancedA stage was skipped unexpectedly. How do you troubleshoot?

Inspect expanded YAML, dependency result, the exact condition, compile-time vs runtime expression syntax, variable scope and branch value (for example Build.SourceBranch). Enable diagnostic logging, simplify the condition, and test cases. Remember that a skipped dependency can propagate unless the downstream condition explicitly handles it.

Know

Operate

Backups, configuration as code, plugin compatibility, controller HA/recovery, ephemeral agents, audit and upgrades.

BeginnerDeclarative vs scripted Pipeline?

Declarative Pipeline provides a constrained, readable structure and built-in validation; scripted Pipeline offers flexible Groovy control flow. Prefer declarative for standard delivery and use shared libraries for reusable complexity rather than embedding large Groovy programs in every Jenkinsfile.

IntermediateWhat belongs in a Shared Library?

Stable, tested pipeline primitives such as build, scan, publish and deploy functions. Version the library, restrict who can modify trusted code, keep interfaces small and document defaults. Avoid hiding every shell command—teams still need understandable logs and override points.

IntermediateHow do you handle Jenkins credentials safely?

Use credential binding scoped to the minimum stage, mask output, never interpolate secrets into unsafe shell command strings, restrict controller/admin access, isolate untrusted builds, rotate credentials and prefer short-lived cloud identity where supported. Do not store secrets in Jenkinsfiles or agent workspaces.

AdvancedHow would you migrate Jenkins to GitHub Actions?

Inventory jobs, plugins, credentials, triggers and network dependencies; group pipelines into patterns; establish reusable GitHub workflows and runner architecture; map credentials to OIDC/secrets; migrate low-risk services first; run parallel validation; compare outputs/digests; train teams; freeze new Jenkins features; retire plugins/controllers after retention and audit requirements are met.

Infrastructure as code

Terraform for Azure

For 5–6 years, be ready for state, modules, provider behavior, imports, drift, safe plans, identity, multi-environment layout and failure recovery—not only resource syntax.

State controls

Azure Storage backend, encryption, RBAC, network restriction, blob versioning, soft delete, locking and break-glass recovery.

Module controls

Small interfaces, validation, secure defaults, provider constraints, examples, tests and semantic versions.

Pipeline controls

Format/validate, lint, security scan, plan, review/policy, apply, verify and scheduled drift detection.

BeginnerWhat are state and the dependency graph?

State maps configuration addresses to real objects and stores attributes needed to calculate changes. Terraform builds a dependency graph from references and explicit depends_on, then parallelizes safe operations. State is sensitive operational data; protect it even if secrets are marked sensitive in output.

Beginnercount vs for_each?

count uses numeric indexes and suits nearly identical instances; removing/reordering items may shift addresses. for_each uses stable keys and is usually safer for named resources. Choose address stability deliberately.

IntermediateDesign a secure Azure remote backend.

Use a dedicated storage account/container, private endpoint or restricted firewall, Entra/RBAC authentication instead of account keys, least-privileged pipeline identity, encryption, blob versioning/soft delete, diagnostic logs and separation by environment/state boundary. Azure Blob provides locking for the azurerm backend. Define and test state recovery.

IntermediateHow do you design reusable modules?

Expose intent, not every provider argument. Use typed variables, validation and secure defaults; return only useful outputs; avoid provider configuration inside child modules; pin compatible versions; add examples, tests and upgrade notes. Separate resources with different ownership/lifecycle to reduce blast radius.

IntermediateHow do you handle drift and emergency changes?

Detect with scheduled plans. For a valid emergency change, document it, then codify and reconcile through Git. Import/adopt resources or update configuration rather than blindly overwriting. Use ignore_changes only when another controller truly owns an attribute; otherwise it hides risk.

AdvancedAn apply partially failed. What next?

Do not immediately rerun with changes. Read the error and Azure activity logs; compare state with actual resources; refresh/plan; identify idempotent vs partially created objects; import or remove stale state only with backup and review; fix cause such as permission, quota or eventual consistency; apply a small corrective plan; verify and record the incident.

AdvancedOne monolithic state or many states?

Split by ownership, lifecycle, privilege and blast radius—for example platform network, AKS cluster, and application add-ons. Too few states increase lock contention and failure impact; too many create dependency/output management overhead. Prefer explicit contracts such as published outputs or data sources, and avoid circular dependencies.

Container orchestration

Kubernetes / AKS

Explain the reconciliation model, workload/networking primitives, rollout safety, probes, resources, autoscaling, policy and troubleshooting from request to pod.

BeginnerPod, Deployment, StatefulSet, DaemonSet and Job?

A Pod is the scheduling unit. A Deployment manages replaceable stateless replicas and rolling updates. A StatefulSet provides stable identity/storage ordering. A DaemonSet runs a pod on selected nodes. A Job runs to completion; a CronJob schedules Jobs.

BeginnerService types and Ingress?

ClusterIP exposes inside the cluster; NodePort opens a node port; LoadBalancer integrates an external load balancer. Ingress/Gateway provides HTTP(S) routing through a controller. A Service selects ready endpoints using labels; troubleshoot selector, EndpointSlice, port/targetPort, DNS and network policy.

IntermediateLiveness, readiness and startup probes?

Readiness controls traffic eligibility. Liveness restarts a stuck container. Startup protects slow starts from premature liveness failure. Avoid using the same shallow endpoint for all three; set timeouts and thresholds from measured behavior, and do not make liveness depend on a fragile downstream service.

IntermediateRequests, limits, QoS and autoscaling?

The scheduler places pods based on requests; the runtime enforces limits. CPU is throttled; memory limit breach can cause OOMKill. HPA scales replicas from metrics, VPA recommends/changes pod resources, and cluster autoscaler changes node count. Use measured usage, protect critical workloads and prevent HPA/rollout capacity conflicts.

IntermediateA pod is in CrashLoopBackOff. Walk through diagnosis.

kubectl describe pod for events/state, current and previous logs, exit code, command/args, config/secret mounts, probe failures, OOMKilled, permissions and dependency reachability. Compare the image digest/config to last good, inspect node events and rollout history, then mitigate by rollback or configuration fix before deeper root-cause work.

AdvancedHow do you secure a multi-tenant AKS cluster?

First challenge whether hard multi-tenancy needs separate clusters. Within a cluster: Entra integration and least-privilege RBAC, namespace boundaries, default-deny NetworkPolicy, Pod Security standards, admission policy, workload identity, restricted egress, secrets from a managed vault, signed images, allowed registries, resource quotas, node-pool isolation/taints, audit logs and runtime detection.

AdvancedDesign a zero/low-downtime rollout.

Multiple replicas across zones/nodes; correct readiness; rolling update with safe maxUnavailable/maxSurge; PodDisruptionBudget; graceful shutdown and preStop; backward-compatible DB changes; capacity headroom; canary/blue-green for high risk; automated health analysis; fast rollback to the prior immutable digest.

AdvancedPending pods after a release—what dimensions do you check?

Unsatisfied requests, quotas/LimitRanges, affinity/anti-affinity, topology spread, taints/tolerations, PVC binding and zones, max pods/IP exhaustion, autoscaler limits, unavailable node pools and admission rejection. The scheduler event normally narrows the first branch of investigation.

FROM golang:1.24-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/app

USER nonroot:nonroot
ENTRYPOINT ["/app"]
BeginnerImage vs container, and CMD vs ENTRYPOINT?

An image is an immutable filesystem/config template; a container is a runtime instance with a writable layer. ENTRYPOINT defines the executable; CMD supplies defaults that users can override. Prefer exec-form JSON so the application receives signals correctly.

IntermediateWhy use multi-stage builds?

Compile/test in a builder stage, then copy only runtime output into a minimal final stage. This reduces image size and attack surface while keeping build tooling readable. It does not automatically remove secrets copied into an earlier layer—use BuildKit secret mounts and never persist credentials.

IntermediateHow do you harden a container at runtime?

Run as non-root with a fixed UID, read-only root filesystem, drop Linux capabilities, disallow privilege escalation, use seccomp/AppArmor, mount only required volumes, set resource limits, restrict network access, inject short-lived secrets at runtime and continuously patch/rebuild the base.

AdvancedWhat does a trustworthy image promotion process look like?

Hermetic/reproducible build where practical; locked dependencies and trusted base digest; SAST/SCA/secret scan; image scan; SBOM; provenance attestation; signature; immutable registry retention; policy verifies signature, allowed builder and severity exception; promote the same digest through environments; monitor newly disclosed CVEs and rebuild.

IntermediateWhat is the difference between continuous delivery and continuous deployment?

Both keep software releasable through automation. Continuous delivery may retain a business/manual decision before production; continuous deployment automatically releases every qualifying change. The right control depends on risk, compliance and product context—not maturity theater.

AdvancedHow do you improve flow without lowering quality?

Reduce batch size and handoffs; parallelize independent checks; shift fast tests earlier; remove flaky tests; standardize paved roads; use risk-based progressive delivery; automate evidence; define SLO/error budgets; measure lead time by phase and fix the dominant queue. BeginnerSAST, DAST, SCA and secret scanning?

SAST analyzes source/bytecode without running the app. DAST probes a running application. SCA inventories open-source dependencies and known vulnerabilities/licenses. Secret scanning detects credentials or high-entropy tokens. They find different classes of risk and need tuning, ownership and remediation—not a single pass/fail tool.

IntermediateHow do you define a useful security gate?

Gate on exploitable, newly introduced risk with clear severity, reachability/exposure, asset criticality and fix ownership. Baseline existing debt; prevent regression; allow time-bound, approved exceptions with compensating controls. Track false-positive rate, waiver age and remediation time. Do not fail every build on an unactionable global CVE count.

AdvancedDesign security evidence for a regulated release.

Link change request/PR, reviewer and protected branch; immutable build logs; test/scan results; SBOM and dependency license data; artifact digest, signature and provenance; policy decision; separation-of-duties approval if required; deployment identity/time/environment; post-deploy verification; exception records and retention. Generate evidence automatically from authoritative systems.

Pull-based operations

GitOps flow

OpenGitOps describes systems as declarative, versioned and immutable, pulled automatically, and continuously reconciled. Git becomes the desired-state control plane; the cluster agent compares and converges.

BeginnerWhat makes GitOps different from a pipeline running kubectl apply?

In GitOps, an in-cluster or environment-side reconciler continuously pulls approved desired state and corrects drift. A push pipeline directly changes the cluster at one point in time. GitOps improves auditability and limits inbound credentials, but still needs secret management, promotion design and operational ownership.

IntermediateHow do you promote across environments?

Build once, identify by digest, then update environment-specific desired-state repositories/paths through PRs. Validate policy and render output, merge, let each environment reconciler pull, and verify health. Avoid rebuilding or retagging mutable images. Choose repo topology based on access boundaries and blast radius.

AdvancedSomeone hot-fixed the cluster. What should happen?

If self-heal is enabled, the reconciler may revert the drift. During an incident, pause reconciliation only with a documented break-glass process; make the minimum safe runtime change; capture it; then commit the desired state and resume. Alert on drift and record who paused/resumed reconciliation.

Branching strategies

Prefer the simplest strategy that supports delivery and release needs. Short-lived branches and frequent integration reduce merge risk; branch policy provides control.

BeginnerWhat branch protections would you enable?

Required PR, required checks, minimum/required reviewers or CODEOWNERS for sensitive paths, up-to-date branch where necessary, no force push/deletion, signed commits/tags if policy requires, conversation resolution and tightly controlled bypass. Keep the required check set reliable and fast.

IntermediateMerge commit, squash or rebase?

Merge commits preserve branch topology; squash creates one clean commit per PR; rebase produces linear history but rewrites branch commits. Choose one based on audit/debug/revert needs. For many service teams, squash plus a well-written PR provides simple history and atomic rollback.

AdvancedHow do you support a long-running feature without a long-lived branch?

Slice it vertically into backward-compatible increments, merge behind a feature flag, use branch-by-abstraction for large replacements, expand/migrate/contract database changes, test in production for internal cohorts, and remove flags after rollout. This preserves continuous integration while separating deployment from release.

DevSecOps deep dive

Security architecture & pipeline controls

Organize answers by identity, code, dependencies, build, artifact, deployment and runtime. State the threat, preventive control, detective control and recovery.

Pipeline threat model

  • Untrusted pull request executes with privilege
  • Third-party action/plugin compromised
  • Dependency confusion or poisoned cache
  • Long-lived credential exfiltrated
  • Artifact replaced after scanning
  • Self-hosted runner persistence

Countermeasures

  • Trust-zone isolation and ephemeral runners
  • SHA pinning, allow-lists and update review
  • Lockfiles, private registry and provenance
  • OIDC/workload identity and least privilege
  • Digest promotion, signature and attestation
  • Immutable images and post-job cleanup
IntermediateSecret management design for CI/CD and AKS?

Keep the source of truth in a managed vault; use workload identity/OIDC; grant per-workload least privilege; fetch at runtime; avoid writing secrets to state, logs, artifacts or images; rotate and audit access; mask output but do not rely on masking; use short TTL and break-glass procedures. In Kubernetes, prefer a CSI/external secret integration over hand-managed base64 Secrets.

AdvancedExplain SBOM, signature and provenance.

An SBOM lists components. A signature proves an authorized identity signed a specific artifact digest. Provenance records how/where/by whom it was built and source inputs. Together with policy, they answer “what is inside?”, “is it authentic?” and “was it built by the approved process?” None alone proves the software is vulnerability-free.

AdvancedA critical CVE has no patch. Do you block?

Assess reachability, exploitability, exposure, asset criticality and compensating controls. Options: block deployment, remove/disable component, isolate network path, WAF/runtime rule, reduce privileges, accept risk with named owner and short expiry. Document evidence and monitor. “Critical” is a strong signal, but risk treatment must be contextual and time-bound.

IntermediateWhy is pipeline success rate not enough?

It can improve by retrying flaky jobs or weakening gates. Pair it with duration/queue, flake and retry rates, escaped defects, change fail rate and user-facing SLO. Segment failures into product code, test, platform, dependency and deployment categories so the team can act.

AdvancedHow would you create a delivery dashboard?

Define event schema and service identity; ingest SCM, CI, artifact, deployment and incident events; deduplicate reruns; connect a change to its production deployment; calculate consistent per-service metrics; expose percentiles and trends; annotate process changes; protect privacy; review with teams. Validate samples manually before trusting automation.

AdvancedWhich security metrics avoid vanity?

Coverage of repos/workloads with enforced controls; median/95th remediation time by risk; newly introduced exploitable findings; expired exceptions; secret exposure response time; signed/provenanced artifact adoption; mean time to revoke compromised identity; and recurrence rate. Raw finding count alone may rise when coverage improves.

BeginnerSLI, SLO and SLA?

An SLI is a measured reliability indicator, such as good requests/total. An SLO is the internal target over a window. An SLA is a contractual commitment that may include consequences. Error budget is the allowed unreliability implied by the SLO.

IntermediateWhat makes a good alert?

User-impacting, actionable, appropriately urgent, with clear owner/runbook and low noise. Prefer symptom/SLO burn alerts over every resource threshold. Include service, environment, severity, dashboard, recent deploy and safe first actions. Tune using false-positive and ignored-alert evidence.

AdvancedProduction latency doubled after deployment. Lead the response.

Declare/coordinate, assess user impact and SLO burn, correlate to change, compare canary/old version, rollback or stop traffic if safe, verify recovery, preserve evidence, communicate status. Then analyze traces/metrics, resource saturation and dependency latency; identify contributing controls; write blameless actions with owners/dates and validate them.

IntermediateManaged identity vs service principal?

A managed identity is an Azure-managed service identity with no credential lifecycle for you to handle. A service principal is an application identity that can use certificates/secrets or federation. For GitHub Actions, federated identity to an app or user-assigned managed identity avoids long-lived secrets. In all cases, RBAC scope remains critical.

IntermediatePrivate endpoint vs service endpoint?

A private endpoint gives a PaaS resource a private IP in your VNet and requires correct private DNS. A service endpoint keeps the service’s public endpoint but extends VNet identity to it. Explain routing/DNS, on-premises access, data exfiltration controls, cost and operational complexity.

AdvancedDesign a private AKS delivery path.

Private API endpoint and controlled DNS/connectivity; CI runners/agents in an approved network or GitOps pull; ACR private endpoint and AKS pull identity; Key Vault private access/workload identity; controlled egress through firewall/NAT; Entra/RBAC; policy and diagnostics; separate deployment identity; break-glass access; zone-aware nodes and upgrade strategy.

IntermediateDisk is full, but deleting a log did not free space. Why?

A process may still hold the deleted inode open. Use lsof +L1 or inspect deleted handles, then safely restart/reopen the process or truncate via the handle as procedure allows. Also distinguish inode exhaustion from block exhaustion and check container overlay/log paths.

IntermediateService works by IP but not hostname. Debug path?

Check the exact resolver/context, dig/nslookup, search domains, record type/value/TTL, split-horizon/private DNS links, CoreDNS health if Kubernetes, network path to DNS, cache, then TLS SNI/certificate hostname. An IP test may bypass load balancing, routing and TLS behavior.

AdvancedWhat makes an automation script production-ready?

Idempotent behavior, validated inputs, explicit dependencies, safe defaults, timeouts/retries with backoff only for transient failures, predictable exit codes, structured/redacted logs, concurrency handling, dry-run where useful, tests, versioning, rollback/cleanup and observable metrics.

Architecture round

System-design scenarios

Start by clarifying constraints. Draw trust boundaries and artifact flow before naming tools.

Whiteboard order: requirements → scale/risk → source/branch policy → CI → artifact → IaC/platform → CD/GitOps → security → observability → rollback/DR → metrics/cost.
AdvancedDesign CI/CD for 50 microservices on AKS using GitHub Actions.

Requirements: deployment frequency, isolation, compliance, regions and RTO/RPO. Design: reusable workflows; PR unit/SAST/SCA/IaC tests; build once; image scan/SBOM/sign/provenance; ACR by digest; OIDC to Azure; config PR to environment repo; GitOps reconciler; progressive rollout; policy verifies signature and workload standards; Azure Monitor/OpenTelemetry; automated rollback from health; DORA/SLO dashboards. Scale: runner groups/autoscaling, concurrency, caching, template versioning, platform ownership and exception process.

AdvancedDesign disaster recovery for the delivery platform.

Define RTO/RPO by component. Source and config repos need protected backups/replication. Registries need retention/geo strategy and known-good digests. Terraform state needs versioning, soft delete, backup/recovery test and restricted break-glass. Recreate runners/controllers from code. Back up only Kubernetes state that cannot be reconstructed. Document identity/DNS dependencies, regularly restore into an isolated environment, and measure recovery.

AdvancedHow would you design pipelines for a monorepo?

Map changed paths to affected components, but retain safe full checks for shared code/lockfiles. Use a generated matrix, dependency graph, remote cache, per-component ownership and independent version/artifact identity. Avoid path-filter gaps in required checks. Track cache correctness, critical-path duration and shared-change fan-out.

AdvancedHow do you handle database changes with zero-downtime delivery?

Use expand/migrate/contract: add backward-compatible schema, deploy code that supports old/new, backfill with throttling and verification, switch reads/writes, then remove old schema after rollback window. Separate schema job with ownership/locking, test production-scale migration, monitor replication/latency, and define roll-forward because destructive DDL may not be reversible.

IntermediateTell me about a production incident you handled.

S: user impact and severity. T: your incident role. A: triage, communication, mitigation/rollback, evidence preservation, cross-team coordination and safety checks. R: recovery time and verified impact. Learning: root/contributing factors, automation/runbook/alert improvements and follow-up validation.

AdvancedA team wants to bypass a slow security control. What do you do?

Understand the delivery impact and the threat the control addresses. Bring data on duration, false positives and risk. Propose a safer faster design: incremental scan, parallelization, pre-merge feedback, scoped exception with expiry/owner and compensating control. Escalate only according to risk policy. Measure both lead time and escaped risk after change.

AdvancedDescribe a mistake.

Choose a real, bounded mistake. Own the decision without blaming; explain early detection and immediate containment; state the user/business impact accurately; show the systemic corrective action and verification. Avoid disguised strengths (“I care too much”) or revealing an unresolved high-risk practice.

Before production

  • Change reviewed and required checks passed
  • Artifact immutable; SBOM/signature/provenance available
  • Identity least-privileged; no long-lived secret
  • Configuration and DB changes backward-compatible
  • Capacity, health verification and rollback tested
  • Monitoring/dashboard/runbook ready

During incident

  • Assess impact; declare severity and owner
  • Stop the bleed: rollback, disable or shift traffic
  • Communicate on a predictable cadence
  • Preserve logs, timeline and changed artifacts
  • Verify recovery against user-facing signals
  • Blameless learning with verified actions

Common weak answers to avoid

  • “We use Kubernetes because it is scalable” without workload or operational context.
  • Listing scans without explaining ownership, gate criteria and false positives.
  • Calling a manual approval the security strategy.
  • Rebuilding the artifact separately for each environment.
  • Using “latest” tags, broad admin permissions or permanent cloud secrets.
  • Describing only the happy path—no failure mode, rollback or verification.
  • Inventing metrics. If a number is unavailable, describe how you would measure it.

Questions to ask the interviewer

  1. How do teams own services from commit through on-call, and where are the major handoffs?
  2. What are the largest constraints in the current delivery platform: speed, reliability, security, cost or developer experience?
  3. How are reusable pipelines/platform standards governed and evolved without blocking teams?
  4. Which delivery and reliability metrics drive decisions, and how trustworthy is the data?
  5. What would success for this role look like after 90 days and one year?
