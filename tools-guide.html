CHAPTER 01

Start here

This is a practical learning path for using NotebookLM, Mermaid, Excalidraw, draw.io, and MinIO together. The aim is not to memorise five interfaces. It is to develop one repeatable skill: turn reliable source material into an understandable architecture, implement a small part of it, and explain what the implementation actually proves.

Assumption: “notebook llm” means Google's NotebookLM, not Jupyter notebooks or running a local language model. Google's help pages checked on 1 October 2026 redirect to Gemini Notebook and use that name. This guide retains “NotebookLM” so it matches the tool you asked about. Screens and account-specific capabilities may differ. S01

Read this before following older MinIO tutorials. The official minio/minio community repository is archived and says it is no longer maintained. Its legacy binary instructions are not a current maintenance promise. This guide uses the documented AIStor container path for the optional lab, which requires your own license file; a single-compute-resource Free tier is documented. Do not assume AIStor and the archived AGPL community edition have the same license or support model. [S21] [S22]

The recommended order

Understand the problem → learn the drawing basics → research with sources → describe the design in text → operate a small storage lab. Begin with the foundations and a simple Excalidraw sketch, use NotebookLM to clarify gaps, then learn Mermaid and draw.io. Leave distributed storage and Kubernetes until you can explain a single-node lab without copying a tutorial.

The default plan is 30 study sessions of about 45–60 minutes each, not a guaranteed completion time. A useful session structure is 10 minutes reading, 25 minutes building, 10 minutes explaining what you did, and 5 minutes recording errors. An experienced cloud engineer can skip familiar basics; a beginner can repeat any session.

What you need

For the diagramming and research chapters, use a modern browser, a local project folder, and approved non-sensitive source documents. A Google account is needed for the research product, subject to its account and regional availability. For the optional storage lab, you need a Docker environment with Compose, Python 3.10 or newer for the supplied scripts, the official mc client, internet access to obtain software, and a valid AIStor license. Those external tools, accounts, images, and licenses are not bundled. The guide and its built-in examples require no internet to read. S01 S22 S30

Your running project: a private document platform

Imagine an internal team that stores approved technical documents. A user reaches a document API through a gateway. The API keeps file bytes in object storage and document IDs, owners, and object keys in a metadata database. A person may separately export an approved, sanitised document for use in NotebookLM. This is a proposed teaching design, not a claim that these tools have a native integration.

The supplied container lab implements only the object store and client operations. It does not deploy a gateway, API, database, identity provider, NotebookLM connector, backup service, or monitoring stack. Keep the full design and the implemented subset visibly distinct.

CHAPTER 02

Foundations

First decide which question the diagram answers

A diagram becomes confusing when it mixes business context, deployment topology, network packets, and individual source-code classes. Write one sentence before drawing: “This diagram explains ___ to ___ so that they can ___.” For example: “This diagram explains document access to the security reviewer so that they can identify trust boundaries.”

The C4 model offers four common abstraction levels: system context, containers, components, and code. A C4 container means a separately runnable application or data store; it does not necessarily mean a Docker container. This distinction prevents a frequent beginner misunderstanding. You do not need all four levels for every project. S35

View The question it answers What belongs in your document-platform example
Context Who uses the system, and what external systems matter? Internal user, document platform, identity service, approved external research tool
Logical / container What are the major responsibilities? Gateway, document API, metadata database, object store
Deployment Where do those responsibilities run? Hosts or cluster, networks, zones, disks, replicas, endpoints
Sequence What happens during one operation? Authenticate, authorise, read metadata, sign URL, fetch bytes
Operational How is the system observed and recovered? Metrics, audit logs, backups, restore procedure, operators

The last three rows are useful complementary views in this guide; they are not a replacement definition of the four C4 levels.

Learn a small vocabulary before collecting icons

An API is an interface through which software requests an operation. A gateway or reverse proxy receives requests and forwards them to another service. A database holds application records; an object store holds objects addressed by a bucket and key. A trust boundary is a place where your assumptions about identity, permissions, or control change. A failure domain is a unit that can fail together, such as one host. In the proposed design, the same service can cross several of these concerns, which is why a single coloured box is rarely enough.

For cloud drawings, distinguish an account or subscription boundary from a Region, a virtual network, a subnet, a security rule, and an availability boundary. Do not draw them as interchangeable nested rectangles. A line crossing a box does not establish a firewall rule, a route, or permission. The picture must agree with a separately checked configuration.

Five rules for diagrams you can explain

Name responsibilities, not only products. “Document API — validates ownership” is more useful than “EC2.” Put a product name below the responsibility when implementation detail matters.

Label relationships. “S3 API over HTTPS” is clearer than an unlabeled arrow. Choose a convention: arrow direction means request initiation, data movement, or dependency. State it in the legend and do not silently change conventions halfway across the page.

Keep scope consistent. A database schema diagram and an organisation-wide architecture diagram need different levels of detail. When something is omitted, say so. “Backup path not shown” is better than implying there is no backup requirement.

Show uncertainty. Use labels such as “proposed,” “to verify,” or “external dependency.” Do not make a guessed service look like discovered infrastructure. A hand-drawn style is not a substitute for these labels.

Keep source and export. An editable .excalidraw, .drawio, or .mmd file is the source; a PNG or SVG is a convenient view. Record the owner, date, and intended audience with both. Excalidraw and draw.io provide image export capabilities, but editability depends on what you save and embed. S10 S13 S14

A first exercise without any software

Write six lines: user, gateway, API, object store, metadata database, and administrator. For each, write one responsibility, one input, one output, and one failure. Then remove the administrator from the main data-path drawing and give administrative access its own small view. This forces you to distinguish “users downloading a file” from “operators changing the server.”

Finish condition: explain the request path in 90 seconds without saying “and then some cloud stuff happens.” If you cannot explain a connection, replace it with an open question rather than a confident arrow.

CHAPTER 03

NotebookLM

Learn source-grounded research, not just prompting

NotebookLM answers questions using material added to a notebook and provides source references. Its study-oriented outputs include formats such as reports, Audio Overviews, and Mind Maps; exact features and limits depend on the current product and account. A citation is a route to verification, not a certificate of truth. S01 S03 S04

Your most important habit is to separate what a source says, what the model inferred, and what you decided to build. For example, “the documentation supports bucket versioning” is a product fact. “We should retain versions for 30 days” is a proposed retention choice. “That policy satisfies our obligations” requires a different kind of review and should not be accepted just because an assistant wrote it.

Build your first useful notebook

Step 1 — choose a narrow question. Use a notebook titled “Private document storage — foundations.” The question is: “How should a small internal application store and retrieve documents using an S3-compatible service?” Avoid combining unrelated certification notes, personal files, and production incident logs in the first notebook.

Step 2 — assemble a small source pack. Start with five to eight selected pages: an S3 introduction, object keys/prefixes, current AIStor installation, access management, versioning, and your own one-page requirements. Those quantities are a learning recommendation, not a product limit. Create a source register with publisher, URL, accessed date, version, and sensitivity. Use the bundled template.

Step 3 — add sources deliberately. Create a notebook and use its source controls to add the supported documents or individual URLs. Inspect the imported content before asking detailed questions. Web URL ingestion generally imports the page's text, not every linked page, image, or embedded video. A documentation home page is not the whole documentation site. Supported import types and update behaviour vary; check the current source help rather than assuming a live mirror. S02 S03

Step 4 — test coverage. Ask for the exact source that explains the distinction between an object key and a filesystem path. If the response cannot identify the relevant passage, improve the source set before asking for a large architecture proposal.

Step 5 — build your vocabulary. Ask for ten terms with one-sentence explanations and one example per term. Correct the list against the documentation. Save a short note in your own words rather than keeping a long, unreviewed generated answer.

Step 6 — compare and challenge. Ask which operational tasks remain your responsibility in the proposed self-managed design. Ask what the sources do not establish. Specifically challenge claims about availability, backups, license scope, and automatic integration.

Step 7 — generate a study artifact. Make a short report or Mind Map, then ask questions about unclear branches. A Mind Map groups ideas; it does not encode a complete network topology or prove data-flow direction. Use it to discover concepts, then draw the architecture separately. S03 S04

Step 8 — export a reviewed brief. Produce a one-page brief containing scope, components, relationships, evidence, assumptions, and open questions. This brief becomes the input to Excalidraw and Mermaid. Mark any sentence you have not personally checked.

A simple evidence audit

Take three statements from the generated brief. Open each citation, read the surrounding context, and check whether it actually supports the whole sentence. Watch for scope creep: a sentence about a supported API is not proof that every SDK feature behaves identically; a single-host free tier is not evidence of a free distributed production cluster. Record verified, partially supported, or unsupported in the source register.

When two sources disagree, record their dates, versions, and scope. Prefer the source that governs your actual edition and deployment. Do not average the two answers. For example, older draw.io Mermaid instructions and its newer container-based Mermaid editing workflow can describe different application versions. S15 S16

Privacy and sharing

Use only data you are permitted to send to the product. Remove credentials, customer data, internal hostnames when unnecessary, and confidential architecture details from practice material. Google's current privacy documentation describes feedback-related collection and review, as well as differences in applicable terms for account types. Do not simplify that into “nothing is ever reviewed or used.” Check your organisation's policy before uploading work documents or sharing a notebook. S05

Practice deliverable: one notebook, one source register, one reviewed brief, and five questions you can answer without the notebook. The goal is understanding that survives after you close the tool.

CHAPTER 04

Mermaid

Start with syntax, then choose an editor

Mermaid turns text descriptions into diagrams. You can practise in the official Live Editor or a compatible editor, save the text as .mmd, and keep it with your documentation. Rendering support depends on the host's Mermaid version; the same text may lay out differently in different tools. This guide's HTML includes static artwork and copyable source, not a live Mermaid runtime. S06

Your first flowchart

Paste this into a Mermaid editor. Change “Application” to “Document API,” render again, and observe that relationships are preserved even if the layout moves.

flowchart LR
    U["User"] -->|HTTPS| A["Application"]
    A -->|S3 API| S["Object storage"]

flowchart selects the diagram type. LR requests a left-to-right direction. U, A, and S are identifiers; the quoted text inside brackets is what a reader sees. --> is a directed edge, and |HTTPS| is its label. Keep identifiers short and labels descriptive. S07

Use quoted labels for punctuation-heavy names. Do not use the lowercase keyword end as an unquoted node label in a flowchart. When a diagram fails, remove styling and reduce it to two nodes before adding complexity back. The official flowchart syntax page is the best place to check escaping and supported shapes. S07

Draw the document platform

flowchart LR
    U["Internal user"] -->|HTTPS| G["Gateway / reverse proxy"]
    subgraph P["Private application environment - conceptual"]
        G -->|Authenticated request| A["Document API"]
        A -->|S3 API over HTTPS| O["MinIO / AIStor"]

    end

This is an original logical example, not a deployable specification. The boundary says what the example groups together; it does not configure a firewall. The metadata database keeps records such as owner and object key, while the object store holds bytes. The lab later in the guide implements only the object-storage portion.

Exercise: add a scanning worker as a proposed component. Label the triggering relationship, the identity used to read objects, and where scan status is recorded. Then decide whether the main diagram has become too dense and needs a separate processing view.

Use a sequence diagram for one operation

A component diagram tells you who is connected. A sequence diagram tells you the order of one interaction. This example shows an alternative download design using a short-lived URL. It is not the same as streaming every download through the API. Mermaid sequence syntax uses participants and message arrows, with constructs such as notes, alternatives, and loops available when needed. S08

sequenceDiagram
    autonumber
    participant U as Authorized user
    participant A as Document API
    participant M as S3 endpoint
    U->>A: Request download for document ID
    A->>A: Authenticate and authorize object access
    A->>A: Sign short-lived GET URL locally
    A-->>U: Return presigned URL
    U->>M: GET using signed URL
    M->>M: Validate signature, expiry and permissions
    M-->>U: Object bytes
    Note over U,M: The endpoint must be reachable by the user; a URL does not create a network route.

Signing can be performed by the SDK using credentials; the act of generating the URL does not itself prove that the object exists or that the recipient can reach the endpoint. A signed URL conveys temporary access under the signing identity's permissions. Treat it as a secret while usable. S28

Exercise: add an alt branch for “user is not the document owner.” The API must refuse before issuing the URL. Explain why a valid storage credential does not automatically establish a user's application-level right to a document.

Architecture-specific syntax: learn later

Mermaid's architecture-beta syntax, documented from version 11.1.0, models services, groups, and edge connection sides. Its built-in icons include cloud, database, disk, internet, and server. Custom icon packs require registration; a service name alone does not automatically load a cloud-provider logo. S09

architecture-beta
    group platform(cloud)[Private platform]
    service user(internet)[User]
    service gateway(server)[Gateway] in platform
    service api(server)[Document API] in platform
    service objects(disk)[Object storage] in platform
    service metadata(database)[Metadata] in platform
    user:R --> L:gateway
    gateway:R --> L:api
    api:R --> L:objects
    api:B --> T:metadata

Begin with flowcharts for compatibility. Use architecture syntax only after checking the renderer in the system where your documentation will actually live. A successful render in one web editor does not prove support in an older wiki plugin.

Maintain a diagram as code

Use a predictable filename such as document-platform.mmd. Change one concern at a time: add a service, update an edge label, or remove an obsolete connection. Render after each change. In a review, ask both “does the syntax work?” and “is the relationship still true?” Git can track the history of these text changes; it does not validate their engineering meaning. S40

Keep a simple convention in your README: solid arrows are request paths, dotted arrows are optional or out-of-band only when explicitly labelled, and grouping boxes represent the boundary named in their title. Avoid relying on colour alone. Your diagram should remain readable in grayscale and when copied into an issue or printed.

Practice deliverable: a valid flowchart, one sequence diagram, and a short explanation of the chosen arrow conventions. The downloadable state diagram and Image Builder learning flow are optional extra exercises.

CHAPTER 05

Excalidraw

What to learn first

Excalidraw provides a canvas, basic shapes, text, arrows, image support, shape libraries, and editable .excalidraw files. Its sketch-like presentation is useful for exploring a design with other people. Start with rectangles and labels before spending time on icon collections. The official project also documents bound and labelled arrows and export to PNG/SVG. S10

Original teaching schematic. The downloadable Excalidraw and draw.io files contain editable versions of this logical design. This illustration is not a discovered cloud environment.

Draw a cloud diagram from a blank canvas

1. Write the title and question. Add “Private document platform — logical view — proposed.” Include an owner and date in your own working copy. Keep detailed network addresses out of the first sketch.

2. Make a five-component inventory. Internal user, gateway, document API, object store, metadata database. Put these in a row/list outside the canvas first. Each component needs one responsibility; remove any icon whose purpose you cannot explain.

3. Draw boundaries before components. Create a large rectangle for the private application environment. Give it a subtle fill or dashed outline and send it behind the other objects. Put the user outside the boundary. Do not label the rectangle “VPC” unless it actually represents a virtual network in your intended deployment.

4. Place boxes with room for labels. Put the gateway on the left, the document API in the middle, and storage plus metadata on the right. Leave enough space for a connector label without squeezing text between shapes. Start with equal-sized application boxes.

5. Add responsibility labels. Use two lines when helpful: “MinIO / AIStor” and “object bytes.” For the database, use “metadata” and examples such as “owner, object key, status.” A database icon and a disk icon are not explanations on their own.

6. Connect the request path. Draw user → gateway → API. Bind arrow ends to the relevant shapes, then move a box to check that the relationship follows. An arrow that merely touches a box can become misleading after a layout change. Add arrow labels describing the interaction, not just “data.” S10

7. Add the storage relationships. Connect the API to object storage with “S3 API over HTTPS.” Connect the API to metadata with “metadata query.” This is a desired secure design; the later local lab deliberately uses HTTP only on loopback. Do not silently present the lab's transport as production TLS.

8. Separate administrative access. In a second frame or separate drawing, place an operator, an approved access path, and the management console. The storage console is not the S3 API endpoint. Add identity, approval, and audit questions to this view rather than cluttering the application path.

9. Mark omitted concerns. Add a short note: “Identity provider, backups, monitoring, and failure domains not shown.” You can draw them later. Omitting a concern from one view is acceptable; forgetting it entirely is not.

10. Align and review. Use consistent spacing, line weights, and text size. Prefer one diagram that can be explained on one screen. When labels overlap, move components instead of making the font too small.

11. Save an editable source. Save the .excalidraw file locally and reopen it. Confirm you can move a node, edit its label, and follow the associated arrows. Keep your working source separate from a sanitised sharing copy. S10

12. Export a readable view. Export SVG for crisp scaling or PNG for broad compatibility, then inspect the actual export. Check margins, small text, transparent backgrounds, and whether editable scene data is embedded. Excalidraw export options can embed scene data, which is useful for editing but may expose more than the visible image. S13

Add AWS, Azure, GCP, or Kubernetes icons

Open the library controls and browse the Excalidraw libraries directory. Search for the cloud platform or component collection you need, add a relevant library, then place only the symbols that improve understanding. The directory includes community-contributed cloud and system-design collections. Verify the collection's age, accuracy, and licensing rather than assuming all icons are current vendor assets. S11

For formal AWS documentation, consult AWS's architecture icon resource. An imported library can be convenient, while an official icon pack gives you a vendor-maintained reference. Keep provider icon sets consistent within one diagram. If an icon is difficult to import, use a labelled box instead of blocking the whole exercise. S17

Do not let an icon dictate the design. A storage symbol does not tell you whether the service is managed, self-hosted, public, private, encrypted, replicated, or backed up. Put those facts in the relevant deployment or operations view.

Place cloud resources correctly

For a follow-up AWS deployment view, choose either managed Amazon S3 or self-hosted AIStor explicitly. They are not the same deployment with a different logo.

Mermaid to Excalidraw: useful, but not lossless

A conversion can give you a starting layout. The official Mermaid-to-Excalidraw package documents native conversion support for flowcharts, with other diagram types rendered as images and some shapes falling back to simpler shapes. That means an imported result may not consist of individually editable native objects. Availability in the web interface can vary; the supplied native .excalidraw example avoids depending on a particular menu. S12

Keep the original Mermaid text. Once you manually rearrange a converted sketch, do not assume the Mermaid source will update automatically. Declare which file is authoritative and treat the other as a derived view.

Three practice challenges

Challenge A: recreate the five-component example without importing the supplied file. Explain every arrow, then compare your drawing to the reference.

Challenge B: add a second application instance. Identify whether the gateway, database, storage, and host are still single points of failure. Merely duplicating the API box does not make the whole system highly available.

Challenge C: make a stakeholder version with no IP addresses or implementation jargon, and an engineer version with protocols, trust boundaries, and open operational questions. Both must describe the same underlying design.

Finish condition: another person can identify the user path, storage responsibility, and three missing operational concerns without your narration.

CHAPTER 06

draw.io

Use structure when the diagram needs to be maintained

The browser editor commonly called draw.io is available through diagrams.net. It supports shape libraries, connectors, templates, and image exports useful for cloud and network diagrams. Treat the editable .drawio file as the working document and the exported image as a view for readers. S14

Recreate the same architecture, not a different one

Start a local diagram. Choose a blank diagram and local/device storage when available, or use an organisation-approved storage integration. Name the file document-platform.drawio. Avoid connecting an external account merely to complete a beginner exercise.

Enable only the relevant shapes. Use More Shapes to enable the cloud or networking library you need. Draw.io documents this workflow for AWS libraries. Templates can accelerate a layout, but remove services that do not belong to your design. A template is not an approved architecture. S14

Build containers and relationships. Add a boundary, place the gateway and API, then add storage and metadata. Use connectors attached to shapes rather than independent line segments. Label the communication. Reposition one component and check that the relationship is still intelligible.

Organise for review. Keep the logical application view separate from a deployment page or layer. Use the same names across views. “Document service,” “upload API,” and “app server” should not accidentally become three names for the same component.

Save and reopen. Confirm that boxes, text, and connectors remain editable. Export a clean SVG or PNG. If you choose to include a copy of the diagram in an image export, review the embedded source for confidential labels or hidden information. Draw.io's export options can preserve editable diagram data. S14

Bring in Mermaid carefully

In the current documented workflow, use Arrange → Insert → Mermaid, or the toolbar's insert control. Paste a supported diagram and choose the appropriate insertion mode. Recent draw.io versions can place native shapes inside a Mermaid container while retaining the Mermaid source. Editing that source regenerates the layout: style/label overrides can be retained, but manual geometry changes can be discarded. An image insertion is a single SVG rather than independently editable shapes. S15

A July 2026 draw.io update documents this newer editing behaviour. Older builds and older help pages can behave differently, so check the application you actually use. Do not assume that every installed desktop copy or enterprise integration has the same feature set. S16

Your exercise: insert 02-document-platform.mmd, move a shape, then edit the Mermaid source and regenerate. Observe what remains and what changes. Save the original .mmd separately even when source is retained inside the diagram.

Excalidraw or draw.io?

For this learning path, use Excalidraw when you are still discussing responsibilities and alternatives. Use draw.io when precise layout, multiple views, and consistent cloud symbols become useful. Use Mermaid when reviewing relationships as text is more important than manual placement. These are workflow recommendations, not claims that one tool cannot perform another tool's job.

You do not need to maintain three equally authoritative diagrams forever. Choose one source of truth for each view. For example: context.excalidraw for exploration, deployment.drawio for the reviewed deployment, and download-sequence.mmd for request behaviour. Write down the rule in the project README.

Practice deliverable: a readable draw.io diagram, its image export, and a short note naming the authoritative file for each view.

CHAPTER 07

Object storage

Understand what MinIO stores

For this guide, concentrate on the S3 object interface: a client stores bytes under a bucket and an object key, with associated metadata. Amazon S3 is a managed AWS service; MinIO/AIStor provides an S3-compatible service that you can operate on your own infrastructure. API compatibility is not a promise that every AWS feature, administrative API, or operational characteristic is identical. S18 S22 S48

Concept Meaning in the lab Example
Bucket Top-level object container and a policy/versioning boundary learning-docs
Object key The identifier used to address an object's bytes lab/sample.txt
Prefix The beginning of a key, used for organisation and filtering lab/
Endpoint The server URL used by the client http://127.0.0.1:9000
Access key / secret key Credentials used to authenticate signed requests Generated docapp identity and its secret
Version ID Identifier for a stored version, when versioning is enabled Returned after a successful versioned write
Metadata Extra descriptive fields associated with an object The lab's SHA-256 field

An object key that contains / can look like a directory path, but S3's key/prefix model is not a traditional filesystem directory hierarchy. Keep that distinction in mind when designing policies or moving data. A bucket/prefix arrangement is not a substitute for an application's document ownership model. S19

Object, file, and block storage are different interfaces

Use object storage when your application wants to put and retrieve whole objects by key. Use a shared filesystem when the workload genuinely depends on filesystem operations and semantics. Use block storage as a disk-like device beneath a filesystem or database when appropriate. In the teaching architecture, a database stores searchable document records, while object storage stores the associated bytes; this separation is a design choice for the exercise, not a requirement imposed on all applications.

Do not install MinIO merely because you need “some storage.” Write down the access pattern first: object size, operation rate, concurrency, retention, recovery needs, and which systems must read the data. Then choose the storage interface and operational model.

Versioning, retention, replication, and backup

Versioning keeps multiple versions of an object rather than simply replacing the previous one. In a typical version-enabled S3 workflow, an ordinary delete adds a delete marker; deleting a specific version can remove that version permanently. Version history consumes storage and needs its own retention consideration. The supplied lab enables versioning and demonstrates writing two versions without deleting either. S27 S34

Retention/lifecycle is a policy decision about how long objects and old versions should remain. Do not enable automatic deletion as your first exercise. Define which objects it covers, who approved the rule, and how you would recover from an incorrect policy. The lab intentionally does not install a lifecycle deletion rule.

Replication creates or maintains another copy according to a configured process. Backup should be judged by whether you can recover the required data and metadata from the failures you care about. A second copy that shares the same credentials, deletion path, or physical failure domain may not provide the independence your recovery plan needs.

Erasure coding divides data into data/parity shards to tolerate certain storage failures. AIStor documents erasure sets, quorum, and parity-dependent behaviour. It does not make one laptop resilient to loss of that laptop, and a one-volume container exercise must not be presented as a distributed erasure-coded deployment. S33

The minimum operating questions

Before describing a real storage system as production-ready, ask who patches it, who rotates credentials, what the capacity alerts are, how a lost disk or host is handled, how TLS is configured, and how you restore both objects and application metadata. Define an acceptable recovery point objective (how much recent data loss is tolerable) and recovery time objective (how quickly service must return). Those are business/engineering requirements to choose and test, not values supplied by a diagram.

Step 6 — inspect the policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyLearningBucket",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": ["arn:aws:s3:::learning-docs"]
    },
    {
      "Sid": "ReadWriteOnlyLabPrefix",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": ["arn:aws:s3:::learning-docs/lab/*"]
    }
  ]
}

Bucket-level actions refer to the bucket resource; object actions refer to object resources. AIStor's policy system uses IAM-compatible structures, and access not granted by the relevant policies is denied. A user can authenticate successfully while still lacking permission for a particular action. S24

For this simple single-user lab, bucket listing is allowed broadly within learning-docs, while object access is prefix-scoped. Do not describe the policy as hiding other prefixes' object names. That would require additional policy conditions and testing.

Step 7 — run the Python storage exercise

Create and activate a virtual environment before installing the dependency:

# macOS / Linux / WSL
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python s3_demo.py

For PowerShell, activation is optional; you can call the environment's Python directly:

py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe s3_demo.py

The script reads the generated application credentials, uses Signature Version 4 and path-style addressing for the local endpoint, uploads sample.txt to learning-docs/lab/sample.txt, downloads it, and compares SHA-256 digests. It lists objects under lab/, then checks that listing all buckets is denied. The example is limited to 10 MiB per input file and deliberately uses a small-object approach; it is not a performance or multipart-upload benchmark. Boto3 documents S3 upload and signed-URL APIs, while MinIO documents S3 SDK compatibility. S28 S29 S48

Expected evidence: a successful write, a returned version ID when enabled, a matching SHA-256 result, the object key in the listing, and a denied all-buckets operation. An unexpected allow is a failed permission test, not a reason to remove that test.

The application script does not use root credentials, create buckets, administer the server, or delete objects. The SHA-256 comparison verifies that these downloaded bytes match the sample; it does not independently prove long-term durability. Do not use an ETag as a universal substitute for a content hash.

Step 8 — practise versioning and recovery without deleting data

Edit the local sample.txt so that it says “Version two,” run the demo again, then inspect the stored versions using the administrator alias:

python s3_demo.py
mc --config-dir .mc version info lab/learning-docs
mc --config-dir .mc ls --versions lab/learning-docs/lab/sample.txt

To retrieve an earlier version, copy its exact version ID from the listing and substitute it below:

mc --config-dir .mc cp --version-id "PASTE_VERSION_ID_HERE" \
  lab/learning-docs/lab/sample.txt ./restored-sample.txt

Open restored-sample.txt and confirm it contains the earlier bytes. The application's policy deliberately does not include historical-version access or version deletion; the administrator performs this learning step. The evidence you want is an actual restored file, not merely a screenshot of a versioning toggle. S27 S34 S52 S53

Step 9 — understand a presigned download

python s3_demo.py --show-url

This deliberately prints a short-lived bearer URL for the current sample object. Open it locally while valid and compare the content. Do not paste the URL into shared logs or tickets. It uses the application's permissions and the local endpoint, so it will not magically work from a colleague's computer: their 127.0.0.1 is their computer, not yours. A production or team design needs an approved user-reachable endpoint, appropriate TLS, and application-level authorisation before signing. S28

Generating a URL is not the same as making a bucket public. It grants the permitted operation to someone who possesses the usable URL. Expiration, credential validity, permissions, HTTP method, and the signed endpoint all matter. Do not change the hostname inside a signed URL as a casual workaround.

Step 10 — stop safely and record evidence

python lab.py stop

This stops/removes the lab containers while retaining the named data volume. Start again and retrieve the sample to check persistence across this lifecycle. That still does not test loss of the host or data volume. S32

Destructive cleanup is a separate decision. docker compose down --volumes removes the lab's named volume and its stored objects, including versions. Do not run it until you intentionally want to discard the lab data. It does not mean your .env, .mc, or license file have also been removed.

Keep a sanitised record of the server image/digest, mc version, Python/Boto3 version, test outcomes, and any deviations from the guide. Record configuration, not secrets. Freeze the complete Python environment after a successful test when you need a transitive dependency record; the included requirements file pins only the direct SDK dependency.

Check your understanding before revealing the answers

1. Why is a NotebookLM citation not enough on its own?

The cited passage can be incomplete, misinterpreted, stale, or narrower than the claim. Open it, inspect its context, and separate the documented fact from an inference or design decision.

2. Does uploading a documentation homepage import the whole site?

Do not assume so. Import the specific relevant pages and inspect what was actually included. Website-source behaviour is documented in the source-import help. [S02]

3. When should you use a sequence diagram instead of adding more arrows to a component view?

When the question is about the order and conditions of one interaction, such as authorising a download before returning a URL. A static relationship view should not be forced to show every step.

4. Can a Mermaid or Excalidraw diagram deploy the cloud resources it shows?

Not by itself. The diagram represents a design. Deployment requires separately reviewed tooling and configuration, and the runtime still needs verification.

5. Why is placing an Amazon S3 bucket inside a private subnet misleading?

A managed regional S3 service is not an instance hosted inside your subnet. Draw the service and the relevant VPC access mechanism separately. [S18] [S20]

6. Is a key such as lab/sample.txt necessarily a real directory and file?

In S3's key model, it is an object key with a slash-containing prefix. A console can present it like a folder hierarchy without making it a traditional filesystem directory. [S19]

7. Why does the demo use an application identity rather than root?

The application's task is object access under one prefix, not server administration. Separate credentials make the intended permission boundary explicit and testable. [S23] [S24]

8. What does the lab's denied list-buckets check prove?

Only that this identity was denied that operation under the tested configuration. It does not prove every unwanted action is denied. Add a permission test matrix for the real application's actions and resources.

9. Is a presigned URL a replacement for application authorisation?

No. The application should establish the requesting user's right to the object before issuing the URL. Possession of a usable URL can confer the signed operation; it also needs a reachable endpoint. [S28]

10. Does versioning protect against loss of the only data volume?

No. All versions can still share that same failure domain. The recovery design needs appropriate independent copies and a tested restore procedure; the local lab does not establish either.

11. What is the difference between stopping the lab and deleting its volume?

Stopping/removing the containers with the documented stop action retains the named volume. Explicit volume removal discards the stored lab objects and versions. [S32]

12. What should you do when the sketch, Mermaid file, and draw.io file disagree?

Identify the declared source of truth, review which fact changed, and update the derived views deliberately. Do not assume round-trip conversion or automatic synchronisation.

After installing the lab requirements, run python -m unittest discover -s tests -v from the project root. The 16 tests use temporary files, fake credentials, and stubbed SDK responses; they do not start Docker or contact a storage server. Passing them checks selected code paths, not deployment success. See VALIDATION.md for the full test boundary.
