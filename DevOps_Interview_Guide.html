CHAPTER 01 Core

DevOps fundamentals & the delivery flow

Describe the system from a customer need to a measured production outcome. Tools enable the workflow; ownership, feedback, and risk control make it effective.

Beginner | explain the vocabulary

Distinguish CI, continuous delivery, continuous deployment, infrastructure as code, observability, and shared ownership. Use one concrete application throughout your answer.

Intermediate | operate the workflow

Explain the exact trigger, checks, artifact, environment promotion, identity, approval, deployment verification, and recovery path.

Advanced | defend the decisions

Discuss blast radius, trust boundaries, bottlenecks, team ownership, operational cost, audit evidence, and the failure modes of your own design.

Beginner

Explain the fundamentals accurately
Q001What is DevOps, without naming any tools?
Model answer / adapt to your actual experience

DevOps is a way of organizing software delivery so the people building a service also share responsibility for operating it well. I would describe small changes, automated verification, repeatable releases, and fast feedback from production. In an interview, I would connect these practices to an outcome such as fewer release failures or less manual work. A dedicated platform team can enable this model, but it should not become a handoff queue that removes ownership from application teams.

Expect this follow-upWhich part of your last delivery process had the longest wait?
Common mistakeDo not define DevOps as knowing Jenkins, Docker, and Kubernetes.
Link to question
Q002How do continuous delivery and continuous deployment differ?
Model answer / adapt to your actual experience

Both require a pipeline that keeps changes releasable. Continuous delivery can retain an explicit production release decision, such as an approval or business schedule. Continuous deployment automatically releases qualifying changes into production. CI is the earlier practice of integrating and verifying changes frequently. Automation alone does not prove quality: tests, security policy, rollback readiness, and production verification determine whether automatic release is reasonable.

Expect this follow-upCan a regulated service use continuous delivery?
Common mistakeDo not say every successful CI build must reach production.
Link to question
Q003What does an artifact mean in a delivery pipeline?
Model answer / adapt to your actual experience

An artifact is a versioned output that later stages consume: a container image, a package, a compiled binary, or a deployment bundle. I distinguish release artifacts from caches, temporary workspaces, and test reports. For a containerized application, I associate the image digest with the source commit, build run, test evidence, and configuration revision. This gives operators a reliable answer to what is actually running.

Expect this follow-upWhat would you record in a release manifest?
Common mistakeA mutable latest tag is not a sufficient release identity.

Intermediate

Implement, operate and troubleshoot
Q004Walk me through a normal application release.
Model answer / adapt to your actual experience

A developer opens a small pull request. CI performs fast checks and tests without production credentials. After review and merge, a trusted workflow builds an image, performs release checks, and records its digest. Staging deploys that digest and runs integration or smoke tests. Production promotion applies environment controls and verifies the same digest with production configuration. After rollout, I check user-facing health and preserve a recovery option. I name the owner and evidence at every handoff.

Expect this follow-upWhere are approvals enforced, and can a YAML author bypass them?
Common mistakeDo not finish your answer at deployment succeeded.
Link to question
Q005How would you reduce a slow release process?
Model answer / adapt to your actual experience

I first measure queue time, execution time, approval waiting, and retry time separately. I find the critical path rather than parallelizing everything. Common experiments include moving cheap deterministic checks earlier, running independent tests concurrently, caching trusted dependencies, right-sizing runners, and making approvals evidence-driven. I compare before and after at a consistent percentile and track failure rate so a faster but less reliable pipeline is not presented as a success.

Expect this follow-upHow would you prove that your cache is helping?
Common mistakeDo not remove important checks solely to reduce duration.
Link to question
Q006What does shift left mean, and what remains on the right?
Model answer / adapt to your actual experience

Shift left means getting useful security and quality feedback earlier, when changes are smaller and easier to correct. Examples include threat modeling, local validation, dependency checks, and pull-request policy. Runtime monitoring, vulnerability rescanning, incident response, and production access controls are still needed because deployment context and new threats change risk. My design combines early prevention with operational detection and learning. [S33]

Expect this follow-upGive an issue that static analysis cannot reliably detect.
Common mistakeEarlier scans do not eliminate the need for runtime security.

Advanced

Defend design, security and recovery decisions
Q007How do you balance delivery speed and reliability?
Model answer / adapt to your actual experience

I make the risk visible instead of treating speed and stability as opposites. Small changes, repeatable environments, and quick recovery can improve both. For a high-impact service I would use SLOs, release evidence, progressive exposure, and an agreed error-budget policy. I would separate low-risk configuration changes from high-risk schema or identity changes. The decision is not always deploy or freeze: reducing scope, using feature flags, or shipping a mitigation can be safer. [S35] [S36]

Expect this follow-upWhat changes when the error budget is exhausted?
Common mistakeDo not claim an SLO automatically defines a universal release freeze.
Link to question
Q008What should a platform team own?
Model answer / adapt to your actual experience

I would assign the platform team reusable capabilities such as approved runner pools, deployment templates, identity patterns, observability defaults, and paved-road infrastructure modules. Application teams should retain service behavior, data correctness, readiness signals, and on-call ownership appropriate to the organization. Security and operations help define guardrails and exceptions. I would treat the platform as a product, measure adoption and friction, and offer an escape path with explicit support boundaries.

Expect this follow-upHow would you handle a team whose needs do not fit the template?
Common mistakeDo not centralize every application decision into one blocking team.
Link to question
Q009What evidence demonstrates five to six years of experience?
Model answer / adapt to your actual experience

I would give a real example with constraints, a decision I personally made, implementation details, an incident or trade-off, and a measured result. For example, I might explain why separate deployment identities reduced blast radius and what operational overhead this introduced. I distinguish what I owned from what another team delivered. When a topic is lab-only for me, I say so and explain what would need validation in production.

Expect this follow-upWhich design would you change now, and why?
Common mistakeNever invent scale, achievements, certifications, incidents, or metrics.

Choose a branching model based on release cadence and support obligations. Protect integration; do not confuse a branch name with an environment security boundary.

Beginner

Explain the fundamentals accurately
Q010Explain working tree, index, commit, and remote.
Model answer / adapt to your actual experience

The working tree contains my editable files. The index, or staging area, selects the next snapshot. A commit records a snapshot with metadata and parent relationships. A remote is another repository location that I fetch from or push to. This distinction explains why editing a file does not automatically change a commit and why committing locally does not publish it. I use git status and git diff, including the staged diff, before creating a commit. [S41]

Expect this follow-upWhat does git diff --staged show?
Common mistakeDo not treat git add as uploading to the remote.
Link to question
Q011What is the difference between merge and rebase?
Model answer / adapt to your actual experience

Merge combines histories and may create a merge commit. Rebase replays commits onto another base, creating new commit identities for the replayed changes. I choose based on the team's history policy. Rebasing a private feature branch can simplify review; rewriting a shared branch requires coordination. Neither operation replaces integration tests. If history must be rewritten, I prefer a guarded push such as force-with-lease over an unqualified force push.

Expect this follow-upWhy do rebased commits have different SHAs?
Common mistakeDo not casually rebase protected or widely shared history.
Link to question
Q012When would you use revert instead of reset?
Model answer / adapt to your actual experience

Revert creates a new commit that counteracts an earlier change, so it is usually appropriate for shared history. Reset moves a reference and, depending on its mode, may also change the index or working tree. I inspect and preserve uncommitted work before using destructive options. In a production incident, reverting application code is only one possible recovery action: database or external side effects may not be reversible by Git. [S52]

Expect this follow-upWhat extra care is needed when reverting a merge commit?
Common mistakeNever suggest reset --hard as the default shared-branch rollback.

Q013What branch protection would you implement?
Model answer / adapt to your actual experience

I would require reviewed pull requests, meaningful status checks, restricted direct pushes, and explicit control of force pushes and deletion. Sensitive paths such as workflows and infrastructure should have designated reviewers. Where available and appropriate, a merge queue verifies the actual combination being integrated. I document emergency bypass rights, audit their use, and verify that the workflow producing a required check cannot be trivially skipped or replaced. [S01] [S02]

Common mistakeA CODEOWNERS file alone is not proof that its review is enforced.

Q014How do you handle a production hotfix?
Model answer / adapt to your actual experience

I start from the deployed release line, not an assumed local main. I create the smallest fix, keep essential verification, and route it through an audited emergency process. After release I ensure the fix is integrated or backported to every relevant maintained branch and add a regression test. I preserve the original artifact and record why any normal control was shortened. A hotfix is not permission to leave the branches inconsistent.

Expect this follow-upHow would this differ with trunk-based development?
Common mistakeDo not patch a release branch and forget main.

Q015How do feature flags support short-lived branches?
Model answer / adapt to your actual experience

A flag can separate merging code from exposing behavior. This lets incomplete work integrate in small increments while limiting user exposure. I treat flag configuration as production configuration with ownership, audit, safe defaults, and a removal date. I test important enabled and disabled paths and account for authorization and data-model compatibility. A flag should not hide a database change that already breaks older application versions.

Expect this follow-upWhat is your process for removing stale flags?
Common mistakeFlags are not a substitute for tests or access control.

Q016How would you choose branching for ten services and two supported product versions?
Model answer / adapt to your actual experience

I would first ask whether the services deploy independently and whether both versions require ongoing fixes. I would prefer a simple protected integration line per independently released codebase, with short-lived branches and explicit release branches only for maintained versions. A release manifest can coordinate compatible service versions without forcing every service into one long-lived environment branch. I would define backport ownership, compatibility tests, and end-of-support rules.

Expect this follow-upWhen would a monorepo improve this design?
Common mistakeDo not equate one repository with one mandatory deployment unit.

Q017How do you prevent a green pull request from breaking main?
Model answer / adapt to your actual experience

A pull request may pass against an older base or in isolation. I would verify the merged result using an integration branch or merge queue, run checks affected by shared libraries, and avoid overly narrow path detection. The trusted build after merge remains essential. Required check names should be stable, and queued changes need the appropriate workflow trigger. I would test failure behavior deliberately rather than assuming branch protection covers every event. [S01]

Expect this follow-upWhy may merge_group be needed in GitHub Actions?
Common mistakeA previously green PR is not proof that the final merge combination is green.
Link to question
Q018What would you do after a secret is committed?
Model answer / adapt to your actual experience

I would treat the credential as exposed and revoke or rotate it first, then investigate its scope and use. Removing it in a later commit does not erase repository history, clones, logs, or caches. I would coordinate any history rewrite, clean affected artifacts where feasible, and improve prevention. Audit evidence and access reviews help determine whether exposure became misuse. I would never print the secret again just to prove that it existed. [S02] [S20]

Expect this follow-upHow do you handle a secret embedded in a published image?
Common mistakeDeleting the file is not credential revocation.

CHAPTER 03 Core

CI/CD architecture & release strategies

Understand the design independently of a vendor. This makes it easier to translate between GitHub Actions, Azure Pipelines, and Jenkins.

Build once, promote deliberately

Promote the same tested artifact digest across environments. Supply environment-specific configuration separately and record its revision. Rebuild when you intend to produce a new artifact.

Separate trust zones

Untrusted pull-request jobs should not share production credentials, privileged runners, writable caches, or deployment permissions with release jobs.

Treat recovery as a release feature

Define the last known good version, health signal, decision owner, and data compatibility before deploying. A successful command is not customer recovery.

StrategyMechanismPrimary caution
RollingGradually replace replicasOld and new versions coexist; capacity and readiness must support overlap.
Blue/greenPrepare another environment and switch trafficCosts extra capacity; data and active sessions remain shared risks.
CanaryExpose a small traffic or user segment, evaluate, then expandNeeds reliable traffic control and statistically meaningful signals.
Feature-flag releaseDeploy code separately from enabling behaviorFlags require lifecycle management, safe defaults, and compatible code paths.

Q019What is the difference between a stage, job, and step?
Model answer / adapt to your actual experience

A stage is a logical phase such as validate or deploy, depending on the platform. A job groups work scheduled onto an execution environment. A step is an action or command within a job. Jobs are often isolated and need explicit dependencies and data transfer. I avoid assuming that a file, shell variable, or login from one job exists in another. GitHub Actions primarily models workflows, jobs, and steps; Azure Pipelines also exposes stages directly. [S01] [S08]

Expect this follow-upHow would you pass a build digest to a deployment job?
Common mistakeVendor terms are similar, but not identical.
Link to question
Q020Why distinguish caches from artifacts?
Model answer / adapt to your actual experience

A cache accelerates repeatable work such as restoring dependencies and may be absent or invalidated. A release artifact is the intentional output being tested or promoted. I key dependency caches by relevant inputs and preserve artifact identity independently. A secure pipeline must still work correctly on a cache miss. I also separate cache write permissions by trust level so untrusted code cannot poison a later privileged build. [S02]

Expect this follow-upWhat belongs in the cache key?
Common mistakeDo not use a cache as the authoritative release store.
Link to question
Q021What does a quality gate do?
Model answer / adapt to your actual experience

A quality gate decides whether evidence satisfies a stated policy before a change advances. It might require passing tests, validated infrastructure, an acceptable security risk assessment, or a reviewed release. I describe what happens when the gate fails and who can approve a time-limited exception. A report that is generated but ignored is visibility, not an enforced gate. Gates should produce actionable feedback rather than only a generic red status. [S33]

Expect this follow-upHow do you prevent an exception from becoming permanent?
Common mistakeDo not say security scanning exists when its failures are silently ignored.

Intermediate

Q022How do you promote the same image across environments?
Model answer / adapt to your actual experience

I build once in a trusted workflow and obtain its immutable registry digest. The release record associates that digest with commit, tests, and security evidence. Staging and production each reference the digest, with separate configuration and secrets. Promotion changes environment state, not application bytes. If registries differ, I copy the exact artifact and verify its identity according to the registry and image format. I also preserve enough retention to perform recovery.

Expect this follow-upWhat changes when production requires a different compiled configuration?
Common mistakeA rebuild using the same source commit can still produce different bytes.
Link to question
Q023How would you make deployment retries safe?
Model answer / adapt to your actual experience

I distinguish retrying an idempotent operation from repeating a side effect. Applying a declarative manifest may be safe when the desired state is unchanged; sending a payment or rerunning a non-idempotent migration may not be. I use bounded retries with backoff only for transient failures, record operation identity, and check resulting state. I do not retry a failing security gate or deterministic test merely to obtain green.

Expect this follow-upWhich stage should not be automatically retried in your project?
Common mistakeRetry is not a fix for an unknown failure.
Link to question
Q024How do you deploy a database change safely?
Model answer / adapt to your actual experience

I prefer expand-and-contract: add backward-compatible schema first, deploy code that works with both shapes, backfill carefully, switch reads or writes, then remove old schema only after the rollback window closes. Migrations need locking or a single executor, timeout behavior, backup and restore expectations, and observability. I assess whether a reverse migration is truly safe. Rolling back application replicas cannot recover data already transformed or deleted.

Expect this follow-upWhat happens when old and new application versions write concurrently?
Common mistakeDo not promise rollback for every schema migration.

Advanced

Q025How do you prevent an older deployment from overwriting a newer one?
Model answer / adapt to your actual experience

I serialize by service and target environment, not merely by workflow filename. I associate every release with a monotonic or otherwise validated revision and reject stale promotions. Cancellation policies must respect stateful operations: interrupting an infrastructure apply or migration can be dangerous. The system needs a documented queue policy and an operator recovery path. Concurrency controls reduce overlap; they do not automatically guarantee business ordering or distributed consistency. [S01]

Expect this follow-upWhat if two repositories can deploy the same service?
Common mistakeA per-repository lock cannot coordinate all independent writers.
Link to question
Q026Design release verification for a canary.
Model answer / adapt to your actual experience

I would define the baseline, target population, exposure steps, observation windows, and rollback criteria before starting. Signals include error ratio, latency distribution, saturation, and a relevant business outcome. I compare versions or cohorts, account for low traffic and delayed failures, and stop on missing telemetry rather than interpreting it as success. I explicitly address session affinity, background workers, and irreversible side effects. Traffic weighting requires an appropriate controller, gateway, or mesh.

Expect this follow-upHow would you canary a queue consumer rather than an HTTP service?
Common mistakeTwo Deployments alone do not provide automated canary analysis.
Link to question
Q027How do you make a pipeline auditable without making every step manual?
Model answer / adapt to your actual experience

I automate evidence collection: reviewed source revision, workflow revision, dependency lockfiles, artifact identity, test and scan results, identity used, approval event, and deployment verification. I protect the evidence store and define retention and access policy. High-risk changes can require additional review while standard low-risk changes follow preapproved controls. Auditability comes from traceable, trustworthy decisions; a screenshot of a green pipeline is weak evidence on its own. [S34]

Expect this follow-upWhich evidence could a compromised builder forge?
Common mistakeA manual approval is not proof that the approver examined relevant evidence.

Q028What is a GitHub Actions workflow?
Model answer / adapt to your actual experience

A workflow is a YAML-defined automation stored under .github/workflows. An event starts a run, which contains jobs. Each job selects a runner or execution environment and performs steps. A step can invoke an action or run a command. I would explain the trigger, permissions, dependencies, timeout, and outputs before adding deployment logic. My first workflow should be understandable enough that a reviewer can identify its trust boundary. [S01]

Q029How do push, pull_request, and workflow_dispatch differ?
Model answer / adapt to your actual experience

Push responds to a repository update; pull_request is suitable for validating proposed changes; workflow_dispatch provides an explicitly initiated run with optional inputs. Their event payloads and checked-out revisions can differ. I would use pull-request validation without deployment rights and a separate trusted path for release. Manual dispatch does not automatically make an arbitrary selected branch or input safe. I validate inputs and restrict which ref can access a protected deployment environment. [S01]

Expect this follow-upWhat commit is being tested on a pull-request run?
Common mistakeA manual button is not an authorization policy.

Q030What are hosted and self-hosted runners?
Model answer / adapt to your actual experience

Hosted runners are managed execution environments supplied by the platform. Self-hosted runners are infrastructure the organization operates. I choose based on network reachability, specialized hardware, cost, and isolation requirements. Self-hosting also means patching, cleaning workspaces, protecting identities, and handling capacity. A private runner on a trusted network must not execute arbitrary untrusted pull-request code just because it is convenient. [S02]

Common mistakeSelf-hosted does not automatically mean more secure.

Q031How do variables, secrets, and contexts differ?
Model answer / adapt to your actual experience

Variables hold configuration; secrets hold sensitive values with controlled access and masking features; contexts expose workflow data such as event, job, inputs, and outputs. I distinguish expression evaluation from shell expansion. Repository names, PR titles, and inputs can be untrusted even when they arrive through a context. I avoid embedding untrusted expressions directly into shell scripts and instead pass values through environment variables and quote them appropriately. [S01] [S02]

Expect this follow-upWhy is a PR title dangerous inside a shell command?

Q032What does needs do?
Model answer / adapt to your actual experience

needs declares that a job depends on one or more other jobs. It creates ordering and allows consumption of their declared outputs. It does not automatically transfer files or credentials. Dependent jobs are normally affected by failure or skipping of their dependencies, so I inspect conditions and status functions when something does not run. Cleanup and reporting may need carefully chosen conditions without overriding safety gates on deployment. [S01]

Expect this follow-upHow would you collect test results after a failure?

Q033What is the GITHUB_TOKEN?
Model answer / adapt to your actual experience

It is the workflow-provided token used for GitHub API and repository operations according to its granted permissions. I set minimal workflow defaults and elevate only specific jobs. It is different from the OIDC identity token used to obtain cloud credentials. A workflow can have permission to request an OIDC token yet still have no authorization to modify Azure. That authorization is controlled by federation trust and Azure role assignments. [S02] [S03]

For a small value such as an image digest, a step writes an output to GITHUB_OUTPUT, the job exposes that output, and a dependent job reads it through needs. Q035How would you use a matrix without wasting resources?

I use a matrix for combinations that actually represent supported environments, such as selected language versions and operating systems. I can include or exclude combinations and limit parallelism when runners or external services are constrained. fail-fast determines whether one failure cancels other matrix work. Q036How do you build a reusable workflow?

Q193A production rollout and a database migration both fail. How do you recover?
Model answer / adapt to your actual experience

I identify the smallest safe way to restore service, which may involve disabling a feature, completing a compatible migration, or restoring data under the recovery plan. I preserve a clear timeline and coordinate one change owner. I do not assume the application and database can be independently reset.

Safe lab contract

Use throwaway repositories and disposable, approved cloud/cluster environments. Read each README before execution. Never paste real secrets into the guide or Git. LAB 01 Local CI baseline

Prerequisites. Python 3.10+; no cloud account.

Task. Run the app and policy unit tests from the project root. Start the service, query /healthz and /readyz, and stop it cleanly. Introduce a failing assertion, observe failure, and then restore it.

Show the interviewer. Test output, endpoint responses, and an explanation of why a failing process must stop a CI job.

Failure exercise. Set APP_READY=false for a local process; explain why readiness is 503 while liveness remains 200.

Cleanup. Stop the local process; no cloud resources are created.

LAB 02 GitHub Actions: first pipeline

Prerequisites. Disposable GitHub repository; permission to configure Actions.

Task. Install templates/github-ci.yml under .github/workflows/. Push a feature branch, open a PR, inspect the event/ref/commit, and configure the appropriate required check.

Show the interviewer. A passing and a failing run linked to the tested revision; explain job versus step, permissions and runner lifetime.

Failure exercise. Break one unit test. Confirm the merge policy rejects the change instead of merely showing a red icon.

Cleanup. Remove the disposable workflow or repository through your normal process; revoke any temporary access.

LAB 03 Azure OIDC and non-production publish

Prerequisites. Sandbox Azure subscription, non-production ACR, configured federated identity, and network access.

Task. Use the publish template only after configuring its environment and scoped identity. Match the actual issuer, subject and audience; publish the tested commit to ACR and capture its digest.

Show the interviewer. An identity diagram, least-privilege rationale, and an artifact reference using @sha256. Never include a token in your evidence.

Failure exercise. Use a separate disposable trust configuration with a wrong audience. Diagnose exchange failure before investigating registry RBAC.

Cleanup. Remove temporary identity federation and lab images when no longer needed; do not delete shared identities or registries.

LAB 04 Terraform module and change review

Prerequisites. Approved Azure sandbox, Terraform, Azure CLI and reviewed provider selection.

Task. Read examples/terraform/README.md. Configure inputs, initialize, validate and inspect a plan. Apply only after explicit review. Add a stable subnet map key and inspect the resulting change.

Show the interviewer. Reviewed plans, module input/output explanation, state location and a no-op plan after convergence.

Failure exercise. Predict the effect of renaming a resource address. Explain a moved block before attempting the refactor.

Cleanup. Review a destroy plan for only this lab. Retain state until Azure cleanup is verified.

LAB 05 Docker image lifecycle

Prerequisites. Docker-compatible environment and access to the declared base image.

Task. Build from the supplied Dockerfile, run on a local bound port, inspect the user and history, and compare build-stage tooling with the final runtime.

Show the interviewer. Image identity, test success, health response and a clear image-versus-container explanation.

Failure exercise. Override an application setting so readiness fails. Separate application configuration from image build failures.

Cleanup. Stop/remove the named lab container; remove only unused lab images.

LAB 06 Kubernetes release and diagnosis

Prerequisites. Disposable cluster, kubectl, available image and correct context.

Task. Read the Kubernetes README. Bootstrap the namespace, render and server-dry-run manifests, apply, inspect rollout status and test via port-forward.

Show the interviewer. Pod events, logs, ready EndpointSlices, rollout status and a request-path diagram.

Failure exercise. Use a deliberate readiness failure in the lab. Explain why a rollout can stall while a process is alive.

Cleanup. Remove the lab workload; inspect namespace contents before any namespace deletion.

LAB 07 GitOps reconciliation

Prerequisites. Disposable Argo CD installation with reviewed project scope and repository access.

Task. Review the project and Application templates. Use one controller to own the workload. Merge a desired-state change and observe diff, sync and health.

Show the interviewer. Commit-to-live-state trace; explanation of self-heal, pruning and ownership.

Failure exercise. Make a controlled live-only replica change while no HPA is active. Observe self-healing, then explain how an HPA changes ownership.

Cleanup. Follow the controller's configured finalizer/cascade process. Verify which resources remain before deleting them.

LAB 08 Security evidence and fail-closed policy

Prerequisites. Python only for the supplied normalized-report exercise.

Task. Run the gate tests and synthetic report. Inspect exit 1 for a policy block and exit 2 for missing/invalid evidence. Explain why the script is not a scanner.

Show the interviewer. A policy decision table and explicit real-world gaps: authenticated scan evidence, coverage, artifact binding and exception governance.

Failure exercise. Remove scan_status or corrupt the digest. The gate must not treat the report as clean.

Cleanup. Delete only temporary copies; no external security scanning or account access occurs.

LAB 09 Translate between CI platforms

Prerequisites. Access to a disposable Azure Pipelines or Jenkins environment, or a whiteboard-only session.

Task. Translate the GitHub pipeline into stages/jobs/resources in Azure Pipelines and stages/agents in Jenkins. Review the supplied scaffolds without claiming they deploy an application.

Show the interviewer. A mapping table plus different credential, approval, concurrency and agent-security decisions.

Failure exercise. Explain what happens when the service connection is unauthorized or the Jenkins agent is offline.

Cleanup. Remove disposable jobs and credentials via the platform's normal process.

LAB 10 Metrics and incident tabletop

Prerequisites. Spreadsheet/paper or Python; use synthetic events, not private logs.

Task. Define a service boundary and event schema. Calculate the five DORA measures where data allows, then add an SLO and one security-remediation metric. Run a release-failure tabletop.

Show the interviewer. Numerators, denominators, timestamps, assumptions, incident timeline and prevention action owner.

Failure exercise. Provide missing/ambiguous events and explain why unknown is not zero; distinguish causation from correlation.

Cleanup. Retain only anonymized or synthetic evidence. Do not invent improvement figures for an interview.

"""Fail-closed demonstration gate over normalized findings; NOT a scanner.

Exit 0: passes this limited policy. Exit 1: policy blocks. Exit 2: invalid report.
A real integration must authenticate scanner output and verify artifact identity.
"""
from __future__ import annotations
import json
from pathlib import Path
import re
import sys
from typing import Any


def evaluate(report: dict[str, Any]) -> list[str]:
    if not isinstance(report, dict) or report.get('scan_status') != 'complete':
        raise ValueError('report must contain scan_status=complete')
    if not isinstance(report.get('artifact_digest'), str) or not re.fullmatch(r'sha256:[0-9a-f]{64}', report['artifact_digest']):
        raise ValueError('report must identify an artifact with a SHA-256 digest')
    findings = report.get('findings')
    if not isinstance(findings, list):
        raise ValueError('findings must be an array, not a missing or null value')
    blocked: list[str] = []
    seen: set[str] = set()
    for finding in findings:
        if not isinstance(finding, dict):
            raise ValueError('each finding must be an object')
        identifier = finding.get('id')
        if not isinstance(identifier, str) or not re.fullmatch(r'[A-Za-z0-9_.:-]{1,100}', identifier):
            raise ValueError('finding id is missing or invalid')
        if identifier in seen:
            raise ValueError('duplicate finding id; normalize first')
        seen.add(identifier)
        severity = finding.get('severity')
        if severity not in {'critical', 'high', 'medium', 'low', 'info'}:
            raise ValueError('severity must be a normalized known value')
        for name in ('known_exploited', 'exposed', 'fix_available'):
            if not isinstance(finding.get(name), bool):
                raise ValueError(f'{name} must be a boolean')
        if finding['known_exploited'] or (severity == 'critical' and finding['exposed']):
            blocked.append(identifier)
    return blocked


def main(argv: list[str] | None = None) -> int:
    args = sys.argv[1:] if argv is None else argv
    if len(args) != 1:
        print('Usage: python gate.py REPORT.json', file=sys.stderr)
        return 2
    try:
        raw = Path(args[0]).read_text(encoding='utf-8')
        blocked = evaluate(json.loads(raw))
    except (OSError, ValueError, TypeError) as exc:
        print(f'INVALID REPORT: {exc}', file=sys.stderr)
        return 2
    if blocked:
        print('BLOCK: ' + ', '.join(blocked))
        return 1
    print('PASS: no finding violates this demonstration policy; not a security guarantee.')
    return 0


if __name__ == '__main__':
    raise SystemExit(main())
