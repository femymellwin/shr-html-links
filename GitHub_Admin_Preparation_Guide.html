01

Start with the right preparation target

Prepare to own the platform, not just write a workflow.

This guide is for a GitHub Administrator / DevOps role combining enterprise governance, CI/CD engineering, Azure integration and Python automation. The goal is to explain a design, implement a small version, deliberately break it, and show how you recover safely. It is a generic learning plan, not an employer-specific interview syllabus.

01 / Explain

Know the boundaries

Separate enterprise policy, organization permissions, repository controls, workflow permissions and Azure authorization.

02 / Build

Produce working evidence

Keep a sandbox repository with reviewed changes, reproducible tests, an automation report and an identity-federation exercise.

03 / Operate

Show safe judgment

Discuss blast radius, auditability, staged rollout, failure handling, rollback and developer communication.

Use this guide in three passes

First pass: score your current skills in the priority map. Second pass: complete the core labs and record evidence. Final pass: answer the interview questions aloud without reading the suggested answers. Treat a checkbox as complete only when you can explain and demonstrate the outcome.

Platform assumption

Examples target GitHub.com / GitHub Enterprise Cloud and Azure public cloud. GitHub Enterprise Server is a separately operated deployment with version-dependent capabilities. Check your actual platform, subscription, repository visibility, identity model and feature entitlements before following setup instructions. [1] [13]

Study estimates assume basic Git, Linux and cloud familiarity. They are planning recommendations, not claims about interview weighting, hiring criteria or guaranteed readiness. Use only authorized test organizations and non-production Azure resources.

Use roughly half the time for hands-on work, one quarter for targeted reading, and one quarter for troubleshooting drills and verbal practice. When a lab exposes a gap, move time from an already strong topic rather than adding more passive reading.

Avoid spending the first week memorizing every Azure service, doing advanced algorithm puzzles, or building a large Kubernetes platform. Establish GitHub governance, Actions and OIDC competence first. Deep GitHub Enterprise Server infrastructure operations are an extension track unless the environment specifically uses Server.

03

Git and repository fundamentals

Be able to help a developer recover without making the incident worse.

Practice branches, remotes, fetch versus pull, merge conflicts, rebasing, cherry-picking, tags, detached HEAD, the staging index and working-tree changes. Before explaining a history-changing operation, describe which of HEAD, the index and the working tree it affects. The official reset guide provides a useful model for this distinction. [30]

Practice promptWhat your explanation should cover
A developer committed to the wrong branch.Inspect status and history first; preserve the commit on a new branch; distinguish local-only changes from changes already shared with others.
Two feature branches conflict.Reproduce the conflict in a disposable branch, understand the intended behavior, resolve it, run tests and request review.
A bad change has already been merged.Discuss a reviewed revert versus a forward fix. Explain why rewriting shared history needs explicit coordination and is not a normal production recovery step.
A pipeline cannot find a tag or older commit.Inspect checkout depth, fetched refs and the exact commit under test. Separate a repository-history issue from a build-system failure.
A release needs traceability.Connect the source commit, release tag, test result, artifact identity, deployment run and rollback candidate.

Mini exercise: narrate your diagnosis

Readiness test

In two minutes, explain what is local, what is already shared, what you will preserve, and which command you will run next. Do not lead with a destructive reset or a force push.

04

Enterprise administration and access

Design predictable access, then prove that it is working.

Know the control hierarchy

Prepare the difference between an enterprise account, an organization, a team and a repository. Enterprise Cloud is hosted by GitHub; Enterprise Server is operated by the customer. For Server discussions, add upgrades, backups, recovery testing, capacity and integration compatibility to your study list. Do not assume that Cloud documentation describes every Server release. [1]

AreaWhat to study and practice
Repository accessCompare Read, Triage, Write, Maintain and Admin. Understand organization base permissions, direct collaborators and team-based grants. Owners have broad access; a lower direct grant is not a substitute for removing another higher-access path. [2]
Identity lifecycleStudy SAML SSO, SCIM provisioning and Enterprise Managed Users as distinct concepts. Explain authentication, account provisioning and repository authorization separately. Prepare an IdP outage / recovery discussion for the actual identity model. [3]
OnboardingPropose an owner-approved request, team assignment, least-privilege role, business justification, expiry for temporary access and a verification step.
OffboardingPropose disabling the identity and reviewing memberships, collaborator grants, credentials, app ownership and recovery contacts. Include a separate deploy-key review; removing a person does not invalidate every copy of a repository deploy key. [2]
Audit evidencePractice filtering organization events by actor, action, repository and date. Capture what changed, who changed it, when and under which approved request. Establish retention requirements rather than assuming an on-screen history is permanent. [36]
Operational inventoryMaintain proposed fields for repository owner, criticality, visibility, default branch, archived status, access-review date and exception owner. Separate facts from fields the credential cannot read.

Scenario: standardize 100 repositories

Start with a read-only inventory and identify the owners. Propose a baseline, a pilot group and a migration plan. Show the expected impact before changing permissions or merge controls. Ask owners to test representative workflows, then roll out in batches. Record exceptions with an expiry and a rollback owner. Finish by comparing the applied state with the intended state.

Interview signal

A strong answer is not "I will make everyone a maintainer" or "I will enforce it everywhere." Explain how access is justified, tested, reviewed and removed.

05

Repository governance and security controls

Know what each control does, and what it does not do.

Branch protection, rulesets and review ownership

Learn required pull requests, approvals, required status checks, force-push restrictions and bypass management. Multiple rulesets may apply together, and rulesets can coexist with branch protection. Diagnose the effective set of controls rather than inspecting just one settings screen. [4]

CODEOWNERS identifies reviewers; it does not independently force approval. Required code-owner review must be enabled in an applicable control. The file on the pull request's base branch matters, matching is case-sensitive, and later matching patterns take precedence. A listed team needs the required repository access. [35]

ControlPrepare this distinctionPractice outcome
Secret scanning / push protectionDetection of exposed credentials versus prevention during a push; coverage and bypass behavior must be understood. [13]Describe detection, authorized exception handling and remediation without creating or exposing a real credential.
Dependabot alertsNotification of known vulnerable dependencies. [13]Triage severity, exposure, fix availability, ownership and a remediation deadline.
Dependabot security / version updatesSecurity fixes are different from scheduled dependency freshness. Configuration of version updates is not proof that all security features are enabled. [13] [37]Explain the included weekly GitHub Actions dependency-update configuration.
Code scanning / CodeQLApplication-code findings are a different class of signal from a leaked secret or a dependency alert. [13]Explain how you would assign findings, validate fixes and govern justified dismissals.
Policy exceptionsTreat bypass as an accountable exception, not a routine release mechanism.Record the reason, approver, affected scope, expiry and follow-up verification.

Credential leak response to rehearse

Prioritize revoking or rotating the credential with its owning system. Establish what access it had, investigate possible use, replace dependent credentials safely, and confirm recovery. Removing a string from the latest commit is not the same as invalidating the credential. Document the exposure and prevention changes; handle any history cleanup as a separate coordinated task. [38]

Availability check

Security products, private-repository features and organization-wide controls depend on the plan and configuration. Verify the entitlement instead of assuming that every lab control is available in a personal sandbox. [13]

06

GitHub Actions: from YAML to a reliable pipeline

Build one pipeline you can explain line by line.

Prepare the execution model

Be comfortable with events, jobs, steps, runners, expressions, contexts, needs, job conditions, matrix strategy, timeouts, outputs and environment files. Understand workflow-level versus job-level permissions: when specific permissions are set, unspecified permissions are set to none. [6]

TopicExercise to completeQuestion to answer
Events and trustCompare push, pull_request, pull_request_target, workflow_dispatch, workflow_call and workflow_run. Add merge_group when required checks must run for a merge queue. [7]Which code and ref are used, who can influence the input, and what privileges are available?
Dependencies and conditionsCreate separate test and package jobs. Make a test fail and inspect downstream behavior.Which job should stop, and which diagnostic collection must still happen?
Matrix and parallel workRun the included tests on two Python versions. Compare fail-fast behavior and meaningful check names.Does parallelism shorten elapsed time, increase resource use, or both?
Caching versus artifactsUse a cache to accelerate dependency reuse; use artifacts for produced outputs that must be kept or transferred. They solve different problems. [31]Can you rebuild without the cache? Can you identify exactly which artifact was deployed?
ConcurrencyCancel obsolete CI work when appropriate; separately design serialization and supersession rules for deployments. [6]What happens when two releases arrive together? Is interrupting a deployment safe?
Performance analysisRecord queue delay, checkout, dependency installation, tests, packaging and deployment separately.Which measured bottleneck justifies your proposed optimization?

Design a reusable delivery path

Use a pull request path for validation and an explicitly trusted path for packaging and deployment. Propose building a versioned artifact, recording its source commit, promoting that artifact through environments, checking health and retaining a rollback candidate. Avoid describing "green CI" as proof that the deployed application is healthy.

Debugging order

Identify the failing run, event, commit and first failing step. Compare with the last successful run. Check inputs, permissions, credentials, network access, dependency changes and runner changes before editing random YAML. Reproduce the smallest failing command and verify both the fix and the relevant negative case.

Included practical example

The package contains examples/ci.yml: a two-version Python test matrix with minimal repository read permission, bounded runtime, SHA-pinned actions and merge-queue event support. It runs only offline unit tests; it is not a cloud-deployment pipeline.

07

Reusable automation and runner operations

Standardize the workflow while keeping execution boundaries explicit.

Choose the right abstraction

MechanismUse it forPrepare to explain
Reusable workflowA reusable job or multi-job workflow, invoked at the job level with workflow_call.Typed inputs, declared secrets, outputs, versioning and caller access. Permissions cannot be elevated through a nested call chain. [5]
Composite actionA bundle of steps called inside an existing job.The caller owns the surrounding job and runner. Do not treat a composite action as a multi-job workflow. [8]
JavaScript / Docker actionA custom packaged implementation when step composition is insufficient.Inputs, outputs, runtime compatibility, dependency maintenance, release versioning and testing.

Practice one reusable workflow with a typed Python-version input and one caller. Understand that environment secrets are not passed through on.workflow_call like ordinary declared secrets; a called job using an environment resolves its environment secrets there. Avoid indiscriminate secrets: inherit in a design discussion. [5]

Hosted versus self-hosted runners

Prepare the tradeoff between managed execution and operating your own runner environment. Runner groups control which repositories can use runners; labels and scale-set names participate in job routing. Self-hosted operation requires an explicit plan for patching, images, capacity, logs, networking and cleanup. [9]

Actions Runner Controller is a Kubernetes operator for orchestrating and scaling self-hosted runners. Study scale sets, the controller/listener/runner relationship, autoscaling limits and how logs survive ephemeral runner deletion. It is an optional depth topic after you understand ordinary runner operations. [10]

Runner scenario to rehearse

A job is queued although one runner appears online. Check routing requirements, runner-group access, availability, capacity and controller health in that order. Then verify connectivity and provisioning. Explain how you distinguish waiting for a runner from an environment approval delay.

Design exercise: separate untrusted validation work from privileged release work. Document allowed repositories, network reach, identity access, image lifecycle and disposal. Ephemeral execution is useful, but a container alone is not a complete trust boundary. [11]

08

Workflow security and production guardrails

Explain where untrusted input can become privileged execution.

Study untrusted pull-request code, event payloads, third-party actions, reusable workflows, caches and artifacts as inputs crossing trust boundaries. Pin reviewed actions to full commit SHAs, keep token permissions narrow, and avoid interpolating untrusted text directly into shell source. Do not run an untrusted pull-request head in a privileged pull_request_target job. [11]

BoundaryPreparation questionEvidence to design
Repository to workflowWho may edit the workflow and its local scripts?Reviewed changes to automation files, ownership rules and a controlled release path.
Workflow to GitHubWhat does this job need to read or write?A per-job permission justification, not a blanket write-all setting.
Workflow to AzureWhich repository, identity context and environment can obtain which Azure permissions?A federation configuration and narrow resource authorization.
Build to releaseHow do you know the deployment uses the artifact you tested?Source commit, artifact identifier, validation results and an immutable promotion reference.
Runner to internal networkCan code execution reach sensitive services or another identity?Network boundaries, runner isolation and a cleanup / rebuild policy.

Environment gates

Study allowed deployment branches/tags, reviewers and protected environment secrets. A deployment job must actually reference the intended environment for its rules to apply. Reviewers and other protections have plan/visibility restrictions; naming a job "production" does not configure a protection rule. [12]

Five checks before approving a deployment design

Identify the trusted source, the required approval, the exact artifact, the scoped identity and the recovery path. Ask who can bypass each control and what audit evidence remains.

Secret handling discussion

Never demonstrate security by printing credentials or full identity tokens. Use redacted evidence and only the necessary non-secret claim values for diagnosis. Explain why masking is a convenience rather than proof that a workflow cannot leak sensitive material. [11]

09

Azure OIDC and managed identities

This is a high-priority integration topic: make the identity flow unambiguous.

Explain the flow in plain language

1GitHub jobRequests an OIDC identity token.
2Microsoft EntraValidates the configured federated trust.
3Azure tokenA short-lived access token is obtained.
4Resource accessAzure authorization determines permitted operations.

OIDC replaces the need to store a long-lived Azure client secret for this federation path. The workflow still needs carefully configured trust, appropriate job permissions and an Azure identity. An OIDC identity token and an Azure access token are not the same object. [14]

For Azure Login federation, prepare either a Microsoft Entra application/service principal or a user-assigned managed identity with a federated identity credential. Assign permissions to the selected identity at the required scope. Do not confuse GitHub federation with the managed identity an application uses after it is deployed. [16]

SettingWhat you must explain
Issuer, subject and audienceMatch the trust to the actual token issuer, audience and subject. For Azure public-cloud login, the usual audience is api://AzureADTokenExchange. [15] [16]
id-token: writeAllows the job to request an OIDC token; it does not grant write access to Azure resources. [15]
Client, tenant and subscription IDsConfiguration identifiers for the chosen identity and subscription. They are not a substitute for trust or authorization. Follow organization policy for storing them. [16]
Azure RBAC scopePrepare to justify the operations needed and their resource scope. Separate deployment access from permission to create role assignments.
GitHub environmentRestrict the release context in GitHub as well as in the federation configuration. An environment subject is not itself a branch protection rule. [12] [15]
Do not memorize one subject string

GitHub documents both name-based and immutable-ID subject formats, including a 2026 rollout. Existing/customized repositories can differ. Inspect the actual subject configuration and match it exactly; adding an environment, renaming or transferring a repository can affect trust. Do not paste an older branch-only example into every setup. [15]

Authentication versus authorization troubleshooting

Login fails: verify the requested token permission, identity configuration, issuer/audience/subject matching and tenant. Login works but deployment fails: verify the target subscription, resource permissions, scope, service-specific prerequisites and network path. The app deploys but cannot read a secret: inspect the application's runtime identity and its data access, not just the CI identity.

Included smoke test

examples/azure-oidc-check.yml performs a manual, main-branch-only login using a preconfigured lab-azure environment. It does not deploy an application, create an identity or prove that the identity can update a service. The README explains the required Azure-side setup.

For your practice design, record the exact deployable version and the success criteria. Propose a smoke test and an observation window. Use App Service as the primary deployment lab when it fits your background and sandbox. Practice AKS troubleshooting conceptually or in an existing authorized lab; do not create an expensive cluster merely to memorize the pipeline steps. Check Azure costs and remove only the resources you deliberately created.

11

Python automation and GitHub APIs

Build reports first; make bulk changes only with explicit safety controls.

Python topics worth revising

Practice functions, dictionaries, lists, iteration, exceptions, type hints, JSON, file handling, command-line arguments, logging, timeouts and unit tests. Spend more time on defensive API integration than on unrelated algorithm puzzles. Explain what a partially successful run should report and how a retry differs from a fresh execution.

CapabilityPreparation target
REST collectionCall an organization repository endpoint, follow pagination and record only the fields returned. Visibility depends on the credential; an empty or short report is not proof that the organization has no other repositories. [21]
Rate-limit handlingRead Retry-After and rate-limit headers, wait rather than hammering the endpoint, and bound retries. Prefer events over unnecessary polling where appropriate. [20]
API versioningSend an explicit supported X-GitHub-Api-Version header. The included example uses 2026-03-10; verify the version for a different enterprise endpoint. [24]
Authentication choiceCompare a user-bound token with a GitHub App installation credential. Installation access is constrained by the app installation and granted permissions; prepare token expiry and renewal. [23]
GraphQLRequest the fields you need and paginate connections with first/after and pageInfo. Do not assume that one query exhausts every nested connection. [22]
Bulk administrationDesign an inventory, desired-state diff, dry run, owner approval, limited batch, per-item result, rollback data and post-change verification. Make retries safe for the chosen operation.

Included read-only exercise

examples/repository_inventory.py uses the Python standard library, supports a configurable API base/version, performs bounded retries, follows same-origin pagination and writes a JSON snapshot without overwriting an existing file. It never makes a mutating API request. Ten offline tests cover pagination, missing fields, malformed responses, rate limits and error paths.

The example is deliberately not a complete governance scanner. It does not enumerate all effective rules, inspect collaborators or certify compliance. HTTP redirects are rejected; unexpected endpoints require explicit review. A production integration would additionally need credential lifecycle management, stronger operational telemetry and target-specific authorization tests.

Interview coding drill

Extend the offline tests before adding a report field. Then describe, rather than immediately implement, a dry-run-only policy comparison. Explain how "unknown because inaccessible" differs from "disabled" or "noncompliant."

Docker, Terraform and Bicep

Prepare these as supporting skills, not as a replacement for the core topics.

Container fundamentals

Study image versus container, Dockerfile stages, build context, .dockerignore, dependency layers, non-root execution and image versioning. Multi-stage builds separate build tooling from the runtime output. Prefer reviewed base images, minimize unnecessary contents and define an update process even when pinning image digests. [25]

Infrastructure-as-code comparison

AreaTerraform preparationBicep preparation
Working modelConfiguration, providers, modules, plan, apply and state.Azure-focused declarative resource definitions and reusable modules. [28]

Practical exercise

Choose one tool. Write a small non-production resource definition and a review checklist. Walk through formatting/validation, an authenticated preview, approval, deployment verification and cleanup. Decide how concurrent changes are controlled. Keep production apply permissions and state access out of untrusted pull-request jobs.

Readiness target

Explain the full review-and-apply lifecycle and one failure mode. Deep provider internals or a large multi-module platform are unnecessary until the GitHub, Actions and identity topics are strong.

Troubleshooting scenarios

Practice hypotheses, evidence and a safe next action.

Use this answer structure: impact → evidence → hypothesis → smallest safe test → recovery → prevention. These are practice investigations, not a claim that one cause explains every occurrence.

Make the answer operational

Include what you would communicate to affected developers, what evidence you would retain and how you would know the issue is resolved. Avoid presenting a rerun as a root-cause analysis.

15

Eight hands-on preparation labs

Build small, keep evidence, and explain one controlled failure.

These exercises prioritize evidence over screenshots alone. The estimated lab time fits inside the study plan, but provisioning and access approval can add waiting time. Each lab has a defined success condition and a controlled failure to investigate.

Lab 1 / P02–3 hours

Govern a sandbox repository

Build: Create a test repository with a documented owner, a default branch, a review policy and meaningful test checks. Add CODEOWNERS using a real authorized test account/team. Configure available branch/ruleset controls.

Break / investigate: Attempt a normal reviewed merge and a change that should be blocked. Change an owned path and check who is asked to review.

Evidence: Keep the policy export or redacted screenshots, one allowed change and one blocked change. Explain which control produced each result.

Boundary: Access and plan limits apply. Never relax an existing production policy for this exercise.

Lab 2 / P02–3 hours

Build, fail and repair CI

Build: Copy the included project into a test repository. Place examples/ci.yml at .github/workflows/ci.yml. Run the two-version test matrix.

Break / investigate: Deliberately change a test expectation on a branch so CI fails. Find the first failing step, explain the failure and repair the change through review.

Evidence: Keep a passing run, a failing run and the fix. Explain permissions, triggers, matrix names, concurrency and timeout.

Boundary: The tests require only Python and use mocked HTTP responses; a live token is unnecessary.

Lab 3 / P02 hours

Create reusable automation

Build: Copy reusable-ci.yml and call-reusable.yml into .github/workflows/. Run the manual caller and change its typed Python-version input.

Break / investigate: Introduce an invalid input or incorrect workflow reference, then diagnose the failure. Sketch when you would use a composite action instead.

Evidence: Keep the caller/callee pair and an interface note explaining inputs, outputs, secrets, permissions and version updates.

Boundary: A same-repository call is simplest. Cross-repository sharing needs separately verified access and a reviewed revision.

Lab 4 / P03–4 hours

Prove Azure OIDC authentication

Build: Use an authorized test subscription. Create an application/service principal or user-assigned managed identity, a matching federation configuration and narrow approved access. Configure lab-azure and the three identifier secrets.

Break / investigate: Run the included smoke test from main. In a separate disposable trust configuration, test a deliberately mismatched subject, then restore it.

Evidence: Keep redacted trust settings, a successful login and an explained negative result. State clearly that you have not yet proven deployment rights.

Boundary: Do not print tokens. A personal sandbox may not support every environment gate. Remove the lab credential and role assignment when finished.

Lab 5 / P03–5 hours

Deploy and recover a small app

Build: Choose App Service, Functions or an existing AKS lab. Package a tiny application, deploy with the authorized identity and record a specific artifact/version.

Break / investigate: Create a controlled unhealthy release in the sandbox. Observe the health signal and follow a written recovery procedure.

Evidence: Keep the deploy run, smoke test, artifact-to-commit mapping and recovery evidence. Explain how runtime configuration affects the result.

Boundary: This is a build-your-own exercise; the bundled OIDC example is not a full deployment. Review service costs before provisioning.

Lab 6 / P02 hours

Operate security findings

Build: Enable the security capabilities available in your sandbox. Install the included Dependabot version-update configuration and review any resulting update change.

Break / investigate: Walk through a fictitious credential incident and a dependency alert. Use provider-approved inert test patterns only if demonstrating secret detection; never commit a real credential.

Evidence: Keep a triage record with owner, severity rationale, action, deadline, evidence and exception expiry when applicable.

Boundary: When a feature is unavailable, record the limitation and practice the procedure without claiming that enforcement was tested.

Lab 7 / P12–3 hours

Create a defensible API report

Build: Run all offline inventory tests, then perform an authorized read-only inventory of a test organization with a least-privilege credential.

Break / investigate: Test two-page responses, a 401, a rate-limit response and malformed JSON. Explain how a restricted credential changes the report scope.

Evidence: Keep the JSON snapshot, test output and a scope statement. Propose a dry-run policy-drift report without adding bulk write capability.

Boundary: Use a new output filename for each run. Do not place private organization exports or tokens in a public portfolio.

Lab 8 / P1 / P22–3 hours

Runner and IaC design review

Build: Design a separated CI/release runner setup and choose Terraform or Bicep for one small resource definition. Explain routing, trust, logging and update responsibilities.

Break / investigate: Walk through a queued-runner incident and a conflicting infrastructure change. Produce a preview/review/recovery sequence.

Evidence: Keep a one-page design and a non-production preview when available. Show the boundary between the runner identity, deploy identity and runtime identity.

Boundary: An existing local or authorized environment is sufficient. ARC and a new cloud cluster are optional extensions, not prerequisites.

17

Thirty interview questions with answer cues

Practice explanation and judgment, not memorized wording.

These are generic practice questions and suggested answer structures, not a prediction of an employer's question bank. Aim for a clear 60–90 second answer, then be ready for a design or troubleshooting follow-up.

01AdministrationHow would you organize access for multiple development teams?

Start from repository ownership and business need. Propose team-based access, limited base permissions, a small set of accountable administrators and a review/expiry process for temporary grants. Demonstrate effective access with a test identity. Discuss exceptions explicitly rather than assuming team membership alone proves the correct permission. [2]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

02AdministrationWhat is different about Enterprise Cloud and Enterprise Server?

Cloud is hosted by GitHub; Server is customer-operated. Explain which infrastructure responsibilities move with that choice. For a Server environment, ask about the installed version, upgrades, backup/recovery, capacity and supported integrations before recommending a Cloud-only feature. [1]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

03AdministrationWhat is the difference between SSO, SCIM and repository permissions?

Explain them as authentication, identity lifecycle/provisioning and authorization concerns respectively. Then identify the actual enterprise account model and identity provider. A successful login is not by itself proof that the person has the intended repository access. [3]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

04AdministrationHow would you remove access for a departing engineer?

Use the approved identity process, then verify repository/team/collaborator access and separately owned credentials or integrations. Review deploy keys and operational ownership. Preserve the change record and test the expected denial; do not equate deleting one membership with reviewing every access path. [2]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

05GovernanceRulesets or branch protection: how would you decide?

Compare available scope, rule layering, discoverability, enforcement modes and bypass needs. Inspect all applicable controls before migration. Propose a pilot and measure unintended blocking. Explain that multiple rulesets may apply and that branch protection can coexist with them. [4]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

06GovernanceWhy is a CODEOWNERS file not enough?

It identifies ownership/reviewers but must be combined with the required review control to gate merging. Check the base-branch file, pattern precedence, team visibility/access and protection of CODEOWNERS itself. Do not assume listing two owners requires two owner approvals. [35]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

07ActionsHow would you design CI and CD for a repository?

Use a validation path for changes and a deliberately trusted release path. Define tests, packaging, artifact identity, environment review, authentication, deployment checks and rollback. Explain the events, permissions and runner for each job instead of describing one large privileged script. [6] [7]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

08ActionsReusable workflow or composite action?

Choose a reusable workflow when the abstraction includes jobs, runners or a complete workflow interface. Choose a composite action when bundling steps inside an existing job. Explain inputs, outputs and versioning, then describe how permissions and secrets stay explicit. [8]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

09ActionsHow do you prevent duplicated or stale deployments?

Define concurrency groups and the business rule for superseding a release. Distinguish cancelling obsolete CI from interrupting production work. State whether every release must run or only the newest, and verify the platform semantics rather than promising an ordered durable deployment queue. [6]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

10ActionsWhat is the difference between a cache and an artifact?

A cache supports reuse to reduce work; an artifact preserves a produced output. A build should still be correct when the cache is absent. The deployable output needs a traceable identity and a retention/promotion policy appropriate to the release process. [31]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

11ActionsWhy might a required check never appear?

Look for a workflow that did not trigger, mismatched names, path/branch filters or a missing merge-queue event. Confirm whether the expected run exists before investigating the test command. Align the check policy with the events the workflow actually handles. [7]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

12RunnersWhen would you choose self-hosted runners?

Justify a specific requirement such as controlled tooling or network access. Then own the consequences: image updates, isolation, capacity, routing, logs and disposal. Compare hosted alternatives. Do not choose self-hosted simply because the organization already owns a VM. [9]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

13RunnersWhat would you check when a job stays queued?

Identify the wait reason, expected runner target, group access and available capacity. For a scale-set environment, inspect listener/controller and provisioning health. Separate an environment approval from a runner scheduling problem. Use a minimal diagnostic job where safe. [9] [10]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

14SecurityWhy pin an action to a full commit SHA?

It fixes the reviewed action revision rather than depending on a movable reference. Pinning is not a security review: maintainers, code, permissions and dependencies still matter. Include an update process, such as reviewed automated update pull requests. [11]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

15SecurityWhat is dangerous about privileged pull-request processing?

Untrusted code or input can run with privileges that ordinary validation should not have. Separate metadata operations from execution of contribution code, minimize permissions and keep release credentials out of untrusted jobs. Never solve a contribution build issue by casually exposing production secrets. [11]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

16SecurityA secret was deleted from a commit. Is the incident closed?

No. Confirm that the owning provider revoked or rotated the credential, investigate potential use and recover affected integrations. Cleanup does not invalidate a copied credential. Record exposure, containment, validation and a prevention action before closing the incident. [38]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

17SecurityDependabot alerts, security updates and version updates: what differs?

Alerts identify known dependency vulnerabilities. Security updates aim to fix vulnerable versions. Version updates keep supported dependencies current on the configured schedule. Explain separate enablement/configuration, review ownership and how you handle a change that breaks tests. [13] [37]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

18AzureExplain GitHub-to-Azure OIDC in under two minutes.

A permitted GitHub job obtains an identity token. Microsoft Entra validates the configured federated trust for the selected identity and enables Azure access-token acquisition. Azure authorization then governs resource operations. This avoids a stored long-lived client secret for the federation path; it does not eliminate trust configuration. [14] [16]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

19AzureDoes id-token: write grant Azure Contributor?

No. It allows the workflow job to request an OIDC token. The federated Azure identity and its resource authorization are configured separately. Explain which operations the deployment needs and how you would limit their scope. [15]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

20AzureOIDC works for one repository but not another. Why?

Compare the actual issuer, audience and subject configuration, including environment and immutable/custom subject formats. Check identity and tenant selection. Diagnose from the observed claims instead of assuming all repositories use the same name-only subject. [15]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

21AzureDeployment identity versus runtime managed identity?

The deployment identity performs pipeline operations. The running application may use a different identity to access its dependencies. Review their permissions independently; granting the pipeline access does not demonstrate that the application can access its data. [16]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

22AzureLogin succeeded but the deployment was denied. What next?

Confirm subscription and target, inspect the denied operation, and verify scope and service-specific authorization. Then check network/deployment prerequisites. Avoid replacing a narrow role with subscription-wide Owner just to make the error disappear.

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

23AzureHow would you deploy to AKS safely?

Connect tested source to a specific image, establish authorized cluster access, target the intended namespace and validate the rollout. Distinguish registry access from cluster authorization. Keep a known-good image/configuration pair and define health-based recovery criteria. [18]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

24AutomationREST or GraphQL for an inventory?

Choose based on the data shape, endpoint coverage, pagination and operational simplicity. REST is straightforward for resource collections; GraphQL can select related fields but each connection still needs proper pagination. A shorter request is not automatically a complete report. [21] [22]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

25AutomationHow would you avoid API throttling?

Use authenticated, appropriately scoped requests and avoid unnecessary polling. Honor server wait/reset guidance, reduce request pressure and bound retries. Differentiate an authorization failure from a rate-limit response. Record an incomplete run explicitly instead of silently dropping pages. [20]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

26AutomationWhy consider a GitHub App for organization automation?

Explain installation-scoped repository access and permissions, token expiry and independent integration ownership. Compare these with a user-bound credential and the endpoint requirements. Do not assume an installation token can access repositories outside its approved installation. [23]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

27AutomationHow would you safely update rules across many repositories?

Inventory first, compute a desired-state diff, provide a dry run, obtain approval and pilot the change. Apply bounded batches with per-item results and saved rollback data. Re-read the affected state and report errors or unknowns. Make retry behavior explicit for the chosen API operation.

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

28IaCDoes marking a Terraform value sensitive remove it from state?

Not by itself. Sensitive output handling is different from whether a value is persisted. Protect the backend, access policy and saved plans; verify the relevant provider/resource behavior before promising that a secret is absent from state. [27]

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

29OperationsHow would you reduce pipeline time without lowering quality?

Measure queue time and stage duration first. Select the largest evidenced bottleneck, propose one change and compare repeated runs. Preserve required validation and release safeguards. Report elapsed-time improvement separately from any increase in compute consumption.

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.

30ExperienceHow should you discuss work you have not done in production?

Separate direct production experience, lab evidence and conceptual understanding. Describe the exact exercise you completed and its limitations, then explain the additional approval, scale, monitoring and recovery work required for production. Do not invent metrics, ownership or incident history.

Follow-up: name one real or lab example, its failure mode, and how you verified the outcome.
