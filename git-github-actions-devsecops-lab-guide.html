Hands-on lab workbook

Git & GitHub Actions for a Cloud-Agnostic DevSecOps Platform

A self-paced practice guide that takes you from your first commit to a security-gated CI/CD pipeline on GitHub.com — with every lab followed by exercise questions and full answers. All labs run on a free GitHub account and a laptop; nothing is tied to any single cloud.

Git basics→ Branching→ GitHub collaboration→ Actions→ Secret scanning→ CI/CD capstone

How to use this guide

Each module has three parts: a short concept briefing, numbered labs you type out yourself, and exercise questions with answers hidden behind expandable panels — try to answer before you click. Work through the modules in order; every lab builds on the state left by the previous one.

What you need:

  • A free account on github.com
  • Git installed (git --version should print 2.40+)
  • A terminal (Git Bash on Windows, Terminal on macOS/Linux) and any code editor (VS Code recommended)
  • For Module 7 only: Docker Desktop or Podman (optional but recommended)
Why "cloud-agnostic"? Everything here uses open standards — Git, YAML workflows, containers, OIDC — so the same skills and pipelines work whether you later deploy to Azure, AWS, GCP, or your own Kubernetes cluster. Cloud-specific steps are deliberately kept out; deployment is treated as a pluggable last stage.

1Git fundamentals

Goal: understand what Git actually stores, configure it safely, and master the everyday cycle of stage → commit → inspect.

Concept briefing

Git is a distributed version control system. Every clone of a repository contains the entire history, not just the latest files. Git stores history as a chain of commits — immutable snapshots, each identified by a SHA-1/SHA-256 hash and pointing to its parent commit(s).

Files move through three areas:

AreaWhat it isCommand that moves files into it
Working directoryThe files you see and edit on diskyou edit / git checkout
Staging area (index)A draft of the next commitgit add
Repository (.git)Permanent, hashed historygit commit

The staging area is what makes Git precise: you choose exactly which changes go into each commit, so one commit tells one story.

Labs

LAB 1.1

Install and configure Git identity

≈ 10 minutes
# Verify the installation
git --version

# Identity — recorded inside every commit you make
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

# Sensible defaults
git config --global init.defaultBranch main
git config --global core.editor "code --wait"   # VS Code as editor

# Inspect everything you set
git config --global --list

Verify: git config user.email prints your address. Use the same email as your GitHub account so commits link to your profile.

LAB 1.2

Your first repository and commits

≈ 20 minutes
mkdir devsecops-lab && cd devsecops-lab
git init                          # creates the hidden .git folder
git status                        # "On branch main, nothing to commit"

echo "# DevSecOps Lab" > README.md
git status                        # README.md is "untracked"
git add README.md                 # stage it
git status                        # now "changes to be committed"
git commit -m "docs: add project readme"

# Make a second change and inspect before committing
echo "A practice platform repo." >> README.md
git diff                          # unstaged changes vs last commit
git add README.md
git diff --staged                 # what the NEXT commit will contain
git commit -m "docs: describe the repo"

git log --oneline --graph         # two commits, newest on top
git show HEAD                     # full detail of the latest commit

Verify: git log --oneline shows two commits with clear messages.

LAB 1.3

Ignore files that must never be committed

≈ 15 minutes

This is your first DevSecOps habit: build files, local settings, and above all credentials stay out of history.

# Simulate files that should never enter version control
echo "API_KEY=fake123" > .env
mkdir node_modules && echo "junk" > node_modules/pkg.js
echo "debug output" > app.log

git status          # all three show as untracked — dangerous

# Create the ignore file
cat > .gitignore << 'EOF'
# secrets & local config
.env
*.pem
*.key

# dependencies & build output
node_modules/
dist/

# logs
*.log
EOF

git status          # only .gitignore is listed now
git add .gitignore
git commit -m "chore: add gitignore for secrets, deps and logs"

git check-ignore -v .env    # proves which rule matched
Important: .gitignore only prevents untracked files from being added. If a secret was already committed, ignoring it later does not remove it from history — Module 6 covers what to do then.
LAB 1.4

Undo safely: restore, amend, revert

≈ 20 minutes
# 1) Discard an uncommitted edit
echo "bad line" >> README.md
git restore README.md             # file back to last commit

# 2) Unstage without losing the edit
echo "keep this" >> README.md
git add README.md
git restore --staged README.md    # out of the index, edit kept
git commit -am "docs: add note"   # -a stages tracked files

# 3) Fix the last commit message (history rewrite — local only!)
git commit --amend -m "docs: add practice note"

# 4) Undo a pushed/shared commit the safe way
git revert HEAD                   # NEW commit that cancels the last one
git log --oneline

Rule of thumb: amend/rebase only on commits nobody else has; revert for anything already shared.

Exercise questions & answers

Test yourself before opening the answers.
Q1. What is the difference between git add and git commit?

git add copies a snapshot of the file into the staging area — a draft of the next commit. git commit takes everything in the staging area and stores it permanently in the repository as a new commit object with a hash, author, timestamp, and parent pointer. Add selects what goes in; commit makes it history.

Q2. You edited a file after staging it. What does git status show, and why?

The file appears twice: under "changes to be committed" (the staged version) and "changes not staged" (the newer edit). Staging takes a snapshot at the moment of git add; later edits are not included until you add again. Committing now would record the staged version, not the latest one.

Q3. Which command shows what will be included in the next commit — git diff or git diff --staged?

git diff --staged (alias --cached) compares the staging area with the last commit — exactly what the next commit will contain. Plain git diff compares the working directory with the staging area, i.e. work you haven't staged yet.

Q4. You committed a file called .env yesterday and only added it to .gitignore today. Is the secret gone?

No. The file is still in every commit made before the ignore rule, and anyone with the repo can read it with git show. You must (1) rotate/revoke the credential immediately — treat it as leaked — (2) remove the file with git rm --cached .env and commit, and (3) if the repo is shared, scrub history with a tool like git filter-repo. Rotation is the step that actually restores safety.

Q5. When is git revert preferred over git reset?

Whenever the commit has been pushed or shared. Revert adds a new commit that undoes the change, so history stays intact and teammates' clones stay consistent. Reset moves the branch pointer backwards and rewrites history — fine for private local commits, disruptive for shared ones.

Q6. Why does Git identify commits by hash instead of version numbers like v1, v2?

The hash is computed from the commit's full content (tree, parents, author, message). This makes every commit content-addressed and tamper-evident: change one byte anywhere in history and every downstream hash changes. In a distributed system with no central counter, hashes also guarantee globally unique IDs without coordination — a foundation of supply-chain integrity in DevSecOps.

2Branching & merging

Goal: work on isolated lines of development, merge them back, resolve conflicts calmly, and know when to rebase or stash.

Concept briefing

A branch is just a movable pointer to a commit — creating one is instant and free. HEAD is the pointer to the branch you are currently on. Two ways histories combine:

  • Fast-forward merge — the target branch simply moves its pointer forward because no divergent work exists. History stays a straight line.
  • Merge commit — both branches have new commits, so Git creates a commit with two parents that ties them together.

A conflict occurs only when both branches changed the same lines of the same file — Git refuses to guess and asks you to decide.

Labs

LAB 2.1

Create, switch and list branches

≈ 15 minutes
git branch                        # * main
git switch -c feature/login       # create + switch in one step

echo "def login(): pass" > auth.py
git add auth.py
git commit -m "feat: login skeleton"

git switch main
ls                                # auth.py is gone — it lives on the branch
git switch feature/login
ls                                # auth.py is back

git log --oneline --graph --all   # see both pointers
LAB 2.2

Fast-forward vs merge commit

≈ 15 minutes
# Fast-forward: main has no new work
git switch main
git merge feature/login           # "Fast-forward" in the output
git branch -d feature/login       # clean up merged branch

# Now force a real merge commit
git switch -c feature/logout
echo "def logout(): pass" >> auth.py
git commit -am "feat: logout"

git switch main
echo "Platform repo." >> README.md
git commit -am "docs: tagline"    # main moved too — divergence!

git merge feature/logout          # editor opens for merge commit msg
git log --oneline --graph         # diamond shape with two parents
LAB 2.3

Create and resolve a conflict

≈ 25 minutes
git switch -c feature/title
sed -i '1s/.*/# DevSecOps Platform/' README.md
git commit -am "docs: rename title"

git switch main
sed -i '1s/.*/# Cloud Platform Lab/' README.md
git commit -am "docs: alt title"

git merge feature/title           # CONFLICT (content): README.md
git status                        # "both modified: README.md"
cat README.md                     # conflict markers appear:
<<<<<<< HEAD
# Cloud Platform Lab
=======
# DevSecOps Platform
>>>>>>> feature/title
# Edit the file: keep one line (or write a merged version),
# DELETE all three marker lines, then:
git add README.md
git commit                        # completes the merge

# If you ever panic mid-merge:
#   git merge --abort   returns to the pre-merge state
LAB 2.4

Rebase for a linear history + stash for interruptions

≈ 20 minutes
# Rebase: replay your branch commits on top of latest main
git switch -c feature/config
echo "timeout: 30" > config.yaml
git add . && git commit -m "feat: config file"

git switch main
echo "MIT" > LICENSE
git add . && git commit -m "chore: license"

git switch feature/config
git rebase main                   # branch now starts after LICENSE commit
git log --oneline --graph --all   # straight line, no diamond
git switch main && git merge feature/config   # fast-forward

# Stash: shelve half-done work to switch context
echo "wip" >> config.yaml
git stash push -m "half-done timeout tuning"
git status                        # clean — free to switch branches
git stash list
git stash pop                     # bring the work back
Golden rule of rebase: never rebase commits that others may already have pulled — it rewrites hashes and forks everyone's history. Rebase your own unpushed branches only.

Exercise questions & answers

Q1. What actually happens on disk when you create a branch?

Almost nothing — Git writes a 41-byte file under .git/refs/heads/ containing the hash of the current commit. No files are copied. That is why branching is instant and why Git workflows encourage a branch per task.

Q2. How can you predict whether a merge will be fast-forward?

If the target branch (e.g. main) has no commits of its own since the feature branch split off — i.e. it is an ancestor of the feature branch — Git can just slide the pointer forward. Check with git log main..feature (commits ahead) and git log feature..main (if this is empty, the merge fast-forwards).

Q3. Both branches edited the same file. Will the merge always conflict?

No. Git merges at the line level: if branch A changed lines 1–3 and branch B changed lines 40–42 of the same file, Git combines them silently. A conflict only occurs when the same or adjacent lines differ on both sides, or when one side deleted a file the other modified.

Q4. In conflict markers, which code is between <<<<<<< HEAD and =======?

The version from your current branch (the one you were on when you ran git merge). The section between ======= and >>>>>>> branch-name is the incoming branch's version. Resolution means editing the file to the final desired content and removing all marker lines.

Q5. Merge vs rebase — what is the real trade-off?

Merge preserves true history (you can see the branch existed and when it joined) at the cost of a busier graph. Rebase produces a clean, linear, easy-to-bisect history at the cost of rewriting commits — new hashes, falsified chronology, and danger if the commits were shared. A common team convention: rebase your private feature branch onto main to stay current, then merge (or squash-merge) via a pull request.

Q6. You are mid-way through a change when an urgent bug arrives on another branch. Walk through the commands.

git stash push -m "wip: my change" → working tree is clean → git switch hotfix-branch, fix, commit → git switch back → git stash pop to restore the shelved work. If the pop conflicts, resolve like a normal merge conflict; the stash entry stays until dropped.

3GitHub collaboration

Goal: connect your local repo to github.com, authenticate securely, and adopt the pull-request workflow with branch protection — the governance backbone of any platform.

Concept briefing

GitHub hosts a remote copy of your repository (conventionally named origin) and adds collaboration on top: pull requests, reviews, protected branches, issues, and Actions. Authentication for Git operations is via SSH keys or HTTPS with a fine-grained personal access token (PAT) — account passwords are not accepted for Git.

The pull request (PR) is the unit of change on a governed platform: propose a branch, let CI and reviewers check it, then merge. Branch protection / rulesets turn that etiquette into enforcement.

Labs

LAB 3.1

SSH authentication and first push

≈ 25 minutes
# 1) Generate a modern key pair (accept the default path)
ssh-keygen -t ed25519 -C "you@example.com"

# 2) Copy the PUBLIC key and add it on github.com:
#    Settings → SSH and GPG keys → New SSH key
cat ~/.ssh/id_ed25519.pub

# 3) Test the connection
ssh -T git@github.com            # "Hi ! You've successfully authenticated"

# 4) Create an empty repo named devsecops-lab on github.com (no README),
#    then connect and push:
git remote add origin git@github.com:YOUR-USER/devsecops-lab.git
git remote -v
git push -u origin main          # -u links local main to origin/main

Verify: refresh the repo page — your files and full commit history are visible.

The private key (id_ed25519, no extension) never leaves your machine and is never pasted anywhere. Only the .pub file goes to GitHub.
LAB 3.2

The pull request cycle

≈ 25 minutes
git switch -c feature/contributing
cat > CONTRIBUTING.md << 'EOF'
# Contributing
1. Branch from main: feature/
2. Open a pull request — never push to main directly.
3. CI must pass and one review is required.
EOF
git add . && git commit -m "docs: contribution rules"
git push -u origin feature/contributing

On github.com: the yellow banner offers "Compare & pull request" — click it, write a description of what and why, and create the PR. Explore the Files changed tab, leave a comment on a line, then Merge pull request → Confirm. Finally sync locally:

git switch main
git pull origin main             # fetch + merge the PR result
git branch -d feature/contributing
git fetch --prune                # drop stale remote-tracking refs
LAB 3.3

Branch protection ruleset + CODEOWNERS

≈ 20 minutes

On github.com: Settings → Rules → Rulesets → New ruleset → New branch ruleset.

  • Name: protect-main, Enforcement: Active
  • Target branches: add Include default branch
  • Tick: Require a pull request before merging (1 approval), Block force pushes, Restrict deletions
  • (After Module 4) add Require status checks to pass and select your CI job
# Prove the rule works — this must now be REJECTED:
echo "sneaky" >> README.md
git commit -am "direct push attempt"
git push                          # remote: Changes must be made through a pull request
git reset --hard origin/main      # discard the local attempt

Now add a CODEOWNERS file so sensitive paths always get the right reviewer:

mkdir -p .github
cat > .github/CODEOWNERS << 'EOF'
# Order matters; last match wins
*                   @YOUR-USER
/.github/workflows/ @YOUR-USER
EOF
# commit via a branch + PR, as the ruleset now demands

Exercise questions & answers

Q1. What is the difference between git fetch and git pull?

fetch downloads new commits from the remote and updates remote-tracking refs (origin/main) without touching your working branch — safe to run any time. pull = fetch plus merge (or rebase, with --rebase) into your current branch. Fetch to inspect first; pull when you're ready to integrate.

Q2. Why do platform teams prefer SSH keys or fine-grained PATs over classic tokens?

Least privilege and blast-radius control. A fine-grained PAT is scoped to specific repositories and specific permissions with a mandatory expiry, so a leaked token exposes little. SSH keys never transmit a reusable secret over the wire (public-key challenge instead). Classic PATs grant broad account-wide scopes and historically never expired — a single leak could compromise everything the account touches.

Q3. What exactly does git push -u origin main do beyond a plain push?

The -u / --set-upstream flag records origin/main as the upstream of your local main. Afterwards plain git push, git pull, and git status (ahead/behind counts) all know which remote branch to compare against without you spelling it out.

Q4. Your PR shows "This branch is out-of-date with the base branch." What are your two options and which keeps history cleaner?

Either merge main into your branch (git merge origin/main — adds a merge commit) or rebase your branch onto main (git rebase origin/main then git push --force-with-lease). Rebase keeps the PR linear and reviewable; it is acceptable to force-push here because a PR branch is understood to be yours. --force-with-lease refuses to overwrite work someone else pushed meanwhile — never use bare --force.

Q5. What does CODEOWNERS actually enforce, and when does it bite?

CODEOWNERS maps file paths to required reviewers. On its own it only auto-requests reviews; combined with the ruleset option "Require review from Code Owners" it becomes blocking — a PR touching /.github/workflows/ cannot merge until the owner of that path approves. This is how platform teams keep control of CI/CD definitions while letting product teams move freely elsewhere.

Q6. Why should even solo developers and admins keep "require PR before merging" on?

Because the PR is where all automation hangs: CI checks, secret scanning push protection feedback, CodeQL results, and an audit trail of what changed and why. Bypassing it means changes reach main unscanned and unrecorded. It also builds the habit that transfers directly to enterprise governance, where direct pushes to default branches are universally blocked.

4GitHub Actions basics

Goal: read and write workflow YAML fluently — events, jobs, steps, runners, marketplace actions, variables and secrets.

Concept briefing

GitHub Actions runs automation defined in YAML files inside .github/workflows/. The vocabulary:

TermMeaning
WorkflowOne YAML file; triggered by events
EventWhat starts it: push, pull_request, schedule, workflow_dispatch…
JobA set of steps on one runner; jobs run in parallel by default
StepA shell command (run:) or a reusable action (uses:)
RunnerThe VM executing a job — GitHub-hosted (ubuntu-latest) or self-hosted
ActionPackaged step from the Marketplace, e.g. actions/checkout

Dynamic values come from contexts like ${{ github.ref }}, ${{ secrets.MY_KEY }}, ${{ vars.MY_VAR }}.

Labs

LAB 4.1

Hello, workflow

≈ 15 minutes
mkdir -p .github/workflows
cat > .github/workflows/hello.yml << 'EOF'
name: Hello

on: push

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - name: Say hello
        run: echo "Hello from GitHub Actions!"

      - name: Show event details
        run: |
          echo "Event:  ${{ github.event_name }}"
          echo "Branch: ${{ github.ref_name }}"
          echo "Commit: ${{ github.sha }}"
          echo "Actor:  ${{ github.actor }}"
EOF
# commit via branch + PR (your ruleset requires it), then check
# the Actions tab: expand each step and read the logs
LAB 4.2

Triggers: filtered push, PR, schedule, manual with inputs

≈ 25 minutes
cat > .github/workflows/triggers.yml << 'EOF'
name: Trigger tour

on:
  push:
    branches: [main]
    paths: ['src/**']          # only when src files change
  pull_request:
    branches: [main]
  schedule:
    - cron: '30 2 * * 1'       # Mondays 02:30 UTC
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        type: choice
        options: [dev, staging]
        default: dev

jobs:
  show:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Triggered by ${{ github.event_name }}"
          echo "Chosen env: ${{ inputs.environment || 'n/a' }}"
EOF

Exercise: after merging, run it manually — Actions tab → Trigger tour → Run workflow → pick staging. Then push a change that only touches README.md to main and confirm the workflow does not run (path filter).

LAB 4.3

A real CI job with marketplace actions

≈ 30 minutes

Add a tiny Python app so CI has something to test:

mkdir -p src tests
cat > src/calc.py << 'EOF'
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("division by zero")
    return a / b
EOF
cat > tests/test_calc.py << 'EOF'
import sys, pathlib
sys.path.insert(0, str(pathlib.Path(__file__).parent.parent / "src"))
from calc import add, divide
import pytest

def test_add():
    assert add(2, 3) == 5

def test_divide_by_zero():
    with pytest.raises(ValueError):
        divide(1, 0)
EOF
cat > .github/workflows/ci.yml << 'EOF'
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read              # least privilege for GITHUB_TOKEN

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install test deps
        run: pip install pytest

      - name: Run tests
        run: pytest -v
EOF

Then: open a PR — the test check appears on it. Go back to your ruleset (Lab 3.3) and add Require status checks → test. Break a test on a new branch and watch the merge button lock.

LAB 4.4

Variables, secrets and contexts

≈ 20 minutes

On github.com: Settings → Secrets and variables → Actions. Create a variable APP_NAME=lab-platform and a secret DEMO_TOKEN=some-fake-value-123.

cat > .github/workflows/config-demo.yml << 'EOF'
name: Config demo
on: workflow_dispatch

jobs:
  demo:
    runs-on: ubuntu-latest
    env:
      APP: ${{ vars.APP_NAME }}
    steps:
      - name: Plain variable
        run: echo "Building $APP"

      - name: Secret is masked in logs
        run: |
          echo "Token length: ${#TOKEN}"
          echo "Token itself: $TOKEN"     # printed as ***
        env:
          TOKEN: ${{ secrets.DEMO_TOKEN }}
EOF

Observe: in the log, the secret's value is replaced by ***. Masking is a safety net, not a guarantee — never intentionally echo secrets, and never write them to files or artifacts.

Exercise questions & answers

Q1. Why is actions/checkout the first step of almost every job?

A runner starts as a blank VM — your repository is not on it. checkout clones the exact commit that triggered the workflow into the workspace. Any job that only calls APIs or prints metadata can skip it; anything that builds, tests, or scans code needs it first.

Q2. Two jobs are defined in one workflow. Do they share files? Do they run in order?

Neither, by default. Each job gets its own fresh runner, so files do not carry over — you pass files between jobs with artifacts (Lab 5.2) and ordering with needs: (Lab 5.3). Steps within one job do share the filesystem and run sequentially.

Q3. What is the difference between secrets, vars, and env:?

secrets.* are encrypted at rest, masked in logs, hidden from forked-PR workflows by default, and unreadable after saving. vars.* are plain configuration values, visible to anyone with repo access — use for non-sensitive settings like app names or regions. env: simply maps either of them (or literals) into environment variables at workflow, job, or step scope. Rule: if leaking it would matter, it is a secret.

Q4. Why write permissions: contents: read at the top of a workflow?

Every run receives an automatic GITHUB_TOKEN. Explicitly declaring permissions drops it to least privilege — here, read-only repo access. If a malicious dependency or compromised action runs inside the job, it cannot push code, open releases, or tamper with issues. Add specific permissions (e.g. packages: write) only to jobs that need them.

Q5. Your schedule: workflow didn't run at exactly 02:30. Why, and what timezone is cron in?

Cron in Actions is always UTC, and scheduled runs are queued on shared infrastructure, so delays of several minutes (occasionally more, at busy times like the top of the hour) are normal. Scheduled workflows also run only on the default branch, and GitHub disables them after 60 days of repository inactivity. Don't build hard real-time assumptions on cron triggers.

Q6. A workflow on pull_request from a fork needs a secret and doesn't get it. Is that a bug?

No — it is deliberate. Fork PRs execute code written by outsiders, so GitHub withholds secrets and gives a read-only token to prevent exfiltration. If maintainers must run secret-dependent checks on fork PRs, they use pull_request_target with extreme care (it runs with secrets but must never execute the fork's code) or require a label/approval gate. For your own platform repos, prefer same-repo branches over forks.

5Intermediate Actions

Goal: build multi-job pipelines: matrices, caching, artifacts, dependencies, conditionals, reusable workflows and protected environments.

Concept briefing

Real pipelines are graphs, not single jobs. The tools: strategy.matrix fans one job definition out across versions/OSes; actions/cache reuses dependency downloads between runs; upload/download-artifact hands files from one job to the next; needs: defines the execution order; if: makes steps or jobs conditional; reusable workflows (workflow_call) let a platform team publish one blessed pipeline that many repos call; environments attach approvals and scoped secrets to deployment stages.

Labs

LAB 5.1

Matrix builds

≈ 20 minutes
cat > .github/workflows/matrix.yml << 'EOF'
name: Matrix CI
on: pull_request

permissions:
  contents: read

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false            # let all combos finish even if one fails
      matrix:
        os: [ubuntu-latest, windows-latest]
        python: ['3.11', '3.12']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - run: pip install pytest
      - run: pytest -v
EOF

Observe: one job definition becomes 4 parallel jobs (2 OS × 2 Python). Exercise: add exclude: to skip windows + 3.11 and confirm only 3 jobs run.

LAB 5.2

Caching and artifacts

≈ 25 minutes
echo "pytest==8.2.0" > requirements.txt

cat > .github/workflows/cache-artifact.yml << 'EOF'
name: Cache and artifact
on: workflow_dispatch

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'                    # built-in pip cache

      - run: pip install -r requirements.txt

      - name: Produce a build report
        run: |
          mkdir -p out
          pytest --junitxml=out/results.xml || true
          echo "built at $(date -u)" > out/build-info.txt

      - name: Upload results
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: out/
          retention-days: 7

  summarize:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: test-report
      - run: cat build-info.txt
EOF

Observe: run it twice — the second run's setup step logs a cache hit and installs faster. The artifact is downloadable from the run's Summary page, and the summarize job proves files crossed the job boundary.

Job graphs and conditionals

≈ 20 minutes
cat > .github/workflows/pipeline-shape.yml << 'EOF'
name: Pipeline shape
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "linting..."

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "testing..."

  build:
    needs: [lint, test]           # waits for BOTH
    runs-on: ubuntu-latest
    steps:
      - run: echo "building..."

  deploy-dev:
    needs: build
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploying to dev (main only)"

  notify:
    needs: [build]
    if: failure()                 # runs only when something upstream failed
    runs-on: ubuntu-latest
    steps:
      - run: echo "pipeline failed — alert the team"
EOF

Observe: the run page draws the dependency graph. On a PR, deploy-dev shows as skipped; on a push to main it runs.

Exercise questions & answers

Q1. A 3×3 matrix with fail-fast: true (the default) has one failing combo. What happens?

As soon as one matrix job fails, GitHub cancels all still-running siblings. That saves minutes but hides whether other combos would also fail. Use fail-fast: false when you want the full compatibility picture (e.g. nightly test grids), and the default for fast PR feedback.

Q2. Cache vs artifact — pick the right one: (a) node_modules downloads, (b) a compiled binary needed by the deploy job, (c) test HTML report for humans.

(a) Cache — speeds up future runs, restored by key, may be evicted anytime (7-day unused eviction, repo size limits), never trusted as the source of truth. (b) Artifact — guaranteed hand-off within the same run across jobs. (c) Artifact — downloadable from the run summary with a retention period. Rule: cache is an optimization, artifacts are outputs.

Q3. What is the difference between if: failure() and if: always() on a job?

Default job condition is success() — run only if all needs succeeded. failure() runs the job only when something upstream failed (alerting). always() runs regardless of upstream outcome, including cancellation (cleanup, publishing partial reports). Beware: a job without needs ignores other jobs' failures entirely — conditions only see what it depends on.

Q4. How is a reusable workflow different from a composite action?

A composite action bundles steps and is used inside an existing job (uses: org/repo/action@v1 as a step) — it shares the caller's runner. A reusable workflow is called at the job level (jobs.x.uses), brings its own jobs, runners, matrices, and environments, and can require secrets explicitly. Composite = shared step logic; reusable workflow = shared pipeline shape. Platform teams typically publish both: composite actions for "how to scan", reusable workflows for "the whole golden pipeline".

Q5. Why put deployment secrets in an environment instead of repository secrets?

Environment secrets are released only to jobs targeting that environment after its protection rules pass — required reviewers, wait timers, and branch restrictions. A compromised PR workflow can read repository secrets it references, but it cannot reach production environment secrets without passing the human gate. It also gives per-stage separation: dev, staging, prod each hold their own credentials.

Q6. Your team wants every repo's CI updated when the security team adds a new scanner. Which feature solves this and how is it versioned?

A central reusable workflow in a platform repo, referenced by tag (@v1) or branch. Teams pin to a major tag; the platform team moves the tag (or teams use Dependabot to bump pinned SHAs) when the golden pipeline changes. Combined with CODEOWNERS on .github/workflows/ and rulesets requiring the check, no repo can silently opt out.

6Secret scanning & pipeline security

Goal: stop credentials from entering the repo, catch vulnerable dependencies and code, and harden the workflows themselves — the "Sec" in DevSecOps.

Concept briefing

Shift-left means catching security problems at commit/PR time, when fixes cost minutes, instead of in production, when they cost incidents. Your layered defenses on GitHub:

  • Pre-commit scanning (gitleaks) — on the developer's machine, before Git even records the secret
  • Push protection — GitHub rejects pushes containing recognizable credential patterns
  • Secret scanning alerts — continuous scanning of existing history
  • Dependabot — alerts and automatic PRs for vulnerable dependencies
  • Code scanning (CodeQL) — static analysis of your own code for injection, path traversal, etc.
  • Workflow hardening — least-privilege tokens, SHA-pinned actions, protected environments
On public repositories all of the above are free. On private repos, secret scanning/push protection and CodeQL require GitHub Advanced Security (now sold as separate Secret Protection and Code Security add-ons). Do these labs on a public practice repo, and only ever use fake or immediately-revoked credentials.

LAB 6.1

Enable secret scanning + push protection, then trigger it

≈ 25 minutes

On github.com: Settings → Advanced Security (or "Code security and analysis") → enable Secret scanning and Push protection.

# Create a fake-but-realistic credential. GitHub recognizes provider
# patterns; an easy one to trigger is a GitHub PAT prefix.
git switch -c test/push-protection
echo 'token = "ghp_0123456789abcdefghijklmnopqrstuvwxyz"' > leak.py
git add leak.py
git commit -m "test: simulate credential leak"
git push -u origin test/push-protection

Expected result: the push is rejected with a message identifying the secret type, file, and line, plus a bypass URL. Read the message carefully — this is what your teammates will see.

# Clean up properly: remove the secret from the commit itself
git reset --soft HEAD~1      # undo commit, keep file staged
git restore --staged leak.py
rm leak.py
git switch main && git branch -D test/push-protection
If a real secret ever gets past protection: 1) revoke/rotate it at the provider immediately — scrubbing Git history does not un-leak it; 2) remove it from history (git filter-repo) and force-push per your org's process; 3) close the secret-scanning alert with the resolution reason; 4) check audit logs for use of the credential.
LAB 6.2

Pre-commit defense with gitleaks

≈ 25 minutes

Catch secrets before they are ever committed — the cheapest possible fix.

# Install gitleaks (pick one)
brew install gitleaks                    # macOS

# One-off scan of the whole repo history

LAB 6.5

Harden the workflows themselves

≈ 25 minutes

Your CI is production infrastructure; attackers target it. Apply four controls:

1 — Pin third-party actions to a full commit SHA. Tags like @v2 are movable; a compromised action repo can re-point them at malicious code (this is exactly what happened in the 2025 tj-actions/changed-files supply-chain attack).

# find the SHA of the release you audited, then:
- uses: gitleaks/gitleaks-action@ff98106e4c7b2bc287b24eaf42907196329070c7  # v2.3.9

2 — Default the token to read-only for the whole repo. Settings → Actions → General → Workflow permissions → Read repository contents. Grant write scopes per-job in YAML only where needed.

3 — Control what can run. Same settings page: restrict actions to "Allow YOUR-ORG actions and select non-org actions" and list the vetted ones.

4 — Prefer OIDC over long-lived cloud keys. Instead of storing AWS_SECRET_ACCESS_KEY / AZURE_CLIENT_SECRET in secrets, the workflow requests a short-lived identity token that any cloud can trust:

permissions:
  id-token: write        # allow the job to request an OIDC token
  contents: read

# then the cloud-specific login action exchanges it, e.g.
#  aws-actions/configure-aws-credentials  (role-to-assume: ...)
#  azure/login                            (federated credential)
#  google-github-actions/auth             (workload identity)

The pattern is identical across clouds — trust is established between the cloud's IAM and GitHub's OIDC issuer, scoped to your repo/branch/environment. No stored cloud secret exists to leak. This is the cornerstone of cloud-agnostic pipeline auth.

Exercise questions & answers

Q1. Push protection blocked a teammate who insists the string is "just a test value." What do you tell them?

Use a value that doesn't match real credential formats (e.g. FAKE_TOKEN_FOR_TESTS), or a provider's documented dummy values, or load test secrets from environment variables/fixtures excluded by .gitignore. Bypass exists (with an audited reason) but should be rare and reviewed — every bypass is logged, and normalizing bypasses trains people to click through the one warning that matters. If it genuinely is a real secret, blocking it just saved a rotation incident.

Q2. Why is "rotate the credential" step one after a leak, before any history cleanup?

Because Git history cleanup does not undo exposure: forks, clones, CI caches, GitHub's own event archives, and scrapers may already hold the value — automated bots harvest pushed secrets within minutes. Rotation makes the leaked value worthless regardless of where copies live. History scrubbing is hygiene; rotation is the actual remediation.

Q3. What is the difference between what secret scanning, Dependabot, and CodeQL each protect against?

Secret scanning → credentials in your repo content (keys, tokens, connection strings). Dependabot → known vulnerabilities (CVEs) in third-party dependencies you import, including your GitHub Actions. CodeQL → vulnerability patterns in code you wrote (SQL/command injection, path traversal, unsafe deserialization). Together they cover secrets, supply chain, and first-party code — three different attack surfaces, so you need all three.

Q4. Why is pinning an action to @v4 weaker than pinning to a commit SHA?

A tag is a mutable pointer controlled by the action's maintainers — or by whoever compromises their repo. Re-pointing v4 at malicious code instantly executes it inside every consumer's runner, with access to that job's token and secrets. A 40-character commit SHA is content-addressed and immutable: what you audited is what runs. Pair SHA-pinning with Dependabot's github-actions ecosystem so pins are still bumped (reviewed) when new releases ship.

Q5. Explain OIDC-based cloud auth to a colleague in three sentences, and why it beats stored keys.

The workflow asks GitHub for a short-lived, signed identity token that states "this run is repo X, branch Y, environment Z." The cloud's IAM has been configured to trust GitHub's token issuer for exactly that claim set, and swaps the token for temporary cloud credentials that expire within the hour. Nothing long-lived is stored in GitHub, so there is no static key to leak, rotate, or find in a dump — and access can be scoped as tightly as "only main-branch runs in the prod environment."

Q6. Where does a pre-commit gitleaks hook fit relative to push protection — isn't it redundant?

They are layers, not duplicates. The pre-commit hook fires before a commit exists, so the secret never enters history at all — nothing to scrub. Push protection is the server-side backstop for machines without hooks installed (hooks are opt-in and local). The CI gitleaks job is the third layer, scanning full history with custom rules. Defense in depth assumes any single layer will occasionally be skipped or fail.

7Cloud-agnostic CI/CD capstone

Goal: assemble everything into one security-gated pipeline: lint → test → secret scan → container build → vulnerability scan → publish → approval-gated deploy. Containers are the cloud-agnostic delivery unit — the same image runs on AKS, EKS, GKE, or a bare VM.

LAB 7.1

Containerize the app and publish to GitHub Container Registry (GHCR)

≈ 35 minutes

Give the app a tiny HTTP face and a Dockerfile:

cat > src/app.py << 'EOF'
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"devsecops-lab: ok\n")

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8080), H).serve_forever()
EOF

cat > Dockerfile << 'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY src/ ./src/
RUN useradd -m appuser
USER appuser                 
EXPOSE 8080
CMD ["python", "src/app.py"]
EOF

# Test locally if Docker is installed:
docker build -t devsecops-lab .
docker run --rm -p 8080:8080 devsecops-lab
curl localhost:8080           # devsecops-lab: ok

Now build and push from Actions using only the automatic token — no registry password anywhere:

cat > .github/workflows/publish.yml << 'EOF'
name: Publish image
on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write             # lets GITHUB_TOKEN push to GHCR

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:${{ github.sha }}
EOF

Verify: after the run, the image appears under your profile → Packages. Tagging with the commit SHA gives you traceability from any running container back to the exact code.

LAB 7.2

The full security-gated pipeline

≈ 45 minutes
cat > .github/workflows/platform-pipeline.yml << 'EOF'
name: Platform pipeline
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install ruff && ruff check src/

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12', cache: 'pip' }
      - run: pip install pytest && pytest -v

  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  build-image:
    needs: [lint, test, secret-scan]      # security is a gate, not a report
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build (no push yet)
        uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          load: true
          tags: candidate:${{ github.sha }}

      - name: Scan image for vulnerabilities (Trivy)
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: candidate:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: '1'                  # fail the pipeline on findings

  publish:
    needs: build-image
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

  deploy-staging:
    needs: publish
    runs-on: ubuntu-latest
    environment: staging                  # human approval gate from Lab 5.5
    steps:
      - name: Deploy placeholder
        run: |
          echo "Would deploy ghcr.io/${{ github.repository }}:${{ github.sha }}"
          echo "Swap this step for kubectl/helm/az/aws/gcloud — the pipeline"
          echo "shape stays identical on every cloud."
EOF

Exercises on the finished pipeline:

  1. Open a PR — confirm lint, test, secret-scan and build-image run, but publish/deploy stay skipped.
  2. Add these jobs as required status checks in your ruleset, so an insecure image can never merge.
  3. Break it on purpose three ways and watch the right gate catch each: a failing test, a fake ghp_… token in a file, and (if Trivy findings allow) an old base image like python:3.8-slim.
  4. Merge to main, approve the staging gate, and read the full run graph — this is a complete DevSecOps pipeline.

Capstone checklist — you have built a platform when…

  • main is protected by a ruleset: PR required, status checks required, force-push blocked
  • CODEOWNERS routes workflow changes to the platform owner
  • CI runs lint + tests on every PR, with matrix coverage where it matters
  • Secrets are blocked at three layers: pre-commit gitleaks, push protection, CI scan
  • Dependabot patches dependencies and action pins weekly
  • CodeQL scans first-party code on PR and on schedule
  • GITHUB_TOKEN is read-only by default; write scopes are granted per job
  • Third-party actions are SHA-pinned
  • Images are built once, scanned by Trivy, tagged by commit SHA, published to GHCR
  • Deployment waits behind an environment approval, and cloud auth is designed for OIDC — no long-lived keys

Capstone questions & answers

Q1. Why does build-image build with push: false while publish builds again with push: true?

The first build exists to be scanned — nothing untrusted should reach the registry. Only after Trivy passes, and only on main, does publish run. (In production pipelines you'd avoid the double build by pushing a digest-addressed candidate to a staging registry or reusing the build cache; the two-job shape here keeps the trust boundary obvious while you learn.)

Q2. What makes this pipeline "cloud-agnostic" concretely?

Every stage uses portable standards: Git for source, YAML workflows, OCI container images as the deploy artifact, GHCR as a standard registry (swappable for ACR/ECR/Artifact Registry by changing one login step), Trivy scanning any OCI image, and OIDC federation supported by all major clouds. The only cloud-specific element is the final deploy step, deliberately isolated in one job — swap kubectl/helm/az/aws there and nothing upstream changes.

Q3. Why tag images with the commit SHA rather than only latest?

latest is mutable — you can never prove which code a running container came from, and rollback means guessing. A SHA tag gives an immutable, auditable link: container → image → commit → PR → review → pipeline run. That chain is the basis of provenance and incident forensics; "latest" is acceptable only as a convenience alias on top.

Q4. Trivy fails your build for a CRITICAL CVE in the base image with no fix released. What are your options?

In rough order: switch to a slimmer/newer base (fewer packages = fewer CVEs — distroless or alpine variants); check whether the vulnerable package is even used and remove it in the Dockerfile; if truly unfixable and unexploitable in your context, add a documented, expiring ignore entry (.trivyignore with a ticket reference) rather than lowering the global severity gate. Never solve it by deleting the scan step — the gate's value is that ignoring it must be a visible, reviewed decision.

Q5. Where would you plug real deployment in, and what changes for Azure vs AWS?

Only the deploy-staging job changes. For Azure: azure/login with an OIDC federated credential, then az aks get-credentials + kubectl apply/helm upgrade. For AWS: aws-actions/configure-aws-credentials with a role ARN, then aws eks update-kubeconfig + the same kubectl/helm commands. The permissions block gains id-token: write, the image reference stays the same GHCR SHA tag, and every gate before deployment is untouched — which is exactly the point.
