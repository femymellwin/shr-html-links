What “five years of experience” should sound like

At this level, the interviewer normally expects more than definitions. Every answer should show:

  1. A real context — application type, team size, environments, traffic or scale, release frequency, and your responsibility.
  2. A design choice — why a tool or pattern was selected and what alternative was rejected.
  3. Implementation detail — repository layout, YAML/HCL structure, commands, controls, and failure handling.
  4. Operations thinking — monitoring, security, rollback, auditability, cost, and ownership.
  5. A measurable result — deployment time, failure rate, recovery time, manual effort, availability, or lead time.
Truth rule: replace every placeholder in the sample answers with facts your friend can defend. A smaller truthful project is much safer than a large invented one. Interviewers routinely follow an answer three or four levels deep.

Two answer frameworks to memorize

CLEAR for design questions

  • C — Context: requirements, scale, constraints, and assumptions.
  • L — Layout: components and flow from commit to production.
  • E — Execution: concrete implementation, commands, and ownership.
  • A — Assurance: security, testing, observability, approvals, and compliance.
  • R — Recovery: rollback, disaster recovery, and lessons learned.

SCOPE for troubleshooting questions

  • S — State the symptom and blast radius.
  • C — Collect evidence before changing anything.
  • O — Isolate the failing layer: source, pipeline, registry, infrastructure, scheduler, network, application, or dependency.
  • P — Patch safely with the lowest-risk reversible action.
  • E — Eliminate recurrence through tests, alerts, guardrails, and a runbook.

Face-to-face behaviours that score well

  1. Start with assumptions. “I will assume the application is stateless, the cluster already exists, and production requires approval. I will call out where the design changes if those assumptions are wrong.”
  2. Think aloud, but stay structured. State the layer you are checking and why. Silence followed by a random command looks weaker than a clear diagnostic tree.
  3. Write the smallest working configuration first. Then add secrets, probes, limits, approvals, rollback and observability.
  4. Use the board. Draw boundaries, arrows, trust zones, artifact promotion and failure paths. Label who owns each control.
  5. Admit a gap professionally. “I have not operated that feature in production. My understanding is X; I would verify Y in the official documentation and test it in a non-production environment.”
  6. Separate what she did from what the team did. Use “I” for her implementation and decisions; use “we” for team outcomes.

A strong answer pattern

Question: “How did you implement CI/CD?”

Weak: “We used Azure DevOps. It builds Docker images and deploys to Kubernetes.”

Strong: “For a containerized API, I created a YAML pipeline with PR validation and separate build and deployment stages. The build ran unit tests and static checks, produced one immutable image tagged with the build ID and commit SHA, scanned it, and pushed it to the registry. We promoted the same digest through dev, test and production rather than rebuilding. Deployment used an Azure DevOps environment; production had an external approval/check, and the service connection had access only to its target namespace. We verified readiness and error-rate signals before completing the release, and rollback selected the previous known-good image. This reduced [real metric] and gave us traceability from work item to production deployment.”

F2F coding etiquette

  • Restate the requirement and inputs.
  • State what can fail.
  • Use meaningful names and indentation.
  • Add set -euo pipefail to non-trivial Bash, but explain when it may need careful handling.
  • Never place a real secret in sample YAML/HCL.
  • Validate: terraform fmt/validate, ansible-playbook --syntax-check, docker build, kubectl apply --dry-run=client, a linter, or a unit test.
  • End by naming two production improvements rather than trying to write a huge solution under time pressure.

How to narrate the drawing

  1. Requirements first: “I would confirm cloud, downtime tolerance, data sensitivity, release frequency, expected load, RTO/RPO, regulatory evidence and existing enterprise standards.”
  2. Source control: protected main branch, short-lived feature branches, peer review, work-item linking, required build validation, and no direct production changes.
  3. Build: one repeatable pipeline compiles and tests, performs code/dependency/secret/image checks, generates an SBOM where required, and creates one immutable artifact or image identified by build ID and commit SHA.
  4. Infrastructure: Terraform manages cloud and shared platform resources through reviewed modules and remote locked state. Ansible configures hosts or middleware when an image/container-only model is not sufficient.
  5. Promotion: the exact same artifact digest moves through environments. Environment-specific configuration comes from controlled variables/configuration stores, not rebuilding.
  6. Deployment: dev can be automatic; test may include integration/performance checks; production is protected by environment authorization, approval/checks and a narrow service identity. Use rolling, blue-green or canary based on risk and platform capability.
  7. Runtime: Kubernetes workloads have readiness/startup/liveness probes, requests/limits, disruption protection, least-privilege service accounts, restricted security contexts and network policy where supported.
  8. Verification and recovery: observe rollout health, error rate, latency and saturation; abort or roll back automatically/manual according to policy. Link evidence to the change record and update the runbook after incidents.

Design decisions the interviewer may challenge

Challenge Strong trade-off answer
“Why Azure DevOps when the target is AWS?” The delivery platform is independent of the target cloud. Use a short-lived, scoped identity, private connectivity where needed, and standard AWS APIs/tools. Choose based on enterprise integration, skills, licensing and governance.
“Why Terraform and Ansible together?” Terraform manages infrastructure lifecycle through provider APIs; Ansible is effective for guest OS, middleware and configuration orchestration. Avoid overlapping ownership of the same setting.
“Why not rebuild per environment?” Rebuilding can change dependencies and breaks artifact provenance. Build once, sign/scan once, and promote the same digest with externalized configuration.
“Rolling or blue-green?” Rolling is resource-efficient but mixes versions temporarily. Blue-green offers fast switch/rollback and stronger isolation but costs more and complicates data migration.
“Pipeline push or GitOps?” Pipeline push is simpler and familiar; GitOps improves pull-based reconciliation and cluster credential isolation. The choice depends on platform maturity, audit needs and operating model.
“How do you handle database changes?” Use backward-compatible expand/migrate/contract changes, separate schema migration, backups, validation, feature flags, and a rollback/forward-fix plan. Application rollback alone may not reverse data changes.

YAML mental model

pipeline
├── trigger / pr / schedules / resources
├── parameters and variables
└── stages
    └── jobs (agent job, deployment job, or server job)
        └── steps (task, bash, powershell, checkout, publish, download, template)
  • Stage: a major lifecycle boundary such as Validate, Build, DeployDev or DeployProd.
  • Job: a unit scheduled to one agent. Jobs are isolated unless outputs/artifacts are deliberately passed.
  • Step: a task or script executed sequentially within a job.
  • Deployment job: a job associated with an environment and deployment history; appropriate for deployments.
  • Template parameter: strongly suited to compile-time structure and reusable templates.
  • Variable: suited to values available during execution. Secrets must be stored in protected facilities, not in YAML.

Expression forms that panels often test

${{ ... }} Template/compile-time expression Insert stages/jobs, choose template structure, use parameters
$[ ... ] Runtime expression Set a variable from runtime context or dependencies

What to say about this YAML

  • PR validation and CI triggers are explicit.
  • Validation runs before build; a failed command stops the Bash step.
  • The build creates a pipeline artifact and a uniquely tagged image.
  • The production stage uses the same image tag created once; it does not rebuild.
  • Dev and prod use separate service connections and namespaces.
  • Production access is attached to an Azure DevOps environment. Approval/check configuration is administered on protected resources rather than entrusted to a changeable YAML file.
  • A production implementation should also include approved security scans, image signing/provenance where required, deployment verification, timeout, rollback, alert integration and retention policy.

Variables versus parameters — interview answer

Parameters are typed, supplied or expanded during template compilation, and are useful when the pipeline’s structure changes. Variables are strings used during execution; they can come from the pipeline, variable groups, output variables or runtime context. Do not put a secret in a parameter because template expansion can expose it. Use a secret store/secret variable, authorize only required pipelines, and map it to an environment variable only for the step that needs it.

Agent questions

Microsoft-hosted agents are ephemeral and simple to maintain, but have fixed images, no persistent cache between runs, internet/network constraints and usage limits. Self-hosted agents allow private network access, custom software and persistent caches, but require patching, isolation, capacity management and stronger protection because build code executes on them.

For sensitive deployments, separate pools by trust level, avoid using the same long-lived agent for untrusted PRs and production access, minimize credentials on disk, clean workspaces and rotate/reimage agents.

Branch and release controls

A credible enterprise flow includes required reviewers, build validation, work-item linkage if needed, comment resolution, restricted bypass, protected main/release branches, immutable artifacts, environment permissions, a clear hotfix path and separation between people who change code and people who approve production when policy requires it.

Terraform — IaC design, state and safe delivery

The interview mental model

Terraform reads configuration, loads provider schemas, compares configuration and state with real infrastructure, builds a dependency graph, proposes a plan and applies provider API operations. The state is not merely a cache to delete when inconvenient; it maps Terraform resource addresses to real objects and stores attributes needed for future operations.

State answers expected at five years

  • Use a remote backend for team collaboration and protect it with encryption, versioning/recovery, tightly scoped access and a backend that supports locking.
  • Terraform automatically locks state for write operations when the backend supports it. Do not disable locking as a normal workaround.
  • State can contain sensitive values even when an output is marked sensitive; control access to the backend and avoid putting secrets into resource arguments when a safer reference pattern exists.
  • Split state by lifecycle/ownership and blast radius, not by creating one enormous state for the whole organization or one state per tiny resource.
  • Back up before dangerous manual state operations. Prefer moved blocks, import blocks/commands and reviewed refactoring over editing state JSON.

  }

  type = string
}

  type = map(string)
}

variable "ami_id" {
  type = string
}

  type = map(object({
    instance_type = string
    subnet_key    = string
  }))
}

variable "allowed_cidrs" {
  type    = set(string)
  default = []
}

  type    = string
  default = "ap-south-1"
}

# main.tf
locals {
  common_tags = {
    Application = var.name
    ManagedBy   = "terraform"
    Repository  = "platform-infra"
  }
}

resource "aws_security_group" "app" {
  name_prefix = "${var.name}-"
  description = "Application ingress and egress"
  vpc_id      = var.vpc_id

  dynamic "ingress" {
    for_each = var.allowed_cidrs
    content {
      description = "HTTPS from approved network"
      protocol    = "tcp"
      from_port   = 443
      to_port     = 443
      cidr_blocks = [ingress.value]
    }
  }

  egress {
    protocol    = "-1"
    from_port   = 0
    to_port     = 0
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    create_before_destroy = true
  }
}

resource "aws_instance" "app" {
  for_each = var.instances

  ami                    = var.ami_id
  instance_type          = each.value.instance_type
  subnet_id              = var.subnet_ids[each.value.subnet_key]
  vpc_security_group_ids = [aws_security_group.app.id]

  metadata_options {
    http_tokens = "required"
  }

  root_block_device {
    encrypted = true
  }

  tags = {
    Name = "${var.name}-${each.key}"
  }
}

# outputs.tf
output "instance_ids" {
  description = "Instance IDs keyed by logical name."
  value       = { for key, instance in aws_instance.app : key => instance.id }
}

Why this example scores well:

  • Types and validation make the module contract clear.
  • for_each gives stable key-based addresses; removing one key does not renumber every later object as count can.
  • Inputs refer to subnet keys rather than relying on map ordering.
  • Security settings and common tags are explicit.
  • The output preserves the same logical keys.

count versus for_each

Use count for nearly identical indexed instances or a simple zero/one condition. Use for_each when objects have meaningful stable keys or different attributes. Converting between them changes resource addresses; plan the state move with moved blocks or explicit state operations rather than accepting unnecessary recreation.

resource "aws_s3_bucket" "logs" {
  for_each = toset(["app", "audit", "access"])
  bucket   = "example-${each.key}-logs"
}

Dependencies

Terraform infers dependencies from references such as aws_security_group.app.id. Use depends_on only for a real dependency Terraform cannot infer. Excessive explicit dependencies make plans conservative and hide poor module interfaces.

Lifecycle controls

lifecycle {
  create_before_destroy = true
  prevent_destroy       = true
  ignore_changes        = [tags["LastPatchedAt"]]
}

Explain each carefully:

  • create_before_destroy can reduce downtime but may fail when names must be unique or quotas are tight.
  • prevent_destroy is a guardrail, not a backup strategy; changing/removing it can still permit destruction.
  • ignore_changes is not a blanket solution for drift. Use it only when another owner legitimately manages that attribute.

Import and refactoring

For existing infrastructure, write the intended configuration, identify the exact resource ID, import it, then review the plan until Terraform proposes only intentional changes. Import brings an object into state; it does not automatically create a complete maintainable design.

Safe Terraform CI/CD flow

  1. PR: fmt, validate, lint/security/policy checks, module tests where present, and a plan generated with read-only/plan permissions.
  2. Review: store or present the plan safely; reviewers inspect create/update/destroy actions and sensitive impacts.
  3. Merge: apply the reviewed commit through a protected environment and serialized state access.
  4. Post-apply: capture outputs/evidence, verify the target, monitor and reconcile any partial failure.
  5. Scheduled drift detection: run a read-only plan and route unexpected drift to owners; do not auto-apply unexplained changes.

Ansible — idempotent configuration and controlled rollout

Core model

  • Inventory defines managed hosts and groups, plus connection variables.
  • Play maps a host pattern to variables, roles and tasks.
  • Task calls a module and should usually describe desired state.
  • Handler runs only when notified by a changed task, commonly for a service restart/reload.
  • Role packages defaults, variables, tasks, handlers, templates, files and metadata into a reusable unit.
  • Facts are discovered host data; gather only what is needed when performance matters.
  • Vault encrypts sensitive Ansible data, but access to the Vault password/key still needs secure management.

Rolling deployment with validation and recovery

# playbooks/deploy.yml
---
- name: Deploy application in small batches
  hosts: web
  become: true
  serial: 1
  max_fail_percentage: 0
  any_errors_fatal: true

  vars:
    release_version: "{{ requested_release }}"
    release_root: /opt/sample/releases
    current_link: /opt/sample/current

  pre_tasks:
    - name: Confirm required release variable is present
      ansible.builtin.assert:
        that:
          - release_version is defined
          - release_version | length > 0
        fail_msg: Pass -e requested_release=<version>

  tasks:
    - name: Deploy and verify release
      block:
        - name: Create versioned release directory
          ansible.builtin.file:
            path: "{{ release_root }}/{{ release_version }}"
            state: directory
            owner: sample
            group: sample
            mode: '0750'

        - name: Unpack immutable release artifact
          ansible.builtin.unarchive:
            src: "/srv/artifacts/sample-{{ release_version }}.tar.gz"
            dest: "{{ release_root }}/{{ release_version }}"
            remote_src: true
            owner: sample
            group: sample
            creates: "{{ release_root }}/{{ release_version }}/app.bin"

        - name: Point current symlink to new release
          ansible.builtin.file:
            src: "{{ release_root }}/{{ release_version }}"
            dest: "{{ current_link }}"
            state: link
            force: true
          notify: Restart sample service

        - name: Flush handler before health verification
          ansible.builtin.meta: flush_handlers

        - name: Wait for local health endpoint
          ansible.builtin.uri:
            url: http://127.0.0.1:8080/health
            status_code: 200
            return_content: false
          register: health
          retries: 12
          delay: 5
          until: health.status == 200

      rescue:
        - name: Stop rollout after a failed host
          ansible.builtin.fail:
            msg: "Release {{ release_version }} failed health verification on {{ inventory_hostname }}"

  handlers:
    - name: Restart sample service
      ansible.builtin.service:
        name: sample
        state: restarted

For a real load-balanced service, add drain/rejoin actions delegated to the load balancer/control plane and preserve the previous symlink target for rollback. Do not hide failures with ignore_errors: true.

Docker — build efficiency, runtime behaviour and security

Concepts that must be precise

  • An image is an immutable content-addressed package of layers and metadata; a container is a runtime instance with a writable layer.
  • Layer cache reuse depends on instruction order and inputs. Copy dependency manifests and restore dependencies before copying frequently changing source.
  • CMD supplies default command/arguments; ENTRYPOINT defines the executable. In exec form they handle signals more predictably than shell form.
  • EXPOSE documents a port; it does not publish it to the host.
  • A volume persists or shares data independently of a container’s writable layer. Bind mounts map a host path and carry tighter host coupling/security implications.
  • Container networking, DNS and port publishing are different layers; know which address/port is used from host, another container and Kubernetes.

Kubernetes — workloads, networking, security and diagnosis

Architecture in one answer

The control plane exposes the API server, stores cluster state in etcd, schedules Pods and runs controllers that reconcile desired state. Each worker has a kubelet that manages Pods, a container runtime and a network component. Users submit desired state to the API; controllers continuously reconcile actual state toward it.

Failure-state playbooks

CrashLoopBackOff

  1. kubectl describe pod for state, exit reason and events.
  2. kubectl logs --previous because the current container may have restarted.
  3. Check command/entrypoint, missing config/secret, dependency reachability, permissions, probe misconfiguration, architecture and OOM.
  4. Compare with previous ReplicaSet/image/config; do not merely increase restart tolerance.
  5. Roll back or fix the smallest cause, then add a pre-deployment test or alert.

ImagePullBackOff

Check exact image/tag, registry existence, pull secret/managed identity, namespace association, node-to-registry DNS/network, rate limits, certificate trust and architecture. Events normally reveal not found, unauthorized or transport failure.

Pending

Read scheduler events. Common causes: insufficient CPU/memory, unbound PVC, node selector/affinity mismatch, taints without tolerations, unavailable zone, quota/limit range, host port conflict or autoscaler limits.

OOMKilled

Confirm lastState.terminated.reason, exit code, node pressure and metrics. Determine leak versus legitimate working set, tune application/runtime, set realistic request/limit, load test and alert on approaching saturation. Raising the limit alone may move the problem to the node.

Lab 01 Bash: endpoint check with retry, timeout and correct exit code Very likely 15 minutes

Interview prompt

Write a script that calls a health URL up to five times, waits three seconds between attempts, treats only HTTP 200 as success, prints useful errors, and exits non-zero if all attempts fail. The URL should be an argument.

What they evaluate

  • Arguments and validation
  • Timeouts and retries
  • HTTP versus transport error
  • Cleanup and quoting
  • Meaningful exit codes

Model solution and explanation

#!/usr/bin/env bash
set -Eeuo pipefail

usage() {
  printf 'Usage: %s <health-url>\n' "$0" >&2
  exit 2
}

[[ $# -eq 1 ]] || usage
url=$1
max_attempts=5
sleep_seconds=3

for ((attempt = 1; attempt <= max_attempts; attempt++)); do
  # Keep curl's transport result separate from the HTTP code.
  response_file=$(mktemp)
  curl_error=$(mktemp)

  if http_code=$(curl \
      --silent \
      --show-error \
      --location \
      --connect-timeout 3 \
      --max-time 8 \
      --output "$response_file" \
      --write-out '%{http_code}' \
      "$url" 2>"$curl_error"); then
    if [[ "$http_code" == "200" ]]; then
      printf 'Health check succeeded on attempt %d: HTTP %s\n' "$attempt" "$http_code"
      rm -f "$response_file" "$curl_error"
      exit 0
    fi
    printf 'Attempt %d/%d returned HTTP %s\n' "$attempt" "$max_attempts" "$http_code" >&2
  else
    printf 'Attempt %d/%d failed: %s\n' \
      "$attempt" "$max_attempts" "$(<"$curl_error")" >&2
  fi

  rm -f "$response_file" "$curl_error"
  (( attempt < max_attempts )) && sleep "$sleep_seconds"
done

printf 'Health check failed after %d attempts: %s\n' "$max_attempts" "$url" >&2
exit 1

Explain aloud: an HTTP 500 can still be a successful TCP/HTTP exchange, so the script separately checks the status code. Timeouts prevent an agent from hanging. Exit 0 lets a pipeline continue; exit 1 fails the gate; exit 2 denotes usage error.

Production refinements: trap cleanup, expected-code parameter, exponential backoff with jitter, TLS/CA policy, authentication from a secret environment variable, JSON parsing and emitting structured telemetry.

Lab 03 Python: summarize JSON application logs Likely 25 minutes

Interview prompt

Each input line is JSON with timestamp, service, status, and optional latency_ms. Read a file, ignore malformed lines while counting them, print 5xx counts by service and p95 latency by service, and return non-zero when malformed lines exceed 1%.

What they evaluate

  • Input validation and types
  • Malformed-data handling
  • Correct grouping
  • Testable percentile function
  • Complexity and production trade-off

Model solution and explanation

#!/usr/bin/env python3
from __future__ import annotations

import argparse
import json
import math
import sys
from collections import Counter, defaultdict
from pathlib import Path
from typing import Any


def percentile(values: list[float], p: float) -> float | None:
    if not values:
        return None
    ordered = sorted(values)
    # Nearest-rank percentile: simple and explainable in an interview.
    rank = max(1, math.ceil(p * len(ordered)))
    return ordered[rank - 1]


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(description="Summarize newline-delimited JSON logs")
    parser.add_argument("path", type=Path)
    return parser.parse_args()


def main() -> int:
    args = parse_args()
    if not args.path.is_file():
        print(f"Input is not a file: {args.path}", file=sys.stderr)
        return 2

    total = 0
    malformed = 0
    errors: Counter[str] = Counter()
    latencies: dict[str, list[float]] = defaultdict(list)

    with args.path.open("r", encoding="utf-8") as handle:
        for line_number, raw in enumerate(handle, start=1):
            if not raw.strip():
                continue
            total += 1
            try:
                record: dict[str, Any] = json.loads(raw)
                service = str(record["service"])
                status = int(record["status"])
                if 500 <= status <= 599:
                    errors[service] += 1
                if "latency_ms" in record:
                    latencies[service].append(float(record["latency_ms"]))
            except (json.JSONDecodeError, KeyError, TypeError, ValueError) as exc:
                malformed += 1
                print(f"line {line_number}: malformed ({exc})", file=sys.stderr)

    print("5xx counts by service")
    for service, count in sorted(errors.items()):
        print(f"  {service}: {count}")

    print("p95 latency in milliseconds")
    for service, values in sorted(latencies.items()):
        p95 = percentile(values, 0.95)
        print(f"  {service}: {p95:.1f}" if p95 is not None else f"  {service}: n/a")

    malformed_ratio = malformed / total if total else 0.0
    print(f"records={total} malformed={malformed} ratio={malformed_ratio:.2%}")
    return 1 if malformed_ratio > 0.01 else 0


if __name__ == "__main__":
    raise SystemExit(main())

Discuss memory: this stores latency lists, which is acceptable for a small exercise. For very large streams, use an approximate percentile sketch or an observability backend rather than retaining every sample.

[CmdletBinding()]
param(

    [ValidateNotNullOrEmpty()]
    [string]$ServiceName,

    [ValidateRange(1, 300)]
    [int]$TimeoutSeconds = 30
)

        Write-Host "Starting service '$ServiceName' (current: $($service.Status))"

    Write-Host "Service '$ServiceName' is Running."
    exit 0
}

Scenario practice

15 high-probability troubleshooting scenarios

For every scenario, begin with impact and evidence. Avoid commands that mutate the system until the failing layer and rollback conditions are understood.

Universal production triage checklist

1. What changed? commit, image, config, secret, infrastructure, traffic, dependency
2. What is the blast radius? one user, one Pod, one AZ, one environment, everyone
3. Which signal proves the symptom? request, log, event, metric, trace, audit record
4. Which layer first diverged from normal?
5. What is the safest reversible mitigation?
6. How will we verify customer recovery?
7. What guardrail prevents recurrence?
Scenario 01Pipeline works locally but fails on the hosted agent
Prompt: The build succeeds on the developer laptop but the Azure Pipeline fails during compile or test.

Use SCOPE:

  1. Confirm the exact failing command, agent image, commit and whether failure is deterministic.
  2. Compare runtime/tool versions (dotnet --info, node --version, terraform version), environment variables, working directory, filesystem case sensitivity, line endings and locale/time zone.
  3. Check restored dependency lock files, private feed authentication, proxy/DNS/firewall and service connection authorization.
  4. Reproduce in the same clean container/agent image. A laptop may have uncommitted files or global tools hiding the problem.
  5. Pin/setup the required tool version in YAML, commit lock files, remove hidden local dependency and add a preflight diagnostic that does not print secrets.

A strong answer does not immediately switch to a self-hosted agent just to inherit the developer’s machine state.

Scenario 02Production stage is waiting or skipped
Prompt: Build and dev succeeded, but Azure DevOps production deployment is either waiting indefinitely or marked skipped.

Check the stage timeline, dependsOn, condition evaluation and branch value first. Then inspect every protected resource consumed by the stage: environment approval/check, service connection, variable group, secure file and agent pool. A resource can be waiting for approval, branch control, business hours, exclusive lock, external REST/Azure Monitor check or authorization.

Do not modify YAML blindly. Identify whether the state is skipped by logic, waiting on a check, queued for an agent, or failing target access. Resolve the correct owner/permission, record any bypass according to policy, and add clear timeout/notification/runbook guidance.

Scenario 03Terraform state lock will not clear
Prompt: A pipeline failed and later runs report that the state is locked.
  1. Stop new applies and identify the backend, workspace/key and lock ID.
  2. Check pipeline runs, HCP/backend activity, process ownership and team communication to prove no legitimate writer remains.
  3. Look for a failed agent/network interruption that prevented automatic unlock.
  4. Only after proving the lock is stale, run terraform force-unlock LOCK_ID from an authorized context.
  5. Immediately run a refresh/plan and inspect real resources/state for partial operations.
  6. Prevent recurrence with serialized applies, graceful cancellation, lock timeout, reliable agents and an ownership/runbook process.

Never use -lock=false as the routine fix; it permits concurrent writers and possible state corruption.

Scenario 04Terraform wants to replace a critical resource
Prompt: A plan unexpectedly shows destroy/create for a production database, load balancer or cluster.

Stop the release. Read the plan at attribute level and determine why the provider marks the change as replacement. Compare provider/version lock file, module upgrade, resource address, state, imported identity, immutable cloud attributes and configuration defaults.

Possible safe paths include a moved block for refactoring, importing the existing object to the correct address, reverting an accidental input, performing a documented maintenance migration, or redesigning with create_before_destroy only when the service supports parallel resources and unique naming. prevent_destroy can guard against accidents but does not solve the underlying design.

Scenario 05Ansible changes the same host on every run
Prompt: A supposedly idempotent playbook reports changed and restarts the service every time.

Run with --check --diff where safe and isolate the first task reporting change. Common causes are shell/command without creates/removes or truthful changed_when, a template containing a current timestamp/random order, file ownership/mode drift, a package task requesting latest, or a normal task that restarts unconditionally.

Replace imperative commands with state modules, make generated content deterministic, notify a handler only on real configuration/artifact change, and add an idempotency test that runs the role twice and expects zero changes on the second run.

Scenario 06New Pods show ImagePullBackOff
Prompt: A Deployment created new Pods, but all remain in `ImagePullBackOff`.

Start with kubectl describe pod events. Distinguish image not found, unauthorized, rate limit, DNS/TLS/network timeout and architecture mismatch. Verify repository/tag or digest exists, registry hostname, pull secret/workload identity, ServiceAccount association, namespace, registry firewall/private endpoint, node DNS/route and certificate chain.

Mitigate by rolling back to the known-good digest if impact exists. Prevent with image existence/signature policy, pre-deployment pull validation, immutable tags, registry monitoring and correct node/registry identity.

Scenario 07New Pod is in CrashLoopBackOff
Prompt: A new release repeatedly starts and exits while the old release was healthy.

Run describe, current logs and logs --previous; inspect exit reason/code, command, config, secret, mounted files, permissions, probes, resources and dependency connection. Compare the Pod spec and image digest with the previous ReplicaSet.

If the last state is OOMKilled, investigate memory. If exit code 1 and logs show invalid configuration, fix the source and add validation. If liveness kills a slow starter, introduce/tune a startup probe rather than simply raising failure thresholds. Pause/rollback when customer impact exceeds the change policy threshold.

Scenario 08Pods are Pending after scaling
Prompt: HPA requests ten replicas but six remain Pending.

Scheduler events are the fastest signal. Check resource requests versus allocatable capacity, node group/cluster autoscaler state and limits, taints/tolerations, affinity/topology rules, zone availability, quota/LimitRange, unbound PVC and host ports.

Avoid “add more nodes” before identifying the constraint. A strict anti-affinity or zonal PVC can remain unschedulable despite spare aggregate CPU. Fix the binding constraint, then load test and align HPA maxima, node scaling, quotas and dependency capacity.

Scenario 09Service has no endpoints
Prompt: The Service exists and DNS resolves, but requests fail; `kubectl get endpoints` is empty.

Compare Service.spec.selector with actual Pod labels. Then check Pod readiness, namespace and target controller. A selector mismatch or all Pods being unready produces no usable endpoints. Verify the Service targetPort resolves to the named/numeric container port and the application listens on the Pod interface, not only 127.0.0.1.

Fix labels/selectors through version-controlled manifests, validate them in CI, and add an endpoint/readiness deployment check. Do not recreate the cluster.

Scenario 10Deployment is green but users receive 503
Prompt: All Pods are Running/Ready and rollout status is successful, yet external clients see intermittent 503.

Trace from the component producing the 503: DNS, edge/load balancer, ingress controller, Service endpoints, Pod logs and downstream dependencies. Inspect ingress/controller events and logs, backend health, connection/timeout/retry settings, readiness accuracy, capacity, termination behaviour during rollout and whether the app returns 503 for dependency saturation.

“Pod Ready” may only test a shallow endpoint. Improve readiness to represent ability to serve safely without making it depend on every optional downstream. Add graceful termination (preStop/drain as appropriate), capacity signals and user-path synthetic checks.

Scenario 11Node or agent disk is full
Prompt: Builds fail with no space left, or a Kubernetes node enters disk pressure.

Check filesystem and inode usage, largest directories, container/image/log/cache growth and deleted-open files. On a K8s node, review node conditions, kubelet eviction events, image filesystem and ephemeral-storage requests/limits.

Mitigate according to ownership: stop runaway logging, safely rotate/retain logs, prune stale build caches/images through policy, expand storage when justified, or replace/recycle an ephemeral agent/node. Prevent with monitoring, retention, quotas/ephemeral-storage controls and capacity forecasting. Never run broad rm -rf on production under interview pressure.

Scenario 12TLS certificate expired or is not trusted
Prompt: Clients fail with certificate errors after a release or endpoint change.

Use openssl s_client -connect host:443 -servername host and curl -v from the affected network path. Check expiry, hostname/SAN, issuer/chain, SNI, listener binding, secret/certificate version, trust store and clock skew. Determine whether the certificate at the edge, ingress or application layer is wrong.

Restore the correct certificate/chain through the controlled secret/certificate process, verify from representative clients, and prevent with automated issuance/renewal, expiry alerts, staged rotation and a runbook. Do not disable TLS verification as a “fix.”

Scenario 13A secret was printed in pipeline logs
Prompt: A token appears in an Azure Pipeline log visible to the project team.

Treat it as compromised: stop/contain the run, revoke or rotate the credential, assess where it was used, review access/audit logs and remove retained copies according to platform policy. Deleting or masking the visible line does not undo exposure.

Find why masking failed: secret was hard-coded, transformed/substringed, printed by set -x, passed on command line, dumped in environment/debug output or fetched too broadly. Move to protected secret/workload identity, map only to the needed step, disable verbose secret output and add secret scanning/training.

Scenario 14Latency increases after deployment but error rate is normal
Prompt: p95 latency doubles after a release; CPU is moderate and error rate remains low.

Compare deployment markers, p50/p95/p99, throughput, saturation and distributed traces. Identify whether time moved into application code, database calls, DNS/TLS, external API, connection pool, garbage collection, lock contention or queueing. Compare old/new versions under the same load and inspect feature/config changes.

Mitigate by canary rollback/feature disable when the SLO burn warrants it. Prevent with performance baselines, trace instrumentation, load tests for critical paths, query budgets and progressive delivery based on latency as well as errors.

Scenario 15Rollback did not restore service
Prompt: The team rolled back the application image, but the system remains broken.

Check what was not rolled back: database schema/data, configuration/secret, infrastructure, feature flag, message format, cache, migration job or external dependency. Confirm the actual image digest and active ReplicaSet/traffic route. Review the release timeline rather than assuming image rollback equals full-system rollback.

Use backward-compatible expand/migrate/contract changes, versioned configuration, reversible flags, database backup/forward-fix plans and explicit rollback testing. During the incident, choose restore, forward fix or data repair based on integrity and risk; communicate clearly that the previous binary may be incompatible with the new data state.

Whiteboard practice

System-design and architecture round

Primary practice prompt

Design a secure CI/CD platform for 20 containerized services across dev, test and production. Source is in Azure Repos, Azure DevOps runs pipelines, Terraform creates cloud infrastructure, Ansible configures the remaining VMs/middleware, images run on AKS or EKS, and production is regulated. Releases should be frequent, traceable and recoverable.

A seven-minute answer structure

1. Clarify requirements

Ask or state assumptions:

  • Number of teams/repositories and whether services release independently.
  • Target cloud/regions, cluster tenancy and network connectivity.
  • Release frequency, availability/SLO, peak traffic and stateful dependencies.
  • Data classification and regulatory evidence/retention requirements.
  • RTO/RPO, disaster-recovery region and maintenance constraints.
  • Existing identity, secret, monitoring, security-scan and service-management standards.
  • Whether the team prefers pipeline-driven deployment, GitOps or a hybrid.

2. Draw trust and lifecycle boundaries

Untrusted/low-trust PR execution
        │
        ▼
Source → CI validation → immutable artifact registry
                         │
                         ▼
             protected deployment orchestration
               │             │             │
              Dev           Test          Prod
                              approval/checks

On a board, draw a clear vertical boundary between build and privileged deployment. Build agents should not automatically inherit production credentials.

3. Source and CI design

  • One service per repository or clear monorepo ownership/path filters; shared templates in a versioned, governed repository.
  • Protected main branch, PR reviewers, work-item linkage where required and required CI status.
  • CI restores from locked dependencies, compiles, tests, checks quality/security/IaC, and produces one image plus metadata: commit SHA, build ID, SBOM/provenance and scan results according to policy.
  • Use ephemeral or isolated agent pools. Untrusted contributions never run where production secrets/network access exist.
  • Publish test results and immutable artifacts; retain evidence by risk/policy.

4. Infrastructure and configuration

  • Terraform root modules per environment/platform boundary; reusable versioned modules; remote encrypted state and supported locking; protected plan/apply identities; reviewed saved plan.
  • Ansible roles for OS/middleware configuration that is not better baked into images or managed through cloud/Kubernetes APIs. Dynamic/static inventory according to environment; Vault/secret integration; rolling batches and health checks.
  • Avoid having Terraform and Ansible both own the same field.

5. Promotion and deployment

  • Dev deploys automatically after successful CI.
  • Integration/performance/security validation occurs in test using the same image digest.
  • Production environment is a protected Azure DevOps resource with authorization, approval/checks, exclusive deployment control where needed and narrowly scoped cloud/Kubernetes identity.
  • Use canary or blue-green for high-risk services when traffic management and observability support it; otherwise controlled rolling update.
  • Environment configuration is externalized and versioned/controlled. Secrets are fetched at runtime through an approved identity.
  • Verify readiness, synthetic transactions, error rate, latency and saturation before marking release successful.

6. Runtime platform

  • Separate namespaces/accounts/subscriptions or clusters based on trust, blast radius and policy.
  • Deployment, Service and ingress/gateway; probes; requests/limits; HPA; PDB; topology distribution; controlled service account/RBAC; restricted Pod security; network policy; registry policy.
  • Central logs/metrics/traces with deployment markers and SLO alerts. Platform and application ownership are clear.

7. Recovery and compliance

  • Previous known-good image/digest and manifests, traffic switch/rollback or forward-fix process.
  • Database changes use expand/migrate/contract with backup and validation; rollback is tested rather than assumed.
  • Audit links requirement/change, code review, CI evidence, artifact, approvals, deployment and post-deployment verification.
  • Runbooks, incident process, restore tests and periodic access review.

Capacity and scaling follow-ups

“How will pipelines scale for 20 services?”

Measure queue time and job duration; use autoscaled/ephemeral agent pools, separate pools by workload/trust, cache dependencies safely, reuse templates, parallelize independent tests, apply path filters in a monorepo, enforce concurrency limits for shared targets and prioritize production/hotfix jobs.

“How will Terraform scale?”

Split state by ownership/lifecycle/blast radius, not per individual resource. Version modules, avoid cross-state dependency chains where possible, expose small stable outputs, serialize each state, use policy/plan review and make platform teams own shared modules with product-team self-service inputs.

“How will Kubernetes survive an AZ loss?”

Distribute nodes and replicas across zones, set topology rules that still permit scheduling, size remaining zones for failure, use multi-AZ load balancing and data services, test disruption, and ensure dependencies and persistent volumes support the same failure model. A three-zone cluster is not sufficient if all replicas or storage are effectively in one zone.

Security follow-ups

“How does the pipeline authenticate to AWS/Azure?”

Prefer workload identity/federated short-lived credentials where platform support and enterprise policy allow. Scope the role to exact resources/actions, restrict which protected pipeline/environment may use it, separate environments/accounts/subscriptions, log use and eliminate static credentials from agents and YAML.

“How do you prevent a malicious PR from stealing secrets?”

Do not expose secrets/protected resources to untrusted PR jobs; isolate agents and networks; require review before privileged stages; use environment/resource checks; avoid automatic authorization of variable groups/service connections; minimize checkout credentials; scan and audit pipeline changes; use short-lived identities.

“What is your supply-chain approach?”

Trusted/pinned bases and dependencies, lock files, approved registries, scanning, secret detection, IaC policy, provenance/signing where required, immutable digests, protected artifact promotion, patch ownership and an exception process with expiry.

Reliability follow-ups

“What if Azure DevOps is unavailable during an incident?”

Define a controlled break-glass process with limited, audited access; keep deployable artifacts and runbooks available according to continuity design; rehearse recovery; restore normal declarative state afterward. Break-glass is not a second everyday deployment path.

“What if the new release is compatible with old DB schema but not vice versa?”

Sequence expand changes first, deploy code compatible with both schemas, migrate/backfill, observe, and contract only after all old code is gone and rollback window closes. Feature flags can decouple activation.

Alternative design prompt: migration from manual releases

A good phased answer:

  1. Inventory applications, dependencies, release pain, ownership and risk.
  2. Establish source control, artifact versioning and a repeatable build before automating production.
  3. Add tests/scans and lower-environment deployment.
  4. Codify infrastructure/configuration incrementally; import existing resources safely.
  5. Introduce production approval, observability and rollback.
  6. Pilot one low/medium-risk service, measure outcomes, standardize templates, train teams and expand by waves.
  7. Retire manual paths only after evidence, support and rollback are ready.

Avoid proposing a “big-bang DevOps transformation” with no migration, ownership or operating model.

Whiteboard scoring checklist

  • Requirements and assumptions stated.
  • Architecture and data/request/release flow visible.
  • Trust boundaries and identities visible.
  • Build once/promote same artifact.
  • Terraform state and Ansible ownership explained.
  • K8s availability/security/observability covered.
  • Database and rollback limitations covered.
  • Regulated traceability and audit covered.
  • Trade-offs and failure modes discussed.
  • Clear, time-bounded communication.

Azure DevOps — 25 questions

01What is the difference between a stage, job and step?P0

A stage is a major lifecycle boundary and dependency/approval point. A job is a unit scheduled to one agent or server and has an isolated workspace/process context. A step is a task or script executed sequentially inside a job.

02YAML pipeline or Classic pipeline — which do you prefer?P1

Prefer YAML for versioning, review, branching and reusable templates. Classic may remain for legacy processes or UI-managed release flows. A mature answer focuses on governance and migration rather than saying Classic is always wrong.

03Parameters versus variables?P0

Parameters are typed and mainly shape templates at compile time. Variables are string values available during execution and can come from runtime context, output variables or protected variable groups. Do not use parameters to carry secrets.

04Explain `${{ }}`, `$[ ]` and `$( )`.P0

${{ }} is template/compile-time expansion, $[ ] is a runtime expression often used for conditions or dependency outputs, and $(name) is macro expansion before a task runs. Scope and evaluation timing are the common source of bugs.

05What is the difference between `trigger` and `pr`?P0

trigger controls CI runs after pushes to branches/paths. pr controls pull-request validation where supported by the repository integration. Repository branch policies can also require a pipeline independently of YAML.

06Why use a deployment job?P0

It models deployment rather than ordinary build work, associates execution with an environment and deployment history, and supports deployment strategies. It is the right place to attach target-specific governance and verification.

07What is an Azure DevOps environment?P0

A logical deployment target/group with history, permissions and protected-resource checks. It can represent dev, test or prod and may contain Kubernetes/VM resources, but it is also useful as a governance boundary even when target details are external.

08Where should production approvals be configured?P0

For YAML pipelines, use approvals/checks on the protected environment or other resource so the resource owner controls consumption. Do not rely only on a condition embedded in YAML that the pipeline author can change.

09What is a service connection?P0

A governed identity/configuration that lets pipelines access Azure, AWS, Kubernetes, a registry or another service. Scope it to the target, restrict which pipelines may use it, separate environments and prefer short-lived/federated identity where supported.

10Microsoft-hosted versus self-hosted agents?P0

Hosted agents are ephemeral and low-maintenance but have fixed images/network limits and no persistent local state. Self-hosted agents support private connectivity/custom tools/cache but require patching, isolation, capacity and strong secret protection.

11Pipeline artifact versus cache?P0

An artifact is an intentional output passed between stages/runs or retained for deployment. A cache is an optimization for restorable dependencies and may be evicted. A release must never depend on cache as its authoritative artifact.

12How do you pass a value from one job or stage to another?P0

Set it with the Azure logging command and isOutput=true on a named step, then reference it through dependencies or stageDependencies using a runtime expression. Ordinary variables set in one job are not automatically global.

13How do templates improve pipelines?P1

They centralize tested stages/jobs/steps and reduce duplication. Use typed parameters and version/govern the template repository. Avoid a monolithic template that hides every decision from service teams.

14What is build once, deploy many?P0

Create and verify one immutable artifact/image, then promote the exact version/digest through environments with externalized configuration. Rebuilding per environment weakens provenance and can introduce dependency differences.

15How should secrets be used in a pipeline?P0

Store them in Key Vault/protected secret variables or use workload identity; authorize only required pipelines; map to a step environment only when needed; never echo, pass on command line or put in YAML. Rotate and investigate any exposure.

16What is a variable group?P1

A Library resource containing shared variables/secrets and its own permission model. It can link to Key Vault. Treat it as a protected resource and avoid granting every pipeline automatic access.

17How do conditions work?P1

A condition decides whether a stage/job/step runs, using status functions and variables. When replacing the default, include the desired success/cancellation semantics explicitly; otherwise work may run after a failure or be skipped unexpectedly.

18Which branch policies would you apply?P0

Required reviewers, build validation, comment resolution, restricted direct pushes/bypass, work-item linkage or status checks where required, and an explicit merge strategy. Tune them to risk and keep an auditable emergency path.

19Why does a pipeline pass locally but fail in CI?P0

CI is clean and may differ in OS, case sensitivity, tool version, working directory, credentials, network and uncommitted files. Print non-secret diagnostics, pin tool versions, use lock files and reproduce in the agent image.

20How would you reduce pipeline duration?P1

Measure the critical path; cache dependencies safely, parallelize independent tests, split long suites, use path filters, avoid duplicate builds/downloads, use appropriate agents and publish only required files. Do not trade away mandatory validation.

21How do you secure a self-hosted agent?P0

Separate pools by trust/environment, patch/reimage, run with least privilege, restrict network/egress, avoid persistent credentials, clean workspace, monitor, limit pipeline authorization and never mix untrusted PR code with production access.

22How would you handle an untrusted fork PR?P1

Run only low-privilege validation with no secrets or protected resources on isolated ephemeral infrastructure. Require trusted review before any privileged pipeline or environment is reachable.

23How do you roll back a release?P0

Retain the last known-good immutable artifact and declarative configuration, trigger an authorized rollback/traffic switch, verify user-facing health and preserve evidence. Explain that data/schema changes may require forward fix or restore, not binary rollback alone.

24How do you deploy to several repositories or consume another pipeline?P2

Declare repository/pipeline resources, pin the expected branch/version and secure authorization. Trigger and artifact lineage should be explicit; avoid silently consuming a mutable latest build from another team.

25How would you prevent two production deployments colliding?P1

Use protected environment checks/exclusive lock or an equivalent serialization mechanism, define whether latest wins or runs queue, and keep deployment logic idempotent. Also serialize any shared Terraform state or migration operation.

Terraform — 25 questions

01Why does Terraform need state?P0

State maps resource addresses to real objects and stores attributes needed to calculate changes. Without correct state, Terraform cannot reliably know what it owns or plan lifecycle operations.

02Why use remote state?P0

It provides a shared authoritative state location for teams, can keep state off local disks, and may provide locking. Protect it with encryption, access control, recovery/versioning and audit.

03What is state locking?P0

A supported backend prevents concurrent write operations against the same state. Terraform acquires it automatically for writes; disabling locks can allow conflicting writers and corruption.

04When is `force-unlock` acceptable?P0

Only after proving the lock is stale and no valid apply is running. Use the exact lock ID, then run a plan and inspect for partial operations. Document the failure that left the lock behind.

05`terraform plan` versus `apply`?P0

Plan calculates proposed actions; apply executes them. In controlled CI, save a plan, review/approve it, and apply that exact plan from the same commit/context rather than silently regenerating a different one.

06What is a module?P0

A reusable group of Terraform configuration with a documented input/output contract. Good modules hide repeated implementation but expose meaningful choices; they are versioned and tested rather than copied.

07`count` versus `for_each`?P0

count creates indexed instances and works for identical items/zero-one conditions. for_each creates key-addressed instances and is safer for objects with stable identities or different attributes.

08Resource versus data source?P0

A resource is managed through lifecycle operations; a data source reads existing information. Reading an object does not make Terraform its lifecycle owner.

09When should you use `depends_on`?P1

Only for a dependency Terraform cannot infer from references. Prefer direct input/output references; excessive explicit dependencies make the graph overly conservative and obscure interfaces.

10Explain `create_before_destroy`, `prevent_destroy` and `ignore_changes`.P0

They customize lifecycle: create replacement first, guard against planned destroy, or ignore ownership of selected attributes. Each has constraints and can hide risk if used as a blanket fix.

11What is drift?P0

A difference between declared/state-known infrastructure and real infrastructure, often from manual changes or external controllers. Detect with scheduled read-only plans, decide the intended owner, then codify or revert the change.

12What does `terraform import` do?P0

It associates an existing object with a Terraform resource address in state. You still need correct maintainable configuration and must review the post-import plan.

13What is a `moved` block?P1

It declares that an object’s address changed during refactoring so Terraform can move state association instead of destroying/recreating. It is reviewable and repeatable across environments.

14CLI workspaces or separate directories?P1

Workspaces offer multiple states for one configuration, but separate roots/directories often better express different permissions, providers and blast radii. Choose based on operating model, not dogma.

15Why use provider aliases?P1

To configure multiple regions/accounts/subscriptions or variants of the same provider and pass the correct alias into resources/modules. Make the target explicit to avoid creating resources in the wrong account.

16Does `sensitive = true` keep a value out of state?P0

No. It hides value display in normal UI/output, but state can still contain it. Protect state and redesign secret handling when persistence is unacceptable.

17How do you protect provider and module versions?P1

Use tested version constraints, commit .terraform.lock.hcl for provider selections, pin remote module versions, review upgrades and test plans in lower environments. Avoid floating unreviewed dependencies.

18`taint` or `-replace`?P2

Prefer the explicit -replace=ADDRESS planning/apply option in modern workflows. It communicates the replacement within the operation; still review the impact carefully.

19What is a refresh-only plan?P1

It updates Terraform’s understanding/state to match out-of-band real changes without changing remote objects. Use it deliberately after deciding the external changes are accepted, not to hide uncontrolled drift.

20What are unknown values in a plan?P1

Values that cannot be known until apply, often because another resource must be created first. Module interfaces and for_each keys should avoid depending on values that are unknown during planning.

21What happens if apply fails halfway?P0

Successful operations are generally recorded. Fix the root cause, inspect state and real resources, then plan again. Do not delete state or manually recreate everything without evidence.

22How do you structure state boundaries?P0

By ownership, lifecycle, permissions and blast radius. Keep strongly coupled resources together, but avoid one global state that makes every change risky or exposes all sensitive state to everyone.

23How do you handle credentials for a backend/provider?P0

Use the platform’s approved environment/credential chain or workload identity, not hard-coded backend arguments or committed files. Backend config and saved plans can retain sensitive values.

24How do you test Terraform?P1

Start with fmt, validate and plan; add lint/security/policy checks, module/unit-style tests where suitable and integration tests in an isolated account/subscription. Verify real outcomes and clean up test resources.

25How would you introduce Terraform to existing manually built infrastructure?P1

Inventory and classify ownership, write configuration, import in controlled waves, reconcile plans to no unintended change, establish remote state/CI controls, then restrict manual mutation. Start with a low-risk pilot.

Ansible — 18 questions

01What makes an Ansible task idempotent?P0

Running it repeatedly converges to the same desired state and reports no change when already correct. State-aware modules, deterministic templates and truthful changed_when are central.

02What is an inventory?P0

The set of managed hosts/groups and connection variables. Keep environment boundaries clear, use dynamic inventory when sources of truth change frequently, and do not store plaintext secrets in it.

03What is a handler?P0

A task triggered by notification from changed tasks, usually a restart/reload. It normally runs once at the end of a play or when flushed, preventing unnecessary service disruption.

04Why use roles?P0

Roles create a standard reusable layout for defaults, vars, tasks, handlers, templates, files and metadata. They need documented inputs, supported platforms and tests.

05Role defaults versus role vars?P1

Defaults are low precedence and intended for callers to override. Role vars have high precedence and should be used sparingly because they make customization harder.

06What are facts?P1

Host information gathered by setup, such as OS, interfaces and memory. Use them for conditional configuration, but disable or limit gathering when not needed to improve speed.

07Template versus copy?P0

template renders Jinja variables/logic and can validate generated content; copy transfers static content or inline data. Keep templates deterministic and avoid embedding secrets into world-readable files.

08What does Ansible Vault solve?P0

It encrypts sensitive Ansible files/values at rest. You still need secure key/password delivery, access control, rotation and prevention of secret output at runtime.

09What are check and diff modes?P0

Check mode simulates supported tasks without changing targets; diff shows before/after for supporting modules. They are useful but not complete because some modules/conditionals cannot predict results.

10Why use tags?P1

To select documented subsets such as config or validation. Avoid a design where correct execution depends on remembering a complex tag combination.

11Include versus import?P1

Includes are generally dynamic at runtime; imports are statically expanded during parsing. This changes how loops, conditions and tags behave.

12What does `serial` do?P0

Limits hosts processed in each batch, enabling rolling changes and smaller blast radius. Pair it with health checks, drain/rejoin and fail-fast settings.

13What do `run_once` and `delegate_to` do?P1

run_once executes a task once for the play/batch; delegation runs it on another host, useful for migrations or load-balancer API actions. Be precise about variable context and concurrency.

14`failed_when` and `changed_when`?P0

They override interpretation of a module/command result. Use them to model the real outcome, not to hide failures or force an all-green run.

15What is `block`/`rescue`/`always`?P1

A structured error-handling group: tasks in block, recovery in rescue, and cleanup that should always execute. It supports clearer rollback and diagnostics.

16`command` versus `shell`?P0

command executes without a shell and is safer for ordinary commands. Use shell only when shell features are required; quote inputs and make idempotency explicit.

17How do you troubleshoot `UNREACHABLE`?P0

Check inventory address, DNS/route/firewall, SSH user/key/bastion, host key, Python interpreter and privilege escalation. UNREACHABLE is a connection issue, not a task-module failure.

18How would you test an Ansible role?P1

Syntax/lint, check mode where supported, run in an isolated test instance/container, verify service/config behaviour and run a second time expecting no changes. Test supported OS families.

Docker — 18 questions

01Image versus container?P0

An image is an immutable package of layers/configuration; a container is a runtime instance with a writable layer and namespaces/cgroups. Many containers can run from one image.

02How does layer caching work?P0

Each build instruction depends on previous layers and its inputs. Put stable dependency metadata/restore before frequently changing source and keep build context small.

03`CMD` versus `ENTRYPOINT`?P0

ENTRYPOINT defines the executable; CMD supplies default command/arguments. Exec-form arrays avoid an extra shell and improve signal handling. They can be combined.

04`COPY` versus `ADD`?P1

Use COPY for normal local files. ADD has extra behaviours such as archive/remote handling; use it only when those semantics are intentional and verified.

05Why multi-stage builds?P0

Separate build/test tooling from the final runtime and copy only necessary output. This reduces size and attack surface while preserving a readable build.

06Why run as non-root?P0

It reduces impact of an application compromise and aligns with restricted runtime policy. Ensure file/port permissions and writable paths are designed rather than switching back to root.

07Volume versus bind mount?P1

A managed volume is Docker-controlled persistent storage; a bind mount maps a host path and is tightly coupled to host layout/permissions. Both bypass parts of the image filesystem.

08What does `EXPOSE` do?P0

It documents the intended container port in image metadata. It does not publish the port; -p/Compose/Kubernetes networking does that.

09Why does `localhost` fail between containers?P0

Each container has its own network namespace, so localhost refers to itself. Use the other service’s DNS name and container port on a shared network.

10How do you debug an exiting container?P0

Inspect status/exit code and logs, command/entrypoint, config/secrets, permissions, architecture and OOM. The container exits when PID 1 exits.

11How do you reduce image size?P1

Multi-stage build, smaller trusted base, .dockerignore, copy only runtime files, clean package caches and remove build/test dependencies. Check docker history rather than guessing.

12How do you handle build secrets?P0

Use an approved build-secret mechanism or dependency proxy so secrets are not stored in ARG, ENV, layers, history or context. Rotate any secret that entered an image.

13Why avoid `latest`?P0

It is mutable and does not identify what was deployed. Use build ID/commit/release tags and promote by immutable digest when possible.

14What is a container health check?P1

A command the runtime executes to assess health. It should be fast and meaningful. In Kubernetes, use startup/readiness/liveness probes for orchestrator behaviour.

15What happens when the root filesystem is read-only?P1

The process can write only to mounted writable paths. Identify required locations such as /tmp or uploads and provide controlled volumes; fix applications that write unpredictably.

16Why can a container ignore SIGTERM?P1

Shell-form entrypoint or a wrapper may be PID 1 and not forward signals, or the app lacks a graceful handler. Use exec form/init where needed and test termination.

17How do you inspect image vulnerabilities?P1

Use the organization’s approved scanner against the final image and dependencies, triage exploitability/severity, rebuild on patched bases, track exceptions and avoid treating a scan as the only control.

18Compose versus Kubernetes?P2

Compose is excellent for local or simpler multi-container orchestration. Kubernetes adds cluster scheduling, reconciliation, service discovery, rollout, policy and ecosystem at greater operational complexity.

Kubernetes — 30 questions

01What is a Pod?P0

The smallest schedulable unit: one or more tightly coupled containers sharing network and selected storage. Pods are ephemeral and normally managed by a controller.

02Deployment versus ReplicaSet?P0

A ReplicaSet maintains a replica count. A Deployment manages ReplicaSets to provide declarative rollout and rollback for stateless workloads.

03Deployment versus StatefulSet?P0

Deployment suits interchangeable stateless replicas. StatefulSet provides stable ordinal identity, ordered operations and volume claim patterns for stateful applications.

04When use a DaemonSet?P1

For one Pod on every or selected node, such as log, network, monitoring or security agents. Tolerations and update strategy matter.

05Service types?P0

ClusterIP is internal virtual access, NodePort exposes on node ports, LoadBalancer requests external load balancing, and ExternalName maps DNS. Platform behaviour varies.

06What does an Ingress do?P0

Defines HTTP(S) routing to Services, but requires an Ingress controller. Modern environments may also use Gateway API. TLS/routing features depend on the implementation.

07ConfigMap versus Secret?P0

Both provide configuration data; Secret is intended for sensitive values but still requires RBAC, encryption/external store and careful delivery. Never commit real secret literals.

08Requests versus limits?P0

Requests guide scheduling and reserved capacity; limits cap usage. CPU over limit is throttled; memory over limit can lead to OOM termination. Set from observed/tested needs.

09Readiness versus liveness versus startup probe?P0

Readiness controls traffic, liveness triggers restart, and startup protects slow initialization by delaying the other probes until startup succeeds.

10What causes `CrashLoopBackOff`?P0

Repeated container exit or failed liveness. Use describe, current/previous logs and last state; check command, config, dependency, permissions, probes, architecture and memory.

11What causes `ImagePullBackOff`?P0

Wrong image/tag, authorization, pull secret/identity, DNS/network/TLS, rate limit or platform architecture. Pod events usually show the category.

12What causes a Pod to remain Pending?P0

Insufficient requested resources, taints/affinity, quota, unbound storage, zone constraints, host port or autoscaler limitations. Read scheduler events.

13How do you diagnose OOMKilled?P0

Check last termination reason/exit code, metrics and node pressure. Determine leak versus workload, tune app/runtime and request/limit, load test and alert.

14How does Service discovery work?P1

Cluster DNS resolves Service names and the Service routes to ready endpoints selected by labels. Namespace-qualified names are needed across namespaces.

15Why might a Service have no endpoints?P0

Selector does not match Pod labels, selected Pods are not Ready, wrong namespace or controller issue. Inspect labels and EndpointSlice/endpoints.

16What is a rolling update?P0

A Deployment gradually creates a new ReplicaSet and scales down the old according to surge/unavailable settings. Readiness and capacity determine safety.

17How do you roll back?P0

kubectl rollout history and rollout undo or the declarative delivery system can restore a prior template. Verify the exact digest and user health; data changes may not roll back.

18What does HPA need?P0

A metrics source, sensible resource requests for utilization targets, scalable dependencies and min/max/behaviour settings. HPA is not instantaneous and should be load tested.

19What does a PDB guarantee?P0

It limits voluntary disruptions so enough selected Pods remain available. It does not prevent application crashes, involuntary node loss or poor topology.

20Affinity versus taints/tolerations?P1

Affinity selects/avoids placement based on labels/topology. Taints repel Pods and tolerations permit scheduling onto tainted nodes; they do not force placement.

21What is RBAC?P0

Roles/ClusterRoles define allowed API actions; bindings grant them to users/groups/service accounts. Scope namespace and verbs/resources, avoid broad cluster-admin.

22Why use a dedicated ServiceAccount?P0

It gives the workload a distinct Kubernetes identity for least-privilege API/cloud access and audit. Disable token automount when the Pod does not need the API token.

23What is a NetworkPolicy?P0

A declaration of allowed ingress/egress between selected Pods/namespaces/IPs/ports. It works only when the network implementation enforces it; include DNS/dependencies deliberately.

24PV, PVC and StorageClass?P1

PV represents storage, PVC is a workload claim, and StorageClass describes provisioning/parameters. Understand access mode, reclaim policy, zone and backup/restore.

25How do labels and selectors fail?P0

A mismatched immutable Deployment selector, Service selector or template label can create no endpoints or adoption errors. Keep a stable label schema and validate manifests.

26How do you achieve high availability?P0

Multiple ready replicas across fault domains, capacity for failures, resilient dependencies/storage, PDB/topology, safe updates and tested recovery. Replica count alone is insufficient.

27What happens during Pod termination?P1

The Pod becomes terminating, endpoint removal/draining occurs, preStop may run, SIGTERM is sent and grace period elapses before SIGKILL. Apps must stop accepting and finish work safely.

28How do you debug without a shell in the image?P1

Use logs/events/inspect, port-forward or a sanctioned ephemeral debug container/image, observability and application endpoints. Do not bloat production images merely for ad hoc debugging.

29What is etcd and why protect it?P1

It stores Kubernetes cluster state. Protect access, encryption, backup/restore and version-compatible recovery; compromise can expose secrets and control.

30AKS/EKS managed means what is still yours?P1

Workload, identity, network, nodes/serverless profiles, add-ons, upgrades, policy, observability, data protection, cost and incident response remain shared/customer responsibilities.

Linux, networking and Git — 20 questions

01How do you investigate high CPU?P0

Confirm host/container scope and time, inspect top processes/threads, correlate load and traffic/deployment, profile the application and check throttling. Do not kill first without impact and evidence.

02How do you investigate high memory?P0

Check available memory, swap, cgroup/container limits, process RSS and OOM logs. Distinguish leak, cache and legitimate working set; correlate over time.

03Disk is full after deleting a large log — why?P0

A process may still hold the unlinked file open. lsof +L1 can show it; safely reopen/restart the process. Also check inode exhaustion.

04What is load average?P1

Average runnable/uninterruptible tasks over intervals. Interpret against CPU count and inspect CPU versus I/O wait rather than equating load directly to CPU percent.

05How do you find what listens on a port?P0

ss -lntup or platform equivalent, then map PID/process and service. In containers/namespaces, run in the correct namespace.

06How do you debug DNS?P0

Check resolver configuration, getent/dig result, search domains, expected record, cache/TTL, network path to resolver and compare from the affected namespace.

07Connection refused versus timeout?P1

Refused normally means the route reached a host but nothing accepted or a reject occurred; timeout suggests dropped traffic, route, firewall or unresponsive target. Verify rather than assuming.

08What does `set -Eeuo pipefail` do?P0

Stops on many unhandled errors, errors on unset variables, propagates pipeline failure and improves error-trap inheritance. Expected non-zero commands need explicit handling.

09How do file permissions work?P1

Owner/group/other read-write-execute bits plus special bits and ACLs. Directory execute controls traversal. Explain octal rather than memorizing recipes.

10SIGTERM versus SIGKILL?P0

TERM allows graceful handling; KILL cannot be caught. Prefer bounded graceful stop, then force only when necessary and account for data consistency.

11Merge versus rebase?P0

Merge creates a commit preserving topology; rebase rewrites commits onto another base for linear history. Avoid rebasing shared published history without policy.

12Reset versus revert?P0

Reset moves references and can rewrite history; revert adds a commit that reverses changes and is usually safer for protected shared branches.

13When use cherry-pick?P1

To apply selected commits to another line, often a hotfix. Test conflicts and ensure the fix is propagated to all maintained branches to avoid divergence.

14What is `git reflog` useful for?P1

It records local reference movements and can recover commits after reset/rebase/checkout while objects remain. It is local and not a team backup.

15What is a detached HEAD?P1

HEAD points directly to a commit instead of a branch. Create a branch before moving away if you need to retain new commits.

16How do you resolve a merge conflict?P0

Understand intent on both sides, edit deliberately, run tests, stage resolved files and continue. Avoid mechanically choosing all ours/theirs.

17HTTP 502, 503 and 504?P1

Commonly bad upstream response, unavailable service/capacity, and upstream timeout respectively, but identify which proxy generated the code and inspect the full path.

18How do you inspect a TLS endpoint?P1

Use openssl s_client with SNI and curl -v; check hostname/SAN, expiry, chain, issuer, protocol/cipher, listener and client trust/clock.

19What is an exit code?P0

Process status where zero conventionally means success and non-zero categories indicate failure. Pipelines depend on it; scripts must not mask failing commands.

20How do you make a script safe for automation?P0

Validate inputs, quote variables, use bounded timeouts/retries, meaningful logs and exit codes, cleanup traps, least privilege, no secret output and idempotent/reversible behaviour.

Cloud, observability and security — 22 questions

01What makes a subnet public?P0

Its route/addressing and gateway path permit public internet connectivity; the name alone does not. Instances also need appropriate public address and security controls.

02Security group versus network ACL?P0

In AWS, security groups are stateful resource/interface controls; NACLs are stateless subnet controls with explicit return-path implications.

03IAM user versus role?P0

A role is assumed for temporary credentials and is preferred for workloads/cross-account access. Minimize long-lived user access keys and enforce least privilege.

04How do you design multi-AZ availability?P0

Spread load-balanced compute and dependencies, retain capacity after a zone loss, use compatible storage/data replication, and test failover. Remove hidden single-AZ components.

05What is autoscaling based on?P1

A demand/capacity signal with min/max, warm-up and dependency limits. CPU alone may be wrong for queues, latency or I/O-bound services; test scale-out and scale-in.

06RTO versus RPO?P0

RTO is target restore time; RPO is tolerated data-loss window. Backup, replication, runbooks and exercises must support both.

07SLI, SLO and SLA?P0

SLI is a measured service indicator, SLO is an internal target, and SLA is a formal external commitment. Alerts should reflect user-impacting burn/action.

08Logs versus metrics versus traces?P0

Metrics show trends/aggregate health, logs show events/context, and traces show distributed request path/timing. Correlate with deployment and trace IDs.

09What makes an alert good?P1

It signals meaningful current/near-term impact, is actionable, has owner/severity/runbook, avoids duplication/noise and is tested. Page on symptoms or fast burn, ticket slower risks.

10Blue-green versus canary?P0

Blue-green switches between full environments for fast isolation/rollback at higher cost. Canary shifts a small traffic portion and needs strong metrics/traffic control.

11How do you perform zero-downtime database changes?P0

Use expand/migrate/contract with backward-compatible schema/code, online techniques where supported, backup, validation and feature flags. Do not deploy a breaking schema and hope rollback works.

12What is least privilege?P0

Grant only required actions/resources/conditions for the necessary duration, then review use. It applies to humans, pipelines, workloads and network access.

13How should secrets rotate?P1

Use a secret manager and dual/overlapping credential or dynamic-secret pattern when possible, update consumers safely, verify, revoke old secret and audit. Avoid coordinated manual edits everywhere.

14What is an SBOM?P1

A software bill of materials inventories components/dependencies for vulnerability and supply-chain response. It does not by itself prove security or licensing compliance.

15What is image signing/provenance?P1

Evidence tying an artifact to an identity/build process and integrity. Enforce trusted sources/digests with policy where required; protect signing identity.

16How do you respond to a critical vulnerability?P0

Validate applicability/exposure, contain if needed, patch/rebuild from trusted sources, test and deploy by risk priority, monitor exploitation and document any time-bound exception.

17How do you reduce cloud cost safely?P1

Measure, rightsize, autoscale, stop idle non-prod, apply storage/retention lifecycle, use commitments for predictable demand, tag/allocate cost and preserve required resilience/security.

18What is a runbook?P1

An executable operational procedure with trigger, prerequisites, commands/decision points, safety/rollback, verification, escalation and owner. Test and update it after use.

19What should a post-incident review contain?P1

Impact/timeline, contributing conditions/root cause, detection/response analysis and owned dated corrective actions. Keep it blameless and verify actions actually reduce risk.

20How do you handle production access?P0

Federated identity/MFA, role-based just-in-time access, approval where required, minimal rights, session/audit logs, break-glass control and regular review. Avoid shared accounts.

21Why is a backup not enough?P1

It may be corrupt, incomplete, inaccessible or too slow. Test restores against RTO/RPO and application consistency, secure backup access and monitor failures.

22How would you explain a technical risk to a client?P1

State impact and likelihood in business language, evidence/assumptions, options with cost/time/trade-offs, recommendation, owner and decision deadline. Avoid hiding uncertainty.

Prepare six reusable true stories

Each story should be two to three minutes and contain numbers. One story can answer several questions when the emphasis changes.

Story Evidence to include

STAR structure without sounding memorized

  • Situation: two sentences — system, business context and pressure.
  • Task: your responsibility and success criterion.
  • Action: most of the answer; decisions and actions you personally took.
  • Result: measurable outcome, residual trade-off and learning.

High-probability questions with answer blueprints

“Tell me about a severe production incident.”

Use: impact and timeline → immediate containment → evidence and isolation → stakeholder updates → root cause → corrective actions. State what you would do differently. Avoid blaming a developer or saying “we restarted and it worked.”

“Tell me about an automation you implemented.”

Use: manual process and failure rate → requirements → design (pipeline/IaC/Ansible) → rollout and stakeholder adoption → security/rollback → measured result. Mention ongoing ownership and documentation.

“A developer wants to bypass checks for an urgent release. What do you do?”

Acknowledge urgency, quantify impact, offer the approved emergency path with a minimum non-negotiable validation set, higher visibility/approval, immutable artifact and rollback, then complete retrospective validation and corrective action. Do not answer with either “always no” or “just allow it.”

“How do you handle a customer who asks for an unrealistic timeline?”

Clarify outcome and deadline driver, decompose scope, identify dependencies/risks, provide options (minimum safe scope, phased delivery, added resources where useful), document assumptions and obtain a decision. Never hide quality/security work to make a date appear possible.

“Tell me about a disagreement on architecture.”

Explain criteria (availability, security, skills, cost, migration, operations), gather evidence or run a small experiment, invite affected owners, document the decision and commit to the chosen direction even if it was not your first choice.

“How do you prioritize several incidents?”

User/business impact, safety/security/data integrity, blast radius, urgency/SLO, recoverability and dependencies. Establish owners/channels, avoid one person context-switching across everything and communicate priority changes.

“Why are you changing jobs?”

Keep it forward-looking: broader ownership, architecture/customer exposure, complex automation and growth. Do not criticize a manager or reveal confidential details.

“Why this role?”

Tie only to the supplied JD: hands-on Azure DevOps, Terraform, Ansible, containers/Kubernetes, cloud, troubleshooting and the opportunity to combine delivery with solution consulting in regulated engineering contexts. Then give one example showing readiness.

Consulting-style requirement questions to ask before designing

  • What business event starts a release, and how often is release needed?
  • What downtime, data loss and recovery targets are accepted?
  • Which environments/accounts/subscriptions and networks already exist?
  • What is regulated/sensitive, and what evidence must be retained?
  • Who owns source, pipeline, platform, application, security, quality and production approval?
  • Which tools are mandated, licensed or prohibited?
  • What are current failure points and baseline metrics?
  • What migration constraints and rollback windows exist?

Final 24-hour revision sheet

The twelve sentences to be able to say cleanly

  1. A stage contains jobs; a job runs on an agent; steps run sequentially inside the job.
  2. Build once, test/scan once, and promote the same immutable artifact or image digest.
  3. Azure DevOps production approval/checks belong on protected resources such as the environment, with restricted ownership.
  4. Terraform state maps configuration addresses to real objects; remote state and supported locking are essential for a team.
  5. Never force-unlock until no legitimate writer remains; then plan and inspect for partial changes.
  6. Ansible idempotency means the second run makes no change when the target is already correct; handlers run only after notified changes.
  7. Multi-stage Docker builds keep compilers and source out of the runtime; run as non-root and avoid mutable tags.
  8. Kubernetes readiness controls traffic, liveness restarts, and startup protects slow initialization.
  9. Requests drive scheduling/capacity; limits constrain use; memory limit breach may produce OOM termination.
  10. For a Kubernetes failure, inspect events, describe, current/previous logs, resources/config and the previous revision before changing the system.
  11. Secrets belong in an approved secret manager or protected identity flow, never source, image, CLI arguments or logs.
  12. A rollback is not complete until user-facing health is verified; database/data changes may require forward fix or restore.

Top red flags to avoid

  • Writing a secret, subscription key, access key or password on the board.
  • Using latest, rebuilding separately in production or not knowing what image is deployed.
  • Saying terraform state rm/delete state as the first answer.
  • Using force-unlock without checking active writers.
  • Making every Ansible task shell and every run changed.
  • Running containers/root Pods as root “to fix permissions.”
  • Omitting readiness and resources from a Kubernetes answer.
  • Treating Running Pod or systemd service as proof of business health.
  • Random restarts before collecting logs/events/metrics.
  • Claiming a tool automatically creates compliance or high availability.
  • Blaming another team or revealing client-confidential details.
  • Giving a five-minute definition when the interviewer asked for one command or design decision.
