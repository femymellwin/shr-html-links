01
First 5 minutes

What the interviewer really wants

This is not a generic cloud-server migration. The source is already GitHub Enterprise Cloud; the target is a new approved GitHub Enterprise Cloud organization. The engineering challenge is preserving useful history while rebuilding access, integrations, security and working pipelines.

Preserve

Repository code, commits, branches, PRs, issues, and supported historical metadata.

Rebuild

Team membership, rulesets, runtime configuration, secrets, runners, webhook integrations and pipeline dependencies.

Prove

Builds, tests, deployment approvals, users, audit readiness and rollback path all work after cutover.

Most important line to remember: “A repository migration is only successful when the code, history, permissions, pipelines, integrations, and business validation all work in the destination.”

Five points she should repeat naturally

  1. Discover what exists and who owns it.
  2. Choose the correct migration method based on whether moving repositories into pre-created orgs or entire orgs between enterprises.
  3. Map identities and licenses: old contributions can remain even if employees have left; do not invite historical authors just to preserve history.
  4. Rebuild CI/CD and security: workflow files alone do not create working secrets, runners or AWS access.
  5. Validate and cut over with explicit no-go conditions and a realistic rollback.
Source accuracy: The resume describes Azure DevOps → GitHub migration workstreams but contains [CONFIRM COUNT] and [CONFIRM ROLE] placeholders. Do not claim exact migrated-repo totals, ownership of GHEC-to-GHEC migrations, or unverified ServiceNow experience.

Concept

Brownfield → greenfield in one picture

Existing GHEC orgCode + 8 years of PRs, users, workflows, bots, policies, secrets, integrations
→
Assess & exportInventory, approvals, GEI trial, data integrity and dependency mapping
→
Approved new GHEC orgMigrated data + new teams, policies, credentials, runners, pipelines
→
Production-readyPassing CI/CD, security checks, business sign-off, monitored operations

Brownfield means

Existing enterprise accounts with years of configuration, legacy integrations, historical authors, naming inconsistencies and unknown dependencies.

Problem: not everything is documented or still owned.

Greenfield means

New approved organizations with current naming, team architecture, least-privilege access, security policies and standard pipeline patterns.

Opportunity: clean up technical debt rather than blindly copy it.

Important distinction: Moving a repository into an already-created destination organization is a repository migration. An organization migration with GEI creates a new destination organization. Confirm which model Project Citadel uses; never assume they are interchangeable.

A small example

The old organization legacy-payments has billing-api, web-portal, 900 closed PRs, a Jenkins webhook, and 15 former employees in history. The destination modern-platform must preserve supported PR history while providing fresh teams, rulesets, pipeline permissions and AWS deployment trust. The former employees do not need to be given access for their historical discussions to remain visible.

1

Discovery and assessment

Collect repository inventory, active/archived status, owners, PRs/issues, large files, Git LFS, workflows, external apps, runner labels, identity and teams. Capture how releases happen today.

2

Target design and approval

Agree org names, member model, SSO/SCIM or managed users, rulesets, runner groups, central reusable workflows, Artifactory endpoints and cloud access. Confirm license and contract ownership.

3

Proof of concept

Choose one representative repo with history, PRs and Actions. Test GEI, identity attribution, workflow parity, runner connectivity and approval gates. Record exceptions.

4

Wave preparation and execution

Obtain change approval; notify owners; enforce write freeze; run approved migration; review logs. GEI does not perform delta migration, so writes made after export start may require manual reconciliation.

5

Post-migration engineering

Rebuild unsupported configuration; reauthorize apps; restore secrets from a vault; configure policies; test code checkout, PR checks, build, artifact publishing, AWS auth and deployment approvals.

6

Business sign-off and closure

Owner confirms expected history and function. Document exceptions, archive source only after approved cutover, update runbooks and hand over on-call ownership.

Three things to decide before any cutover

  1. Freeze: When will source pushes, PR comments, and merges stop?
  2. Go/no-go: Which objective results let you move forward or require rollback?
  3. Ownership: Who makes the final decision, who executes and who validates?

Correct migration tool

GEI, Git mirror, transfer: what to choose?

MethodWhat it doesBest fit / limitation
GitHub Enterprise Importer (GEI)Migrates Git and supported repository metadata (PRs, issues, comments etc.)Main candidate when high-fidelity GHEC-to-GHEC migration is required. Review unsupported data.

Practical procedure: (1) obtain assigned migrator roles, (2) coordinate required classic PATs for source and destination and any SAML authorization, (3) verify IP allow lists and rulesets, (4) perform a POC, (5) collect migration logs, (6) remediate exceptions, (7) validate owner acceptance.

Do not confuse token policies: The GEI migration path currently requires classic PATs, not fine-grained PATs. The JD's fine-grained PAT/GitHub App preference applies to appropriate ongoing automation and integrations. Obtain an approved time-bound exception or escalated migration method if classic PATs are blocked.
Ruleset trap: Enterprise or org rulesets can time out GEI's bulk ref pushes. GitHub documents a scoped Repository migrations → Exempt bypass for that situation, subject to approval. Do not broadly disable protections for normal users.

Official references: GEI repository migration guide; GEI access requirements; Ruleset bypass.

The interview differentiator

Employees who left, old comments and historical contributions

Many teams misunderstand this: preserving historical contributions is not the same as re-creating user access. Migration engineers must treat historical identity, live access and paid licensing as three different topics.

Original PR by AlexAlex left company in 2022
→
GEI migrates supported PRComments and review activity represented by mannequin
→
Target repoHistory visible; Alex need not be member
→
Access decisionOnly current approved people are granted membership

Understand four different identity scenarios

Person / identityHistorical recordCorrect migration decision
Current employee who must work in new orgCommits, PRs, comments and reviewsProvision approved org/team access; optionally reclaim mannequin to map PR/issue activity.
Former employeeOld comments and PR reviews remain part of project record when supportedDo not invite or rehire a user account to preserve history. Keep mannequin unclaimed unless a legitimate mapping is approved.
Employee renamed / changed GitHub identityMay appear as mannequin until reclaimedVerify identity mapping via HR/IdP and GitHub owner; reclaim to actual current member.
Bot, service account or deleted accountAutomation activity can appear in historySeparate historic bot attribution from current production GitHub App/bot installation and license review.

Mannequins (PR / issue activity)

GEI represents migrated non-Git user actions as mannequin placeholder identities. An organization owner can reclaim them to an existing organization member, subject to attribution process. This does not automatically give repository access.

Git commit authorship (separate)

Commits retain Git author metadata and are linked to GitHub accounts primarily by commit email. Reclaiming a mannequin does not rewrite commit authorship. Enterprise Managed Users (EMU) have stricter email-matching limitations.

Important surprises she should mention

  • Preserved is not identical: some review threads/comments can generate warnings or be represented differently. Read migration logs; validate specific high-value records.
  • Mentions may not resolve: historical @old-org/team, old issue URLs and user mentions may remain literal and point to the old place.
  • Do not map the wrong people: never reclaim a former person's activity to a current colleague merely to remove the mannequin.
  • Team membership is separate: organization migration can migrate team structures, but not team membership; repo migration requires target access configuration.
  • Privacy and retention: confirm policy for comments containing confidential information and preservation of source as audit evidence.

Cost and compliance

Licensing: who actually consumes a seat?

Licensing is driven mainly by current access and the enterprise's billing model, not by how many historical commits, PRs or comments a person authored.

Usually license-consuming

  • Current organization members (including owners).
  • Outside collaborators on private/internal repos, under applicable account model.
  • Dormant users who remain members.
  • Some pending invitations depending on EMU, billing type and invitation type.

Do not confuse with a seat

  • Historical commit author with no active access.
  • Former employee's preserved PR/comment mannequin.
  • Repository or commit count.
  • Suspended Enterprise Managed User account (subject to billing-cycle timing).

Worked illustration (not an invoice)

PopulationPeopleWould they require a seat in target?
Current approved engineering members50Generally yes: 50 unique active members.
External collaborators with access to private/internal repos8Generally yes: 8 unique accounts unless already counted in same enterprise.
Former employees whose activity remains in PRs30No seat solely because of historical attribution, provided they are not granted billable access.
Bot names appearing in old comments6Historical names alone do not determine seat consumption; audit actual account memberships and App choices.
Illustrative active requirement58Assumes all 58 are distinct, billable in target and no other license offsets or special terms.
Same vs separate enterprise: Access to multiple organizations inside the same enterprise is not automatically a new seat per organization for the same licensed person. Source and destination in different enterprises can have separate entitlements or subscription arrangements. Ask the licensing/billing team to reconcile both license reports and contract terms.

Cost and compliance questions to ask the admin

  1. Are the old and new organizations in the same enterprise or separate enterprises/contracts?
  2. Is the new enterprise standard personal-account/SAML or Enterprise Managed Users (EMU)?
  3. Is billing volume/subscription-based or usage-based? How are pending invites counted?
  4. How many active members, dormant users, outside collaborators and automation accounts exist?
  5. Are retired accounts deprovisioned from access but retained as historical attribution?
  6. Do we need to account for GitHub Actions usage, storage, LFS, security subscriptions, Copilot, runners or additional usage separately?
  7. Has the enterprise billing manager exported a pre- and post-migration license report?
Billing nuance: Under some usage-based terms, a user who consumed a seat earlier in the current billing cycle can remain billable for that cycle after removal. Pending invitations also have billing nuances. Never promise immediate savings without checking the plan.

Simple answer to the interviewer

“I separate historical users from active access. PR comments by ex-employees can remain under mannequins and do not by themselves need enterprise licenses. The cost review is based on current members, applicable collaborators, dormant accounts and invitation/billing rules. I would compare enterprise license exports before and after each wave, and never give a former employee access just to preserve history.”

Conceptual GitHub Actions YAML (illustrative, not production-ready)

name: Validate and Deploy
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Unit tests
        run: ./scripts/test.sh

  deploy:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write   # Request GitHub OIDC token
    steps:
      - uses: actions/checkout@v4
      - name: Get short-lived AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.DEPLOY_ROLE_ARN }}
          aws-region: us-east-1
      - name: Run approved deployment
        run: ./scripts/deploy.sh

Example only: scripts and AWS role are placeholders, environment reviewers must be created separately, and production workflows should use organization-approved/pinned action versions or full commit SHAs, hardened trust, proper gating and a deploy strategy matching the application.

Reusable workflow and approval concepts

  • Reusable workflow: common YAML callable from multiple repositories; confirm cross-org access and referenced actions.
  • Environment: protected deployment target, e.g. staging or production; can enforce approvals and branch restrictions.
  • Secrets: sensitive values stored securely; not migrated by GEI. Do not print them in logs or put them in repo history.
  • Variables: non-secret configuration like region or registry hostname; recreate with correct scope.
  • Status check: rule may rely on exact workflow/job name; a rename can block PR merges even when CI passes.

Where pipelines execute

GitHub-hosted and self-hosted runners

GitHub-hosted runner

GitHub provides the job execution machine. Simpler operations and fresh hosted environment, but network access, hosted image availability, billing and private-resource connectivity must be designed.

Failure example: job works on old private runner but cannot reach internal Artifactory from hosted runner.

Self-hosted runner

Your company operates the runner VM/container. Useful for internal connectivity and custom tools, but requires lifecycle management, network allow lists, isolation, patching, permissions, scaling and secure cleanup.

Failure example: labels or runner group do not permit jobs from the greenfield org.

Runner troubleshooting sequence

  1. Is the runner online and idle? If queued, check labels, group permissions and target repo eligibility.
  2. Can runner make outbound HTTPS connections to required GitHub endpoints? Check proxy, DNS, TLS inspection and firewall.
  3. Can it resolve and connect to Artifactory/approved URLs, registry and AWS services?
  4. Does it have the right tools, images, architecture, certificates and storage?
  5. Can it authenticate securely using approved short-lived credentials and scopes?
  6. Inspect job logs and runner diagnostic logs. Correlate time, commit, workflow run ID and any service outage.
Security principle: Do not run untrusted pull-request code on broadly privileged persistent self-hosted runners with production network access. Prefer well-isolated, ephemeral runners and minimize secrets and network privileges.

Example triage: “Build passed, publishing failed”

  1. Confirm artifact upload step error, run ID and exact target registry URL.
  2. Check runner network: DNS, proxy, TLS certificate, outbound connectivity.
  3. Verify repository path, existing service account, token expiry and minimal publish permission.
  4. Confirm new org/repo is approved by Artifactory if credentials are bound to project or app identity.
  5. Run a controlled test, record evidence and update the incident/change ticket.

Production safety

Migration waves, cutover and rollback

Good wave sequencing

Wave 0Pilot: low-risk representative repo
→
Wave 1Shared libraries and reusable workflows
→
Wave 2Lower-criticality applications
→
Wave 3Business-critical services

This is an illustrative order only. Actual waves follow dependency mapping; some shared workflows may need to be established ahead of application migration without cutting consumers over yet.

Before cutover

  • Approve ServiceNow change, impact, bridge call and timing.
  • Validate target org setup and license capacity.
  • Back up/retain source state and historical evidence.
  • Freeze merges, comments and pushes as required.
  • Agree source status, final writer and rollback deadline.
  • Confirm named owners and clear go/no-go conditions.

After cutover

  • Check GEI status and warnings.
  • Compare refs, sample historical PRs and issues.
  • Recreate secure configuration and approvals.
  • Run CI, artifact publish, release and deploy smoke tests.
  • Ask owner to test and approve.
  • Update remote URLs, documentation, webhooks and integrations.

Rollback is not just “undo migration”

If the source is preserved and writable again, redirect contributors and integrations back to the source. However, new commits, issues, PRs or releases created in the target after cutover can diverge from the source. Plan a reconciliation decision; simply reversing DNS/remote URLs can cause missing work.

No delta import: GEI does not automatically migrate changes made during the production migration after the relevant export point. Treat source write-freeze and target write discipline as fundamental to data integrity.

Practice aloud

Likely interview questions with simple answers

Open each answer, read it twice, then close it and explain it using your own words. A good answer has approach + why + validation.

Q1. What is brownfield to greenfield migration?
Moving existing GitHub repositories and selected history/configuration from established organizations into newly approved organizations. It's not only moving Git data; the new organization needs access, security policies, pipelines, integrations and evidence that applications work.
Q2. How do you start a GHEC-to-GHEC migration?
Discover repositories, owners and dependencies; confirm source/destination enterprise model; select repository vs organization GEI migration; get approved roles and tokens; pilot a representative repository; define waves, freeze, rollback and acceptance gates.
Q3. Why not just git clone --mirror?
A Git mirror preserves Git refs and history but not GitHub-specific issues, PR discussions, reviewers and configuration. For high-fidelity enterprise movement, GEI is the main migration option to assess.
Q4. Does GEI migrate PR comments and reviews?
Supported pull requests, issues, comments and user activity can migrate. But specific review threads, historical links or comments can have migration warnings and fidelity limitations. Sample-check important PRs and read every warning, rather than assuming every record is perfect.
Q5. What happens to someone who left the company?
Their historical non-Git activity can remain represented by a mannequin. They do not need to be invited into the new enterprise. Reclaim mannequins only to eligible current organization members, after identity verification and approval.
Q6. Does an ex-employee's PR/comment history consume a license?
No, historical activity by itself does not create an active licensed seat. Billing primarily depends on current organization membership, applicable private/internal collaborators, dormant accounts and some pending invitation rules. Check the actual enterprise and billing cycle.
Q7. What is the difference between commit authors and mannequins?
Git commits retain author email information and are linked to GitHub identities through email matching; mannequin reclamation concerns migrated non-Git actions like PRs and comments. Reclaiming a mannequin does not reassign Git commit authorship.
Q8. What doesn't GEI migrate?
Important gaps include Actions secrets/variables/environments/runners/run history, GitHub Apps, rulesets, team/user access for repository migrations, Packages, Git LFS objects, code scanning results and some comment links/metadata. Always use the current support matrix for the specific source.
Q9. Are GitHub Actions workflows migrated?
The workflow YAML stored in the repository can migrate, but execution dependencies usually require work: runner registration, environment approvals, secrets, variables, external actions, Artifactory and cloud trust. I validate a real build and deployment.
Q10. Can you use fine-grained PATs for GEI?
Current GitHub docs require classic PATs for the GEI migration, with specified scopes and source/destination roles. Fine-grained PATs and GitHub Apps can be appropriate for other automation; use a security-approved exception or process for migration.
Q11. What is a mannequin and when do you reclaim one?
A mannequin is a placeholder representing migrated user activity other than Git commits. Reclaim only after confirming the identity maps to an eligible existing member and receiving approval; former employees can remain unclaimed.
Q12. How do you manage licensing?
Export active members, outside collaborators, dormant users and pending invitations. Compare source and target enterprises and subscription types. Avoid treating historical contributors as seats, and ask billing to reconcile unique active entitlements and cycle rules.
Q13. Why are team permissions challenging?
Users, teams and repo access are not all preserved automatically, and org migrations do not preserve team membership. Create target access from the approved IdP/ownership model and verify every critical repository and CODEOWNER.
Q14. How do you plan migration waves?
Group repositories by dependencies and criticality, start with POC and lower-risk services, schedule shared workflow dependencies appropriately, use approved cutover windows, assign owners and require post-wave validation before advancing.
Q15. How do you handle no-delta migration?
Use a coordinated source write freeze, communicated cutover point and current source snapshot. GEI does not automatically pick up later changes; if source remains writable, those later commits/comments require manual reconciliation and change control.
Q16. What is rollback for a GitHub repo migration?
Keep the approved source as the fallback, redirect users/integrations back if necessary, and reconcile any content added to the target. Define rollback triggers, decision owner, time window and evidence before cutover.
Q17. Why would a migrated workflow fail with 403?
Possible missing token scope, GitHub App installation, restricted GITHUB_TOKEN permissions, Artifactory service identity, AWS role trust or org policy. Read the exact failing step and separate platform permission problems from external service authorization.
Q18. How do you troubleshoot a runner stuck in queued state?
Check runner health, runner group eligibility, labels, capacity, GitHub endpoint reachability and assignment restrictions. Then review runner diagnostics and the workflow's runs-on expression.
Q19. How do you secure an AWS deployment pipeline?
Use GitHub OIDC and an AWS role scoped to an approved repository/environment, restrict GITHUB_TOKEN permissions, protect deployment environments, avoid long-lived AWS keys, limit runner access and validate the role trust after org migration.
Q20. How do you handle CODEOWNERS after migration?
Check the file path and team references, create/authorize corresponding target teams, configure required reviews, and submit a test PR to confirm the intended people are requested and the rule blocks unauthorized merges.
Q21. A P1 pipeline incident occurs after cutover. What do you do?
Confirm impact and open/participate in the incident bridge, communicate business effect, preserve logs and run IDs, stabilize service using approved mitigation or rollback, engage owners, provide updates and document RCA with preventive tasks.
Q22. How do you prove migration was successful?
Produce Git ref/commit validation, sampled PR/issues evidence, verified access/policies, clean pipeline runs, artifact publish, deployment smoke test, security checks, open exception list and repository-owner approval.
Q23. What will you do if the owner of a repository has left?
Escalate to the designated business/system owner and org admin; don't guess ownership. Mark it blocked until responsibility and retention decisions are approved. Separate that decision from preserving the departed person's historical activity.
Q24. Why do you want this role if your background is mostly Azure/OCI?
My strongest experience is engineering and running enterprise CI/CD platforms with GitHub Actions, Terraform, security controls and production change processes. Those skills transfer directly to the migration's target-state engineering and troubleshooting. I'm strengthening my GHEC-to-GHEC importer and AWS OIDC knowledge through focused labs.
