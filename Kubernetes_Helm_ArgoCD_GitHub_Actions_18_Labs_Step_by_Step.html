How to use this lab book

Use a local Kubernetes cluster first. A managed cloud cluster is useful later, but it adds IAM, networking, billing, and provider-specific concepts before the Kubernetes fundamentals are stable.

1
Predict

Before each command, say what resource or state you expect to change.

2
Observe

Use get, describe, logs, events, Helm history, and Argo CD status.

3
Break it

Use a bad image, wrong port, bad value, or manual drift. Troubleshooting is part of the lab.

4
Explain back

Do not mark a lab complete until you can explain the control flow without reading the steps.

Recommended environment: Docker + minikube + kubectl + Git + GitHub account. The Docker driver keeps the first cluster setup simple. Helm is installed only when the curriculum reaches Helm, and Argo CD is installed only after raw Kubernetes feels comfortable.

Kubernetes

Runs desired workloads

You submit API objects. Controllers continuously try to make cluster reality match those objects.

Helm

Packages and renders manifests

A chart is a parameterized package of Kubernetes resources. Helm can install, upgrade, inspect history, and roll back releases.

Argo CD

Continuously reconciles Git

Argo CD compares Git's desired state with live Kubernetes state and can sync, prune, and self-heal.

GitHub Actions

Automates CI workflows

Actions can test, lint, build a container, push it to a registry, and update the GitOps desired state.

Important Argo CD + Helm idea: when Argo CD deploys a Helm chart, Argo CD uses Helm to render templates; Argo CD owns the application lifecycle and reconciliation. Treat Git as the source of truth rather than running helm upgrade manually against the same Argo-managed application.

Every lab is written as a guided exercise: prepare, perform, observe, verify, explain, break/fix, and clean up. Do not skip the observation steps; that is where the understanding is built.

Recommended terminal: the lab commands use Bash syntax. On macOS/Linux, use Terminal. On Windows, use WSL2 Ubuntu or Git Bash for the labs; use PowerShell only where a Windows installation command is explicitly shown. Keep Docker Desktop running whenever minikube is running.

01Build the local Kubernetes workbenchInstall the tools, create the repository, start minikube, and prove kubectl is connected.Kubernetes · setup
You are learningDocker vs minikube vs Kubernetes vs kubectl, kubeconfig, context, node, and namespace.
Success evidencekubectl get nodes shows one Ready minikube node and kubectl config current-context prints minikube.
Machine requirements: use a machine with at least 2 CPUs, 2 GB free RAM, roughly 20 GB free disk, Internet access, and Docker or another supported minikube driver. Docker Desktop is the simplest path for this guide.

Step 1 — install and start Docker

Install Docker Desktop on macOS/Windows, or Docker Engine/Desktop on Linux, using Docker's official installer. Start Docker and wait until its engine reports that it is running. Then verify:

docker version
docker info
Expected: docker version shows both a Client and Server section. If the Server section is missing, Docker is installed but the engine is not running.

Step 2 — install Git, kubectl, and minikube

Choose one operating-system block. The rest of the labs assume the commands are available on your PATH.

macOS with Homebrew
brew install git kubectl minikube
Windows PowerShell with winget
winget install -e --id Git.Git
winget install -e --id Kubernetes.kubectl
winget install Kubernetes.minikube

Close and reopen the terminal after installation so PATH changes are picked up.

Ubuntu / Debian / WSL2
sudo apt-get update
sudo apt-get install -y git curl ca-certificates
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl
curl -LO https://github.com/kubernetes/minikube/releases/latest/download/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
rm minikube-linux-amd64

If your Linux machine is ARM64, use the ARM64 downloads from the official Kubernetes/minikube pages.

Step 3 — verify the binaries before creating a cluster

git --version
docker --version
kubectl version --client
minikube version

Understand: kubectl is only a client. A successful kubectl version --client does not mean a Kubernetes cluster exists yet.

Step 4 — create the lab repository folder

mkdir -p cloud-native-labs
cd cloud-native-labs
git init
git branch -M main
mkdir -p app k8s helm argocd .github/workflows

If Git asks for identity later, configure it once with your own name/email:

git config --global user.name "YOUR NAME"
git config --global user.email "YOUR_EMAIL@example.com"

Step 5 — start a local Kubernetes cluster

minikube start --driver=docker
Expected: minikube creates or reuses a cluster named minikube, enables core components, and configures kubectl to use that cluster.

Step 6 — prove kubectl is connected to the correct cluster

kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
kubectl get namespaces
kubectl get pods -A
Look for: current context minikube; node STATUS Ready; system Pods in namespaces such as kube-system.

Step 7 — inspect context information

kubectl config get-contexts
kubectl config view --minify

Understand: kubeconfig stores cluster, user/credential, and context information. A context is the combination kubectl uses to decide which cluster and which identity to use.

Step 8 — intentional connectivity failure

minikube stop
kubectl get nodes
Expected failure: kubectl cannot reach the API server. This is a connectivity/cluster problem, not a Deployment YAML problem.

Recover:

minikube start --driver=docker
kubectl get nodes
Explain before continuing

What is the difference between Docker, minikube, Kubernetes, and kubectl? If kubectl reports connection refused, why should you check cluster/context connectivity before editing application YAML?

02Deploy Nginx without YAMLUse imperative commands once so you can see Deployment, ReplicaSet, Pod, labels, Service, and reconciliation.Kubernetes · no Helm
You are learningDeployment → ReplicaSet → Pod ownership, selectors, Service routing, scaling, and controller reconciliation.
Success evidenceNginx is reachable through a Service and a deleted Pod is automatically replaced.
  1. Confirm you are on minikube.
    kubectl config current-context
kubectl get nodes

    Do not continue if the node is not Ready.

  2. Create your first Deployment imperatively.
    kubectl create deployment web --image=nginx:alpine
kubectl scale deployment web --replicas=2

    Understand: you asked the Deployment controller for two Pod replicas. You did not create the Pods one by one.

  3. Trace the ownership chain.
    kubectl get deployments
kubectl get replicasets
kubectl get pods -o wide
kubectl describe deployment web
    Look for: Deployment READY 2/2; one ReplicaSet; two Pods whose names start with the ReplicaSet name.
  4. Inspect labels and selectors.
    kubectl get pods --show-labels
kubectl get deployment web -o jsonpath='{.spec.selector.matchLabels}' ; echo
kubectl get deployment web -o yaml

    Find the Deployment selector and the same label on the Pod template. Controllers use these labels to determine which Pods belong to them.

  5. Create a ClusterIP Service.
    kubectl expose deployment web --name=web --type=ClusterIP --port=80 --target-port=80
kubectl get services
kubectl describe service web
kubectl get endpointslices -l kubernetes.io/service-name=web

    The Service selector finds Pods by label. The EndpointSlice should contain Pod IP addresses.

  6. Reach the Service from your laptop.

    Run this command and leave it running:

    kubectl port-forward service/web 8080:80

    Open http://localhost:8080 in a browser, or in a second terminal run:

    curl -I http://localhost:8080
    Expected: HTTP 200 and the standard Nginx welcome page.
  7. Scale to four replicas and watch convergence.
    kubectl scale deployment web --replicas=4
kubectl get pods -w

    Press Ctrl+C after four Pods are Running and Ready.

  8. Delete one Pod and watch Kubernetes replace it.
    kubectl get pods
kubectl delete pod <PASTE_ONE_WEB_POD_NAME>
kubectl get pods -w

    The old Pod disappears and a new Pod appears because the Deployment still desires four replicas.

  9. Inspect the controller relationship directly.
    kubectl get pods -o custom-columns=NAME:.metadata.name,OWNER_KIND:.metadata.ownerReferences[0].kind,OWNER:.metadata.ownerReferences[0].name
kubectl get rs -o custom-columns=NAME:.metadata.name,OWNER_KIND:.metadata.ownerReferences[0].kind,OWNER:.metadata.ownerReferences[0].name
  10. Clean up the imperative resources.
    kubectl delete service web
kubectl delete deployment web
kubectl get all

    Leave minikube running.

Core model: Deployment declares desired Pods; ReplicaSet maintains the count; Service provides a stable virtual endpoint for matching Pods. Kubernetes continuously compares desired state with observed state and acts to close the gap.
Knowledge check

If a Pod dies, which object should you normally repair or change: the Pod, the ReplicaSet, or the Deployment? Why? How does the Service decide which Pods receive traffic?

  name: web
  namespace: raw-lab

  replicas: 2
  selector:
    matchLabels:
      app: web

        app: web

            - name: http

Step 3 — create k8s/service.yaml

apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: raw-lab
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - name: http
      port: 80
      targetPort: http
  1. Ask kubectl to parse the files locally.
    kubectl create --dry-run=client -f k8s/namespace.yaml -o yaml > /tmp/namespace-check.yaml
kubectl create --dry-run=client -f k8s/deployment.yaml -o yaml > /tmp/deployment-check.yaml
kubectl create --dry-run=client -f k8s/service.yaml -o yaml > /tmp/service-check.yaml

    If YAML indentation or field names are invalid, fix them before touching the cluster.

  2. Apply the namespace first, then the namespaced objects.
    kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml
  3. Verify desired and observed state.
    kubectl get all -n raw-lab
kubectl get deployment web -n raw-lab
kubectl get pods -n raw-lab --show-labels
kubectl get endpointslices -n raw-lab -l kubernetes.io/service-name=web
    Expected: Deployment 2/2, two Running Pods, one Service, and endpoints for both Pods.
  4. Test the Service.
    kubectl port-forward service/web -n raw-lab 8080:80

    In another terminal run curl -I http://localhost:8080, then stop port-forward with Ctrl+C.

  5. Change desired state in the file.

    Edit k8s/deployment.yaml and change replicas: 2 to replicas: 3. Before applying, ask Kubernetes what would change:

    kubectl diff -f k8s/deployment.yaml || true

    Then apply and verify:

    kubectl apply -f k8s/deployment.yaml
kubectl get deployment web -n raw-lab
kubectl get pods -n raw-lab
  6. Inspect the live object and compare it with your source file.
    kubectl get deployment web -n raw-lab -o yaml > /tmp/live-deployment.yaml
kubectl describe deployment web -n raw-lab

    The live YAML contains status and server-generated metadata that your source manifest does not need to store.

  7. Commit the desired-state files.
    git status
git add k8s
git diff --cached
git commit -m "lab 03: add raw kubernetes manifests"
git log --oneline -3
  8. Prove the files are reproducible.
    kubectl delete namespace raw-lab
kubectl get namespace raw-lab || true
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml
kubectl get all -n raw-lab

    You reconstructed the application from versioned desired state instead of remembering imperative commands.

Knowledge check

What is the difference between the spec you submit and the status Kubernetes records? Why is source YAML usually stored in Git while live-object YAML is not copied back wholesale?

04Add ConfigMap, Secret, health probes, resources, and scalingMake the raw Kubernetes workload operational instead of merely Running.Kubernetes · operations
You are learningConfiguration injection, Secret handling, readiness vs liveness, requests/limits, and declarative scaling.
Success evidenceA Pod exposes the configured environment variables, reports healthy probes, and has explicit resources.

Step 1 — create k8s/configmap.yaml

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
  namespace: raw-lab
data:
  APP_MESSAGE: "Hello from a Kubernetes ConfigMap"
  APP_ENV: "raw-lab"

Step 2 — create a training Secret from the CLI

Do not create a real credential for this exercise.

kubectl create secret generic demo-secret \
  --from-literal=API_TOKEN='training-only-value' \
  -n raw-lab
kubectl get secret demo-secret -n raw-lab
kubectl get secret demo-secret -n raw-lab -o yaml

Understand: the YAML displays base64-encoded data. Base64 is encoding, not encryption. Do not commit real secrets into this public learning repository.

Step 3 — replace k8s/deployment.yaml with the operational version

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: raw-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:alpine
          ports:
            - name: http
              containerPort: 80
          envFrom:
            - configMapRef:
                name: web-config
          env:
            - name: API_TOKEN
              valueFrom:
                secretKeyRef:
                  name: demo-secret
                  key: API_TOKEN
                  optional: true
          readinessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              cpu: 200m
              memory: 128Mi
  1. Apply configuration before the Deployment that consumes it.
    kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/web -n raw-lab --timeout=120s
  2. Verify Pod readiness and resource configuration.
    kubectl get pods -n raw-lab
kubectl describe deployment web -n raw-lab

    In the describe output, find Environment, Readiness, Liveness, Requests, and Limits.

  3. Read the injected ConfigMap and Secret values inside a Pod.
    POD=$(kubectl get pods -n raw-lab -l app=web -o jsonpath='{.items[0].metadata.name}')
echo "$POD"
kubectl exec -n raw-lab "$POD" -- printenv APP_MESSAGE
kubectl exec -n raw-lab "$POD" -- printenv APP_ENV
kubectl exec -n raw-lab "$POD" -- printenv API_TOKEN
    Expected: the Pod prints the ConfigMap strings and the training-only token.
  4. Inspect probe state.
    kubectl describe pod -n raw-lab "$POD"

    Look for Ready: True, readiness/liveness configuration, and restart count.

  5. Break readiness intentionally.

    Edit only the readiness path in k8s/deployment.yaml from / to /does-not-exist, then apply:

    kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/web -n raw-lab --timeout=45s || true
kubectl get pods -n raw-lab
kubectl describe pod -n raw-lab $(kubectl get pods -n raw-lab -l app=web -o jsonpath='{.items[0].metadata.name}')

    Observe: the container can be Running while the Pod is not Ready. Readiness determines whether it should receive Service traffic.

  6. Repair readiness.

    Change the path back to /, apply, and verify:

    kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/web -n raw-lab --timeout=120s
kubectl get pods -n raw-lab
  7. Commit non-secret configuration.
    git add k8s/configmap.yaml k8s/deployment.yaml
git diff --cached
git commit -m "lab 04: add config probes and resources"

    The CLI-created Secret is intentionally not committed.

Security boundary: for real environments, use a dedicated secret-management pattern such as External Secrets, Sealed Secrets, SOPS, or a cloud secret manager. A public Git repository and a normal Helm values file are not secret stores.
Knowledge check

Can a container be Running while its Pod is not Ready? What is the consequence? What does a liveness failure cause? Why are CPU/memory requests different from limits?

05Perform rollout, failure diagnosis, and rollbackLearn a repeatable Kubernetes troubleshooting ladder before automation hides the mechanics.Kubernetes · failure drill
You are learningRollingUpdate behavior, rollout status/history, ImagePullBackOff evidence, events, logs, undo, and the difference between live rollback and source-of-truth repair.
Success evidenceYou intentionally create a broken image rollout, identify the exact cause, and recover.
  1. Record the current baseline.
    kubectl get deployment web -n raw-lab -o wide
kubectl get pods -n raw-lab
kubectl rollout history deployment/web -n raw-lab
  2. Create a healthy new revision declaratively.

    Edit k8s/deployment.yaml, change image: nginx:alpine to image: nginx:1.27-alpine, then:

    kubectl diff -f k8s/deployment.yaml || true
kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/web -n raw-lab --timeout=120s
kubectl rollout history deployment/web -n raw-lab
kubectl get pods -n raw-lab -o wide

    Watch old Pods disappear gradually while new Pods become Ready.

  3. Commit the healthy desired state.
    git add k8s/deployment.yaml
git commit -m "lab 05: roll nginx to 1.27-alpine"
  4. Introduce a bad image tag in the YAML.

    Change the image to nginx:this-tag-does-not-exist, then apply:

    kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/web -n raw-lab --timeout=45s || true
kubectl get pods -n raw-lab
  5. Diagnose systematically; do not guess.
    BAD_POD=$(kubectl get pods -n raw-lab -l app=web --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
echo "$BAD_POD"
kubectl describe pod -n raw-lab "$BAD_POD"
kubectl get events -n raw-lab --sort-by=.lastTimestamp | tail -n 20
    Look for: ErrImagePull, ImagePullBackOff, and an event saying the image/tag could not be pulled.
  6. Try logs and learn when logs are unavailable.
    kubectl logs -n raw-lab "$BAD_POD" || true

    If the image never starts, there may be no container logs. In that case, describe and Events are more useful than logs.

  7. Roll back the live Deployment.
    kubectl rollout undo deployment/web -n raw-lab
kubectl rollout status deployment/web -n raw-lab --timeout=120s
kubectl get pods -n raw-lab
kubectl get deployment web -n raw-lab -o jsonpath='{.spec.template.spec.containers[0].image}' ; echo

    This repairs the cluster, but your local YAML still contains the bad tag.

  8. Repair the source of truth too.

    Change k8s/deployment.yaml back to nginx:1.27-alpine, then:

    kubectl apply -f k8s/deployment.yaml
git add k8s/deployment.yaml
git commit -m "lab 05: restore valid image after failure drill"
git status
  9. Practice the troubleshooting ladder once more.
    kubectl get all -n raw-lab
kubectl describe deployment web -n raw-lab
kubectl get events -n raw-lab --sort-by=.lastTimestamp | tail -n 15
  10. Clean the live raw-lab environment for later GitOps labs.
    kubectl delete namespace raw-lab
kubectl get namespace raw-lab || true

    Do not delete the k8s/ files from Git; Argo CD will deploy them later.

Troubleshooting ladder: workload status → Pod list → describe → events → logs → configuration/manifests → Service/network. Start with evidence and narrow the failure domain.
Knowledge check

06Install Helm 4 and learn chart anatomyInstall Helm only after understanding the Kubernetes YAML that Helm will render.Helm · setup
You are learningHelm client installation, chart vs release, values, templates, rendering, and the difference between generating YAML and installing it.
Success evidencehelm version works and you can render a starter chart without modifying the cluster.

Step 1 — install Helm

macOS
brew install helm
Windows PowerShell
winget install Helm.Helm
Linux / WSL
curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-4
chmod 700 get_helm.sh

rm get_helm.sh

    helm version

    minikube status

    Helm uses your Kubernetes configuration when installing releases.

    Package metadata such as chart name and version.

    values.yaml

    Default input data for templates.

    templates/

    Kubernetes manifests containing Go-template expressions.

    An installed instance of a chart plus configuration and revision history.

    rm -rf helm/anatomy-demo

Step 3 — create .github/workflows/build-promote-dev.yaml

name: Build Image and Promote Dev

on:
  push:
    branches: [ main ]
    paths:
      - "app/**"

permissions:
  contents: write
  packages: write

jobs:
  build-promote-dev:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6
        with:
          fetch-depth: 0

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push immutable SHA image
        uses: docker/build-push-action@v6
        with:
          context: ./app
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

      - name: Update the dev image tag in Git
        env:
          IMAGE_TAG: ${{ github.sha }}
        run: |
          python - <<'PY'
          from pathlib import Path
          import os, re

          path = Path("helm/cloud-lab/values-dev.yaml")
          text = path.read_text()
          new_tag = os.environ["IMAGE_TAG"]
          updated, count = re.subn(
              r'(?m)^(  tag:\s*).+$',
              rf'\1"{new_tag}"',
              text,
              count=1,
          )
          if count != 1:
              raise SystemExit("Could not find exactly one image tag in values-dev.yaml")
          path.write_text(updated)
          PY

          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add helm/cloud-lab/values-dev.yaml
          git diff --cached --quiet && exit 0
          git commit -m "promote dev image ${GITHUB_SHA} [skip ci]"
          git push
