Senior-level answer checklist for every topic

  1. Architecture: name the components, data flow, state, and external dependencies.
  2. Normal operation: explain how users consume the service and what good health looks like.
  3. Failure modes: identify the likely bottlenecks and blast radius.
  4. Telemetry: state the metrics, logs, traces, and synthetic checks that prove or disprove hypotheses.
  5. Recovery: describe mitigation, validation, rollback, and communication.
  6. Prevention: add automation, capacity, testing, controls, or architecture changes.

Four answer frameworks

Technical explanation: D-A-O-F

  1. Direct: answer the question in one sentence.
  2. Architecture: components and data flow.
  3. Operations: health, scale, security, upgrade.
  4. Failure: likely failure mode, detection, recovery.

Incident: I-S-O-R-P

  1. Impact and severity.
  2. Stabilize and limit blast radius.
  3. Observe evidence and isolate the layer.
  4. Recover and validate.
  5. Prevent with RCA actions.

Live coding: C-D-I-T-O

  1. Clarify inputs, scale, failure behavior.
  2. Design functions and data model.
  3. Implement the happy path cleanly.
  4. Test invalid input, timeout, partial failure.
  5. Operationalize logs, metrics, exit code, secret handling.

Whiteboard: R-D-S-S-O

  1. Requirements and SLOs.
  2. Dataflow and state.
  3. Scale and failure domains.
  4. Security and controls.
  5. Operations, observability, DR, trade-offs.

What to write on the board before solving an incident

User impact -> recent change -> service topology -> evidence by layer -> safest mitigation -> validation -> communication -> RCA actions

How to recover when stuck

  • State the layer you are testing: client, DNS, network, load balancer, application, database, storage, or external dependency.
  • Ask for one concrete signal: HTTP status, timestamp, correlation ID, affected scope, recent change, queue depth, JVM metrics, or Kubernetes events.
  • Say what result would confirm or reject the hypothesis.
  • Do not invent a product-specific menu or command. Explain the vendor-neutral operational principle and say where you would verify exact syntax.

F2F coding etiquette

  • Use meaningful function names and small functions. Avoid writing one long script.
  • Never place tokens or passwords in the code. Read them from a secret store or environment variable.
  • Call out time complexity only when relevant; operational correctness matters more here.
  • For an API task, mention pagination, rate limiting, retries, timeouts, authentication, and partial failures.
  • For a cleanup task, require a dry-run, explicit scope, audit output, and a safe threshold.

Core reliability vocabulary

SLIA measured indicator, such as successful workflow dispatch rate, API availability, P95 queue time, or artifact download latency.
SLOAn internal reliability objective for an SLI over a window, such as 99.9% successful requests per 30 days.
SLAA formal service commitment with consequences or escalation when missed. It may include response and resolution targets.
Error budgetThe permitted unreliability implied by the SLO. It helps balance feature or change velocity against stability.
ToilManual, repetitive, automatable operational work that scales with service usage and produces little enduring value.
RunbookA tested operational procedure with trigger, scope, prerequisites, steps, validation, rollback or escalation, owner, and revision date.
MTTD / MTTA / MTTRMean time to detect, acknowledge, and restore or resolve. Define which interpretation of R you use.
RTOMaximum acceptable restoration time after a disruption.
RPOMaximum acceptable data-loss interval, determined by replication and backup cadence.

Availability and error-budget math

Formulas
Availability = successful service time / total scheduled service time

For a 30-day window:
99.9% SLO  -> about 43.2 minutes of error budget
99.95% SLO -> about 21.6 minutes of error budget
99.99% SLO -> about 4.32 minutes of error budget

Example request-based SLI:
availability = successful_valid_requests / all_valid_requests
Exclude only explicitly documented cases such as client-caused invalid requests.
Interview nuance: do not use CPU availability as the service SLI. Users care whether jobs dispatch, artifacts resolve, deployments execute, and APIs respond correctly. Resource metrics help explain why the SLI is at risk.

Actionable alert design

  • Alert on a user-visible symptom or an imminent capacity breach, not every metric fluctuation.
  • Include service, environment, severity, current value, threshold, duration, scope, dashboard, owner, and runbook.
  • Use a duration or multi-window rule to suppress brief noise, while keeping hard-down checks fast.
  • Deduplicate related alerts and route to the team that can act.
  • Review false positives, false negatives, and repeated manual actions after incidents.

Failure domains to mark explicitly

  • Control plane: Jenkins controller, UCD server, Harness or GitHub SaaS control plane, identity provider.
  • Execution plane: self-hosted runners, agents, Kubernetes build namespaces, worker node pools.
  • Artifact plane: Artifactory nodes, load balancer, database, filestore, remote repositories.
  • Network: DNS, proxy, firewall, NAT, certificate chain, private endpoints, WAN or Internet path.
  • Shared dependencies: secrets manager, database, object/NFS storage, logging, ticketing, vendor service.

Design principles for a large developer base

Isolation

  • Runner groups, labels, namespaces, quotas, network policies.
  • Separate high-risk or privileged workloads.
  • Per-tenant credentials and least privilege.
  • Protect production deployment workers from untrusted pull requests.

Elasticity

  • Ephemeral runners or build pods for burst demand.
  • Autoscale on queued workload plus node capacity.
  • Warm capacity for predictable peaks.
  • Bound concurrency to protect downstream systems.

Recoverability

  • Document state and stateless components.
  • Backup database, configuration, keys, and artifact metadata or binaries as required.
  • Automate rebuild of execution workers.
  • Test restoration and regional failover.

Governance

  • Reusable templates and approved actions/plugins.
  • Version pinning and artifact immutability.
  • Change control and audit evidence.
  • Platform standards with an exception process.

End-to-end request path to explain

  1. A developer event or scheduled trigger reaches the CI/CD control plane.
  2. Policy, identity, branch or environment rules, and workflow syntax are evaluated.
  3. A job enters a queue and is matched to an eligible runner, agent, delegate, or build pod.
  4. The worker retrieves source and dependencies, then builds, tests, scans, and publishes artifacts.
  5. Artifact metadata and immutable version identify exactly what is promoted or deployed.
  6. A deployment orchestrator updates the target and performs health or approval gates.
  7. Metrics, logs, traces, audit events, and status return to dashboards and users.

  • Review service SLOs, queue wait, failed dispatches, agent availability, disk and JVM health.
  • Investigate recurring job failures separately from platform failures.
  • Check controller and agent certificate, credential, and image expiry windows.
  • Review noisy jobs, abandoned workspaces, artifact retention, and long queues.

Monthly / planned

  • Patch OS/JVM/controller, review plugin advisories and compatibility.
  • Test backup restore, disaster procedures, and configuration-as-code drift.

How to scale Jenkins safely

  • Keep the controller focused on orchestration; configure its built-in node with zero executors for normal workloads.
  • Use agents with purpose-specific labels and right-sized executor counts.
  • Prefer ephemeral agents on Kubernetes or cloud for bursty and untrusted build work, with immutable images and automatic cleanup.
  • Use shared libraries and configuration as code to standardize behavior, but version and review them because they have broad blast radius.
  • Offload build artifacts to Artifactory and keep controller retention bounded.
  • Reduce expensive polling, oversized logs, uncontrolled parallelism, and plugin sprawl.
  • Partition workloads only when required by scale, security, failure-domain, or organizational boundaries; multiple controllers increase operational overhead.

Upgrade runbook answer

  1. Inventory and compatibility: controller/JVM/OS versions, plugins, agents, integrations, deprecated APIs, support matrix, security advisories.
  2. Risk and recovery: consistent backup of JENKINS_HOME and keys, restore rehearsal, rollback package, database or external storage checks if used.
  3. Rehearsal: restore production-like configuration to non-production, upgrade there, run representative jobs and integration tests.
  4. Change preparation: approvals, user communication, freeze or drain plan, active build handling, vendor support window, monitoring baseline.
  5. Execution: stop or quiet down safely, snapshot, upgrade core then compatible plugins in a controlled sequence, start and inspect logs.
  6. Validation: UI/API, authentication, SCM webhooks, credentials, agent connection, sample pipelines, artifact publishing, notifications and performance.
  7. Observe and close: enhanced monitoring, document deviations, close change only after stability window; roll back on defined triggers.

Queue troubleshooting decision tree

Queue growing? -> Is item blocked by upstream, quiet period, lock, or concurrency rule? -> Is it buildable but no matching label/permission? -> Are matching agents online and idle? -> Is cloud/Kubernetes provisioning failing or slow? -> Is controller scheduling delayed by JVM, plugin, storage, or thread pressure? -> Is downstream dependency intentionally throttling concurrency?

Security points

  • SSO and role-based authorization; no broad anonymous or matrix permissions.
  • Credential scopes and folders; never print credentials; rotate and audit usage.
  • Restrict Script Console and in-process script approvals because they are high privilege.
  • Pin, review, and minimize plugins; track security advisories and provenance.
  • Protect controller network access and administrative endpoints; use TLS and trusted certificates.
  • Separate trusted deployment workers from untrusted pull-request builds.

Jenkins Declarative Pipeline

  agent none

  options {
    timestamps()
    disableConcurrentBuilds(abortPrevious: false)
    timeout(time: 45, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '30', artifactNumToKeepStr: '10'))
    skipDefaultCheckout(true)
  }

  environment {
    ARTIFACTORY_URL = 'https://artifactory.example.com'
  }

  stages {
    stage('Build and test') {
      agent { label 'linux-docker' }
      steps {
        checkout scm
        sh 'python -m pip install -r requirements.txt'
        sh 'python -m pytest --junitxml=reports/junit.xml'
        sh 'docker build --pull -t app:${BUILD_NUMBER} .'
      }
      post {
        always {
          junit allowEmptyResults: false, testResults: 'reports/junit.xml'
        }
      }

CI workloads on Kubernetes

  • Build workloads are bursty, short-lived, I/O intensive, and may pull large images; autoscaling must include node startup and registry capacity.

  • Control ephemeral-storage requests/limits and workspace cleanup; node disk pressure can evict builds.
  • Cache dependencies carefully: shared cache improves speed but introduces consistency, poisoning, isolation and storage concerns.
  • Export logs and results before ephemeral Pods disappear.

Prometheus concepts

  • Counter: monotonically increases except reset; use rate() or increase() for events.
  • Gauge: can rise or fall; use for queue depth, free bytes, current workers.
  • Histogram: bucketed observations supporting server-side aggregation and quantiles; use for queue or request latency.
  • Label cardinality: every unique label set creates a series. Avoid unbounded values such as build ID, commit SHA, raw URL, user ID, or error message.
  • Recording rules: precompute frequently used or expensive queries with controlled names.
  • Alertmanager: groups, routes, deduplicates, silences, and inhibits notifications; it does not repair poor alert design.

Full health-check example

Python 3 health-check utility
#!/usr/bin/env python3
"""Concurrent endpoint health checker with retries and machine-readable output."""

from __future__ import annotations

import argparse
import concurrent.futures
import json
import logging
import random
import sys
import threading
import time
from dataclasses import asdict, dataclass
from pathlib import Path

import requests

LOG = logging.getLogger("healthcheck")
_thread_state = threading.local()
TRANSIENT_STATUS = {408, 425, 429, 500, 502, 503, 504}


@dataclass(frozen=True)
class Result:
    url: str
    healthy: bool
    status: int | None
    latency_ms: int
    attempts: int
    error: str | None


def session() -> requests.Session:
    if not hasattr(_thread_state, "session"):
        _thread_state.session = requests.Session()
        _thread_state.session.headers.update({"User-Agent": "ci-platform-health/1.0"})
    return _thread_state.session


def check(url: str, timeout: float, retries: int) -> Result:
    started = time.monotonic()
    last_error: str | None = None
    last_status: int | None = None

    for attempt in range(1, retries + 2):
        try:
            response = session().get(url, timeout=(min(timeout, 3.0), timeout))
            last_status = response.status_code
            if 200 <= response.status_code < 400:
                return Result(url, True, response.status_code,
                              int((time.monotonic() - started) * 1000), attempt, None)
            last_error = f"unexpected HTTP status {response.status_code}"
            if response.status_code not in TRANSIENT_STATUS:
                break
        except requests.RequestException as exc:
            last_error = f"{type(exc).__name__}: {exc}"

        if attempt <= retries:
            delay = min(8.0, 0.5 * (2 ** (attempt - 1))) + random.uniform(0, 0.25)
            time.sleep(delay)

    return Result(url, False, last_status,
                  int((time.monotonic() - started) * 1000), attempt, last_error)


def load_urls(path: Path) -> list[str]:
    urls = []
    for raw in path.read_text(encoding="utf-8").splitlines():
        value = raw.strip()
        if value and not value.startswith("#"):
            if not value.startswith(("https://", "http://")):
                raise ValueError(f"unsupported URL: {value}")
            urls.append(value)
    if not urls:
        raise ValueError("input file contains no URLs")
    return sorted(set(urls))


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser()
    parser.add_argument("--input", type=Path, required=True)
    parser.add_argument("--output", type=Path, default=Path("health-report.json"))
    parser.add_argument("--timeout", type=float, default=5.0)
    parser.add_argument("--retries", type=int, default=2)
    parser.add_argument("--workers", type=int, default=8)
    return parser.parse_args()


def main() -> int:
    args = parse_args()
    logging.basicConfig(level=logging.INFO,
                        format="%(asctime)s %(levelname)s %(message)s")
    try:
        urls = load_urls(args.input)
    except (OSError, ValueError) as exc:
        LOG.error("cannot load input: %s", exc)
        return 1

    workers = max(1, min(args.workers, 32, len(urls)))
    with concurrent.futures.ThreadPoolExecutor(max_workers=workers) as pool:
        futures = [pool.submit(check, url, args.timeout, args.retries) for url in urls]
        results = [future.result() for future in concurrent.futures.as_completed(futures)]

    results.sort(key=lambda item: item.url)
    payload = {
        "checked": len(results),
        "healthy": sum(item.healthy for item in results),
        "unhealthy": sum(not item.healthy for item in results),
        "results": [asdict(item) for item in results],
    }
    args.output.write_text(json.dumps(payload, indent=2), encoding="utf-8")
    LOG.info("checked=%d healthy=%d unhealthy=%d output=%s",
             payload["checked"], payload["healthy"], payload["unhealthy"], args.output)
    return 2 if payload["unhealthy"] else 0


if __name__ == "__main__":
    sys.exit(main())

How to explain the example

  • time.monotonic() measures elapsed time safely even if the system clock changes.
  • A thread-local session avoids sharing mutable session state between threads.
  • Retries are bounded and used for transient status codes; a 401 or 403 is not retried blindly.
  • Concurrency is capped to avoid overwhelming the network or target.
  • The report is deterministic, sorted, JSON-formatted, and returns code 2 when a service is unhealthy.
  • For production, add TLS policy, proxy configuration, authentication from a secret manager, tests, and metrics according to the environment.

API pagination pattern

API pagination pattern
from __future__ import annotations

import os
import time
from collections.abc import Iterator

import requests

BASE_URL = "https://api.github.com"
TOKEN = os.environ["GITHUB_TOKEN"]


def iter_org_runners(org: str) -> Iterator[dict]:
    url = f"{BASE_URL}/orgs/{org}/actions/runners"
    params = {"per_page": 100}
    headers = {
        "Accept": "application/vnd.github+json",
        "Authorization": f"Bearer {TOKEN}",
    }

    while url:
        response = requests.get(url, headers=headers, params=params, timeout=(3, 20))
        if response.status_code in {429, 502, 503, 504}:
            retry_after = int(response.headers.get("Retry-After", "2"))
            time.sleep(min(retry_after, 30))
            continue
        response.raise_for_status()
        payload = response.json()
        yield from payload.get("runners", [])
        url = response.links.get("next", {}).get("url")
        params = None  # next URL already contains pagination parameters

First 15 minutes of a high-severity incident

  1. Confirm actual user impact, scope, start time, critical business window and whether data integrity or security is at risk.
  2. Declare severity using the organization's criteria; appoint incident lead and scribe, open the correct bridge/channel/ticket.
  3. Freeze unrelated changes and identify the latest relevant deployment, configuration, certificate, network or infrastructure change.
  4. Choose a safe mitigation: rollback, failover, traffic reduction, queue throttling, unhealthy-node removal, or temporary workaround.
  5. Collect synchronized evidence from dashboards, logs, events and dependencies; assign parallel workstreams without duplicating effort.
  6. Send a concise update: impact, current action, known/unknown, next update time. Never speculate as fact.

Mitigation versus root cause

Mitigation restores or reduces impact now. Root cause explains the technical and systemic conditions that allowed the incident. Restarting a controller may mitigate a stuck process, but it does not prove why it became stuck. A mature answer keeps these separate.

Capacity review method

  1. Define the user-facing threshold: queue SLO, artifact latency, storage safety level, or deployment throughput.
  2. Segment workload by pool, repository, tenant, size, duration and time of day; averages hide peaks.
  3. Measure effective capacity during normal operation and one failure domain lost.
  4. Forecast at least to the next procurement, quota, license or change lead time.
  5. Choose trigger and action: autoscale, add nodes, tune concurrency, optimize workload, expand storage, archive, or redesign.
  6. Load test or simulate with representative workload and verify dependencies do not become the new bottleneck.
  7. Record owner, threshold, planned date, cost, risk and post-change result.

Performance investigation method

  • Use a baseline and a precise percentile; "slow" is not measurable.
  • Separate queue time, execution time, and dependency time.
  • Compare affected versus unaffected tenant, site, worker pool, node or artifact type.
  • Overlay changes and demand. Check saturation and errors before tuning.
  • Change one controlled variable, validate, and retain rollback.
  • Do not make JVM heap, thread pool, database pool, or executor counts larger without proving the previous limit and downstream capacity.

Capacity traps

  • Autoscaling Pods when the node pool or cloud quota cannot grow.
  • Adding Jenkins executors to already saturated hosts.
  • Deleting Artifactory content without retention ownership or understanding garbage collection.
  • Using average job duration when a small number of long jobs consume most capacity.
  • Ignoring image-pull, package-proxy, database, or network bandwidth limits.
  • Running at 95% steady utilization with no failure or maintenance headroom.

How to answer a sizing question

"I would not size from user count alone. I would collect peak arrival rate by workload class, duration distribution, CPU/memory/storage per job, startup overhead, required queue SLO, node and downstream constraints, and failure headroom. I would model initial capacity, validate with a representative load test, set autoscale and hard limits, then revisit from production telemetry."

import json

import requests


def check(url: str) -> dict:
    error = None
    started = time.monotonic()
    for attempt in range(1, 4):
        try:
            response = requests.get(url, timeout=(3, 7))
            if 200 <= response.status_code < 400:
                return {"url": url, "ok": True, "status": response.status_code,

        if attempt < 3:

    return {"url": url, "ok": False, "error": error,
            "latency_ms": int((time.monotonic() - started) * 1000),
            "attempts": attempt}

def certificate_days_left(host: str, port: int = 443, timeout: float = 5.0) -> int:

    return candidates

class State(StrEnum):

A. Systems operations and reliability fundamentals

1How is a systems operations engineer different from an application DevOps engineer?P0

An application DevOps engineer may focus on one product team's pipeline and infrastructure. A systems operations engineer for this JD operates shared CI/CD platforms as services: administration, availability, upgrades, incident/change/problem, capacity, observability, BCP, security controls and support for many developer teams.

A senior answer still understands pipelines, but emphasizes platform blast radius, tenancy, SLOs and lifecycle ownership.

2What is the difference between SLI, SLO, and SLA?P0

An SLI is a measured indicator such as successful job dispatch ratio or P95 queue time. An SLO is the internal objective for that indicator over a window. An SLA is a formal service commitment and may define support response, resolution or consequences.

3What is an error budget?P0

It is the amount of unreliability permitted by an SLO. For a 99.9% request-success SLO, up to 0.1% of valid requests may fail in the window. Teams use consumption and burn rate to decide when stability work or change restraint is needed.

4Which SLIs would you use for a CI/CD platform?P0

Valid workflow dispatch success, P95 queue-to-worker time, API/UI availability, artifact upload/download success and latency, deployment orchestration success, and possibly support MTTA/restore time. Resource metrics are diagnostic indicators, not the primary user outcome.

5Explain the four golden signals.P0

Latency, traffic, errors and saturation. For example: queue or request duration; jobs or requests per second; failed dispatches or 5xx; and worker, thread, DB pool or storage saturation.

6What are RED and USE?P1

RED is Rate, Errors and Duration for request- or event-driven services. USE is Utilization, Saturation and Errors for resources. Use RED for artifact/API behavior and USE for nodes, executors, disks, databases and network interfaces.

7What is toil, and how do you reduce it?P0

Toil is repetitive, manual, automatable operations work that scales with service usage and has little enduring value. Measure frequency and risk, automate the highest-value pattern safely, add observability and ownership, then verify that engineer-hours and error rate fall.

8What is the difference between availability and reliability?P1

Availability is whether the service can be used at a point or over a period. Reliability is broader consistency of correct service, including success, latency and predictable behavior. A service may be technically up but unreliable if jobs regularly time out or wait too long.

9What is capacity headroom?P0

The margin between effective capacity and expected peak demand. It must account for workload variability, maintenance and loss of a failure domain. A system at 90-95% steady utilization may have insufficient operational headroom even if it is not failing yet.

10How do you measure MTTR?P1

First define R: restore service or fully resolve root cause. For operations, mean time to restore is often the useful user-impact metric. Measure from an agreed start point, such as impact or detection, to validated restoration, and segment by severity instead of averaging unlike incidents.

11What makes an alert actionable?P0

It indicates real or imminent impact, reaches the team able to act, includes scope/value/duration/severity, links a dashboard and tested runbook, and has clear recovery behavior. It should not page solely because a low-level metric briefly crossed a static threshold.

12How do you avoid alert fatigue?P1

Page on user symptoms and urgent capacity risk, use duration and multi-window logic, group/inhibit dependent alerts, route by ownership, silence maintenance safely, and review pages for actionability. Remove or downgrade alerts that repeatedly require no action.

13What is a runbook?P0

A tested operational procedure with trigger, scope, prerequisites, permissions, numbered steps, expected results, validation, rollback or escalation, owner and review date. It should capture decisions, not only a list of commands.

14What is a playbook versus a runbook?P2

Usage varies, so define local terminology. Commonly a runbook is a precise procedure for a known operation, while a playbook is a broader response strategy with decision branches, roles and multiple runbooks. Do not argue over terms; explain content and ownership.

15How do you classify a platform incident versus an application failure?P0

Use evidence and documented service boundaries. If one repository fails its unit test, it is application-owned. If many teams cannot acquire workers, authenticate, resolve dependencies or publish artifacts, it is likely platform or shared dependency. Keep classification reversible as evidence changes.

16What is a blast radius?P0

The users, tenants, environments, regions, data and downstream services that can be affected by a failure or change. Senior change and incident answers state the blast radius before acting and use canaries, isolation or staged rollout to reduce it.

17What does idempotent automation mean?P0

Running it repeatedly with the same desired state produces no unintended additional change. The automation first observes actual state, computes a plan, applies only needed changes and verifies convergence. Destructive operations remain explicitly controlled.

18How do you decide what not to automate?P1

Do not fully automate poorly understood, rare, high-impact or policy-sensitive decisions until guardrails and evidence are strong. Examples include irreversible data deletion, broad access changes or production failover. Automate data collection, validation and safe reversible steps first, with human approval at the risk boundary.

19What is graceful degradation for a CI/CD platform?P1

Preserve critical functions while limiting noncritical demand. Examples include prioritizing emergency production pipelines, pausing large batch builds, serving cached artifacts when upstream is slow, or operating at reduced worker concurrency during DR. The degraded service level must be explicit and controlled.

20How do you prove a service has recovered?P0

Validate the user-facing SLI and a representative end-to-end transaction, not only process status. Confirm backlog drains, errors and latency return to baseline, dependencies are healthy, data/state is consistent, and monitoring itself is receiving current telemetry.

B. Jenkins administration and troubleshooting

21Explain Jenkins controller, node, agent, and executor.P0

The controller stores configuration and schedules work. A node is a machine or environment on which an agent can run. The agent connects and executes work for the controller. An executor is one concurrent work slot on a node. Multiple executors share that node's CPU, memory and I/O.

22Why should normal builds not run on the Jenkins controller?P0

Builds compete with scheduling, UI/API, configuration and plugin work; they also expand security exposure and disk pressure. Keep the controller focused on orchestration and set its built-in node executors to zero for normal jobs.

23How do you choose the number of executors on an agent?P0

Size from CPU, memory, I/O, workspace, tool licensing and workload profile. One executor per core is not a universal rule. Measure peak utilization and job duration; too many executors increase contention and can make total throughput worse.

24Static agents or ephemeral agents?P0

Static agents have faster startup and suit specialized hardware or software, but accumulate drift and require cleanup. Ephemeral agents improve isolation, consistency and elasticity, but depend on provisioning speed, image management and externalized logs. Many enterprises use both by workload class.

25How do you troubleshoot an offline Jenkins agent?P0

Check scope, controller disconnect reason, agent process and logs, host resources/clock, launcher credentials, DNS/port/TLS/proxy and version compatibility. If many agents share a zone or launcher, investigate the common dependency before restarting each host.

26Why can a Jenkins job remain queued even when an executor is idle?P0

The idle executor may not match the label, folder/authorization boundary, node mode or workspace requirement. The item may also be blocked by upstream, lock, quiet period, throttle or concurrency condition. Inspect the queue reason rather than infer from the global idle count.

27What metrics would you monitor on a Jenkins controller?P0

UI/API latency and errors, queue length and oldest wait, job dispatch, heap and post-GC use, GC pause, CPU, threads, file descriptors, disk/inodes/I/O, plugin exceptions, backup health and agent connections.

28How do you investigate high Jenkins heap usage?P0

Check usage after GC, allocation rate, pause time, workload and recent plugin/config changes. Capture GC logs and approved heap diagnostics. Look for job/build metadata, plugin cache, leaked objects or excessive concurrency. Do not simply increase heap without identifying limits and container/host memory.

29How do you investigate high Jenkins CPU?P0

Correlate CPU with per-thread usage, thread dumps, GC CPU, request volume, queue, SCM polling, plugin tasks and disk/network wait. Compare recent changes and healthy baseline. Restart may restore service but does not identify the hot thread or cause.

30What is Jenkins Configuration as Code?P1

Commonly the Jenkins Configuration as Code plugin represents controller configuration in reviewed YAML so environments can be reproducible. Treat it as privileged code: version, validate, test and roll out carefully; secrets should be referenced from approved stores, not committed.

31How do you back up Jenkins?P0

Identify required JENKINS_HOME content, configuration, job definitions, plugin inventory, credentials/secrets and encryption keys, plus any external database or storage. Create a consistent protected backup, document version/JVM dependencies, and prove restore in a separate environment with representative jobs.

32What is the most important part of a Jenkins backup?P0

Restoreability. A successful backup job is not enough. The team must recover the configuration and cryptographic material with a compatible Jenkins/plugin/JVM stack, connect agents and run representative pipelines within RTO/RPO.

33Describe a Jenkins upgrade strategy.P0

Inventory core/JVM/OS/plugins/integrations, review supported path and advisories, back up and restore-test, rehearse with production-like jobs, schedule controlled drain/quiet-down, upgrade with rollback checkpoints, validate authentication/SCM/agents/artifacts/notifications, then observe performance.

34How do you manage Jenkins plugins safely?P0

Minimize count, assign owners, track security advisories and dependencies, pin/test compatible versions, stage upgrades, retain rollback packages and avoid installing directly in production to solve an ad hoc request. Remove only after dependency and usage review.

35What is the Jenkins Script Console risk?P1

It executes highly privileged Groovy inside the controller and can read secrets, change configuration or damage state. Restrict access, audit use and prefer supported APIs/configuration-as-code. Use it only under approved administrative procedure.

36What is a Jenkins shared library?P0

Versioned reusable pipeline code and functions shared across jobs. It standardizes controls and reduces duplication, but a change can affect many pipelines. Use review, versioning, tests, canary consumers and rollback; avoid uncontrolled implicit latest versions for critical workflows.

37Declarative versus Scripted Pipeline?P1

Declarative Pipeline provides a structured model, validation and standardized sections; Scripted Pipeline is Groovy-driven and more flexible. Prefer the simplest maintainable model. Both still require security, agent, timeout, retry and artifact discipline.

38How should credentials be used in Jenkins pipelines?P0

Store them in an approved credential provider, scope access, bind only for the required step, never echo or place in command arguments/artifacts, and rotate. Masking helps but is not a complete control; shell tracing and encoded values can still leak.

39How do you prevent concurrent deployments to one environment?P1

Use an environment-specific lock, concurrency control or deployment orchestrator gate, with timeout and clear cancellation behavior. The lock key must represent the target environment and not serialize unrelated deployments unnecessarily.

40What is a quiet-down or drain strategy before Jenkins maintenance?P1

Stop accepting new work or restrict scheduling, allow active jobs to finish within a defined window, decide how to handle long jobs, preserve queue state according to product behavior, communicate impact, then perform change. Validate queue and agents after return.

41How do you reduce Jenkins disk usage safely?P0

Identify logs, build records, workspaces, caches, artifacts and deleted-open files. Enforce job/build/artifact retention, offload artifacts, clean workspaces after confirming no active use, rotate logs and expand capacity if needed. Never bulk-delete JENKINS_HOME by guess.

42What causes Jenkins controller startup failure after an upgrade?P1

Unsupported JVM/core path, plugin incompatibility or dependency, corrupted/incompatible configuration, port/permission/storage issue, missing keys, or failed migration. Use startup logs, version inventory and tested rollback rather than repeatedly reinstalling plugins.

43How do you separate a Jenkins platform problem from a bad pipeline?P0

Check scope across jobs, agents and repositories. Platform problems affect shared scheduling, agents, credentials, SCM, artifacts or API. A single job failing a deterministic test or syntax step is application-owned, though platform telemetry should make the distinction clear.

44How do you make Jenkins highly available?P0

Start by clarifying supported product architecture and recovery objective. The controller has state and cannot be made active/active merely by placing two instances behind a load balancer. Use supported storage/backup/standby or vendor-specific HA design, externalize workers/artifacts, automate rebuild and test failover/restore.

45What should a Jenkins operations runbook contain?P1

Service topology, dependencies, dashboards, queue and agent triage, JVM diagnostic capture, disk-full procedure, backup/restore, upgrade/rollback, credential/certificate rotation, high-severity incident path, vendor escalation and validation transactions.

C. GitHub SaaS and GitHub Actions

46GitHub-hosted versus self-hosted runners?P0

GitHub-hosted runners reduce worker infrastructure administration and provide clean hosted environments, but have network/customization and usage constraints. Self-hosted runners offer controlled networks, software and hardware but the organization owns patching, isolation, scaling, cleanup, logs and compromise response.

47What is an ephemeral self-hosted runner?P0

A runner registered to process one job and then deregistered/destroyed. It improves isolation and reduces state drift. Production design must export logs, manage image versions, scale capacity and ensure deregistration even on failure.

48What is Actions Runner Controller?P0

It is GitHub's Kubernetes-oriented runner autoscaling solution. It manages runner scale sets/workloads in Kubernetes. The operations team still owns cluster capacity, RBAC, networking, images, namespaces, upgrades, logs and secure workload separation.

49What is the difference between runner labels and runner groups?P0

Labels describe capabilities used by runs-on matching. Runner groups are an access and organization boundary controlling which repositories or workflows can use runners. A job needs both eligibility and matching labels.

50Why do GitHub Actions jobs remain queued?P0

No eligible online idle runner; exact label mismatch; runner group restriction; autoscaler/provisioning failure; Kubernetes/VM quota; registration/network issue; or intentional workflow/environment concurrency. Inspect the exact pool and oldest job, not only total runner count.

51How do you monitor self-hosted runners?P0

Queued jobs and oldest wait by group/label, online/idle/busy/offline supply, registration/startup time, pickup/requeue failures, job duration/result by image/pool, runner version, worker CPU/memory/disk, and Kubernetes/VM provisioning health.

52How do you autoscale GitHub Actions runners?P0

Use a supported scale-set/controller or custom demand integration to create ephemeral workers from queued demand. Bound min/max, provide warm capacity, ensure cluster/cloud quota, select workload class, register with correct group/labels, export logs and destroy after use.

53How do you secure self-hosted runners?P0

Separate trust pools, use ephemeral immutable workers, minimal network access and short-lived credentials, restrict runner groups, avoid untrusted fork PRs on sensitive pools, pin actions, patch images, monitor egress and have rapid revocation/rebuild procedures.

54What are workflow permissions?P0

They control the GITHUB_TOKEN capabilities available to jobs. Set the minimum needed at workflow or job scope, for example contents: read, and grant id-token: write only where OIDC is required.

55What is OIDC in GitHub Actions?P0

GitHub issues a short-lived identity token containing workflow claims. A cloud or secret system validates those claims and returns short-lived credentials for an authorized role. Security depends on tight trust conditions, workflow/repository/environment claims and minimal target permissions.

56Why are reusable workflows useful?P0

They centralize tested CI/deployment logic, permissions, OIDC and controls across repositories. Version and review them because their blast radius is broad. Define inputs/secrets/outputs explicitly and restrict who can call sensitive workflows.

57Reusable workflow versus composite action?P1

A reusable workflow composes jobs and can choose runners, permissions and environments. A composite action packages steps within a job. Use a workflow for end-to-end standardized pipelines or deployment gates; use a composite action for reusable step logic.

58What does concurrency do in GitHub Actions?P0

It limits simultaneous workflow runs or jobs sharing a concurrency group. Use environment-specific keys to prevent overlapping deployments. Understand pending replacement and cancel-in-progress behavior before applying it to production.

59How do environments protect deployment?P0

Environments can associate protection rules, required reviewers, wait controls and scoped secrets/variables depending on configuration. The job should reference the environment, and the deployment identity should still be least privilege and auditable.

60How do you restrict third-party actions?P0

Use enterprise/organization allowed-action policy, approved sources, version or commit pinning, code/provenance review and reusable workflows. Monitor updates and avoid allowing arbitrary actions on sensitive self-hosted runners.

61How should secrets be managed in GitHub Actions?P0

Scope repository/organization/environment secrets carefully, prefer OIDC/short-lived credentials, rotate, limit exposure to trusted events and runners, and never print or persist them in caches/artifacts. Masking is not complete protection.

62What is the risk of pull_request_target?P1

It runs in the base repository context and can have access to secrets or write permissions. Checking out and executing untrusted PR code in that context can be dangerous. Use only with a carefully reviewed design and minimal permissions.

63How do you troubleshoot a workflow that did not trigger?P0

Check whether the workflow exists on the relevant default/ref, the on event and branch/path filters, event permissions, disabled workflow state, syntax and whether the event type is supported. Distinguish no run from a queued/failed run.

64How do you troubleshoot a failed GitHub Actions workflow?P0

Inspect the visualization and exact step logs, runner/pool, inputs and permissions. Compare recent workflow/action/runner-image/secret/network changes. Enable debug or tool verbosity in a controlled rerun and protect secrets. Reproduce in a safe branch.

65How do you manage runner-image upgrades?P0

Build an immutable versioned image, scan/test it, run representative workflows in canary pool, compare performance and failure, promote gradually, retain rollback image and track runner software currency. Never mutate every worker manually.

66What happens when no runner picks up an assigned job?P1

The service can requeue according to GitHub behavior, but operationally the important issue is why the runner failed after assignment: process crash, lifecycle deletion, network, registration state or resource pressure. Monitor pickup/requeue and worker logs.

67How do you handle API rate limits in GitHub automation?P0

Use the right authentication type, paginate, cache and avoid repeated full inventory scans, inspect rate-limit response headers, back off with jitter, honor retry guidance and schedule heavy work. Distinguish primary from abuse/secondary limiting and log request IDs.

68How do you administer GitHub SaaS in a large enterprise?P0

Identity/team lifecycle, organization and repository policy, runner groups, allowed actions, secrets/environments, rules and reviews, audit, GitHub Apps/tokens, webhook/integration health, usage/capacity, vendor incidents and exception governance.

69How do you respond to a suspected runner compromise?P0

Stop scheduling to the pool, preserve evidence, involve security, identify jobs/credentials/network scope, revoke short-lived and long-lived access, rebuild from trusted image, validate unaffected pools and correct the trust/action/network control. Do not only delete the worker.

70How do you distinguish a GitHub SaaS outage from a local runner issue?P0

Compare GitHub status/vendor evidence with API/UI from multiple networks, GitHub-hosted versus self-hosted runs, runner connectivity logs, DNS/proxy/TLS and one organization versus all. A local network or identity issue can resemble SaaS outage.

D. JFrog Artifactory administration

71What are local, remote, and virtual repositories?P0

Local repositories hold organization-published artifacts. Remote repositories proxy and cache an upstream. Virtual repositories aggregate selected local/remote repositories behind one client URL. Administrators govern permissions, resolution order, upstreams, retention and performance.

72Describe an Artifactory HA architecture.P0

Multiple supported Artifactory nodes behind a load balancer, an external supported database, resilient binary filestore/object storage, consistent cluster keys/configuration and same supported node version. Monitor and back up every state dependency, and test node loss and restore.

73Why does Artifactory HA need more than two application nodes?P1

The exact supported minimum and quorum behavior depend on version/edition, so do not invent a number. The design question is application-node redundancy plus resilient DB, filestore, load balancer and network. More app nodes do not fix a single shared database or storage failure.

74What data is in the database versus filestore?P0

Broadly, the database stores metadata/configuration/runtime records, while the filestore stores binary content. Exact implementation varies. Recovery must keep them consistent and preserve keys/configuration; restoring only binaries or only DB may not yield a usable service.

75What should be monitored in Artifactory?P0

Request success/latency/rate, node health, JVM/threads, DB pool/query, filestore capacity/latency/errors, repository growth and traffic, remote fetch/cache behavior, replication, LB/TLS/network and backup/restore status.

76How do you troubleshoot Artifactory 503 errors?P0

Check whether the LB has healthy nodes, then node startup/application logs, DB reachability/pool, filestore availability/latency, cluster config/version and recent change. Test one direct node only when policy permits. Validate downloads and uploads after recovery.

77How do you troubleshoot slow artifact downloads?P0

Segment local versus remote, cache hit/miss, repository/package/site and node. Compare LB/direct path, JVM/thread, DB, filestore and network/upstream latency. One slow remote repository often indicates upstream/proxy/cache path rather than core storage.

78How do you handle Artifactory storage at 90%?P0

Validate metric/mount and forecast, identify growth by repository/category, protect service with capacity or demand control, then apply approved retention with dry-run and owner review. Check trash/temp/log/backup/replication too. Never delete release artifacts by filename guess.

79How do you define artifact retention?P0

By artifact class, promotion/release status, age, build references, legal/audit need, owner and recovery requirement. Implement search/dry-run, approval, deletion and reclamation validation. Remote cache retention differs from authoritative local release retention.

80What does build once, promote many mean?P0

Create one immutable artifact, attach build and source metadata, then promote the same digest/version through environments. Rebuilding per environment breaks traceability and can produce different bits.

81How do you secure Artifactory access?P0

SSO/groups, scoped permission targets, service identities/tokens, separation of read/deploy/promote/admin, rotation, restricted upstreams, TLS, network segmentation and audit. Pipelines should use short-lived or narrowly scoped credentials and not log them.

82How do you troubleshoot 401 versus 403?P0

401 indicates missing/invalid/expired authentication; 403 means identity was recognized but lacks authorization or is blocked by policy. Check token validity and time first for 401; group, permission target, repository/path and action for 403.

83What is the purpose of a virtual repository?P1

It gives clients one governed endpoint across selected repositories, simplifying configuration. The administrator must understand resolution order, package type, permissions and how a dependency source is traced to avoid ambiguity.

84How do remote repositories improve reliability?P1

They proxy/cache external dependencies, centralize allowlists and reduce repeated external downloads. They do not remove upstream risk for cache misses and can serve stale or blocked content according to policy; monitor upstream latency and cache behavior.

85How do you upgrade Artifactory?P0

Review supported path and DB/JVM/OS/storage/integration compatibility, back up and restore-test DB/filestore/config/keys, rehearse representative formats/load, execute supported node sequence with LB drain and rollback, validate auth, publish/download, Docker, remote resolution, build info and telemetry.

86How do you verify an HA cluster?P0

Check each node health/version/config, LB routing, shared DB/filestore visibility, upload on one node and download through another path, node-loss behavior, logs/metrics and user transactions. Include dependency failover; app-node checks alone are insufficient.

87What can cause Docker push to fail while pull works?P1

Write permission/token scope, storage/full threshold, proxy/request size, manifest/blob upload path, repository type, quota or policy. Compare exact HTTP status and server request log; successful read does not prove write path health.

88What are artifact properties and build info used for?P1

They add searchable metadata such as source revision, build, environment/classification and dependency relationships. They support traceability, promotion, retention and impact analysis. Use controlled keys/values; do not store secrets or unbounded sensitive data.

89How do you design Artifactory DR?P0

Define RTO/RPO and authoritative data, protect DB/binaries/config/keys, choose supported replication or restore design, provision network/DNS/identity/licenses, and test a real upload/download and metadata flow at expected capacity. Plan reconciliation and failback.

90What evidence would you give JFrog support?P1

Exact version/topology, timestamps/timezone, impact/scope, request IDs and status, relevant node/request/system logs or approved support bundle, JVM/DB/storage metrics, recent changes, reproduction and mitigation results. Remove credentials and restricted data before sharing.

92Why use an UrbanCode Deploy agent relay?P0

93How do you troubleshoot UCD agents offline behind a relay?P0

94What are components, applications, environments, and snapshots in UCD?P0

A component represents deployable content and its process; an application composes components and application processes; an environment maps an application to target resources; a snapshot selects a coordinated set of component versions for deployment.

95What should be monitored in UCD?P0

Server API/UI, JVM, task queue, DB pool/query, CodeStation capacity/latency, agent/relay online counts, process success/duration, version import, certificates/licenses, target connectivity and backup/restore health.

96How would you back up UCD?P1

Protect the relational database, CodeStation/file store, server configuration, plugins and required cryptographic material in a consistent state. Record versions and restore order, then test server startup, agent/relay communication, version import, deployment and inventory recovery.

97How do you scale a large UCD agent population?P1

Use relays for remote zones, distribute load according to supported topology, ensure server/JVM/DB capacity, cache artifacts near agents, monitor connection/task backlog and separate environments/failure domains. More agents require network and CodeStation throughput too.

Inventory server, DB, JVM, plugins, agents/relays and supported mixed-version path; back up/restore-test; rehearse; upgrade in supported sequence; validate UI/API, version import, process design, agent/relay connection, deployment, rollback, inventory and telemetry.

99What is a Harness delegate?P0

A worker/service deployed in or near the customer environment that executes or brokers tasks and reaches connected systems. Operations owns its availability, replicas, resources, selectors, version, logs, credentials and network access.

100Why can Harness tasks wait even when delegates are online?P0

No delegate may match the required selectors/tags or connector selection. Matching delegates may be saturated, disconnected from a target, incompatible or unable to reach the control plane. Check eligibility and task assignment, not only global online count.

101How do you make Harness delegates highly available?P0

102What is a Harness connector?P0

103How does Harness CI use Kubernetes build infrastructure?P0

A configured Kubernetes cluster/namespace is used to run build Pods, with a delegate coordinating communication. The team must manage cluster capacity, service account/RBAC, quota, network, images, Pod scheduling/startup, logs and cleanup.

104How do you troubleshoot a Harness connector?P0

Identify selected delegate, test endpoint DNS/port/TLS/proxy from that environment, validate credential expiry/scope/secret reference, inspect delegate task logs and target audit logs, compare recent rotation/config changes and retest minimally.

105Harness versus Jenkins: how would you compare them?P1

107How do you secure delegates?P1

Say so directly, then map proven experience: controller/control plane, agents/delegates, queues, credentials/connectors, artifacts, deployment targets, HA, logs, upgrades and incident response. Explain the product architecture studied and avoid claiming UI-level expertise.

109What is the operational risk of a shared deployment template?P1

110How do you validate a deployment platform after maintenance?P0

F. Docker and Kubernetes operations

111How is a container different from a virtual machine?P0

A VM virtualizes hardware and normally includes a guest operating system. A container isolates processes while sharing the host kernel. Containers are usually faster to start and denser, but kernel, runtime, namespace, cgroup, image and host-security concerns remain part of the operational boundary.

112What happens during a Docker image build?P0

The builder evaluates Dockerfile instructions and creates cacheable content-addressed layers. Build context size, instruction order and cache invalidation affect speed. A production image should use a pinned trusted base, multi-stage build where appropriate, a small runtime layer, non-root execution and no embedded secrets.

113Why use a multi-stage Dockerfile?P0

Compilation and test dependencies stay in a builder stage while only required runtime artifacts are copied into the final image. This reduces image size, attack surface and transfer time. Reproducibility still requires pinned inputs and verification of what is copied.

114Why does PID 1 behavior matter in a container?P1

The container entry process receives signals and is responsible for reaping orphaned children. An application or small init process must correctly handle SIGTERM and child cleanup so Kubernetes can terminate the Pod gracefully rather than forcing a kill.

115What container hardening controls would you use?P0

Run as a non-root UID, prevent privilege escalation, drop Linux capabilities, use read-only root filesystem where feasible, mount only required volumes, avoid hostPath and privileged mode, scan and sign images, pin dependencies, use seccomp/AppArmor or equivalent, and restrict network and registry access.

116Walk through Kubernetes Pod scheduling.P0

The scheduler filters and scores nodes using resource requests, selectors, affinity, taints/tolerations, topology and policy. After binding, the kubelet asks the runtime to pull images, prepare networking and volumes, and start containers. A Pending Pod can therefore be blocked by scheduling, image, volume or admission conditions.

117What is the difference between requests and limits?P0

Requests drive scheduling and are the reserved basis for capacity planning. Limits cap resource use: CPU is typically throttled and memory overuse can lead to OOM termination. Incorrect values cause either poor utilization and Pending Pods or throttling, eviction and instability.

118Explain Kubernetes QoS classes.P1

Guaranteed Pods have matching CPU and memory requests and limits for every container; Burstable Pods have some resources specified but do not meet Guaranteed criteria; BestEffort Pods have none. Under node pressure, lower-QoS workloads are generally more vulnerable, but priority and actual usage also matter.

119How do you investigate OOMKilled?P0

Confirm the terminated reason and exit code, compare working set and peaks with limit, inspect application logs and node pressure, check traffic or workload change, heap or cache behavior, leaks and concurrency. Stabilize with controlled capacity or traffic measures, then right-size and fix the cause rather than repeatedly raising limits.

120Readiness, liveness, and startup probes: what is the difference?P0

Readiness controls whether a Pod receives service traffic. Liveness detects a stuck container and can restart it. Startup protects slow-starting applications by delaying liveness and readiness behavior until initialization succeeds. Probe endpoints must be cheap, meaningful and configured with realistic timing.

121How do you troubleshoot CrashLoopBackOff?P0

Check current and previous container logs, exit reason/code, events, command and arguments, environment and mounted configuration, secrets, probes, permissions, dependencies and resources. CrashLoopBackOff is retry backoff, not a root cause. Reproduce the exact image and configuration when necessary.

122How do you troubleshoot ImagePullBackOff?P0

Inspect events for image name/tag or digest, registry DNS/TLS/connectivity, credentials and imagePullSecrets, service-account linkage, rate limits, proxy policy and architecture compatibility. Validate access from the node or equivalent network context without exposing credentials.

123A Pod remains Pending. What do you check?P0

Start with describe/events. Check unsatisfied CPU/memory or ephemeral storage, taints, affinity, topology spread, quota or limit range, unbound PVC, admission policy and scheduler health. For CI build Pods, also inspect burst concurrency and stale Pods consuming quota.

124Explain Service, Ingress, and cluster DNS.P0

A Service provides stable discovery and load balancing to selected endpoints. Cluster DNS resolves service names. Ingress or Gateway exposes HTTP/S routes through a controller. Troubleshooting follows endpoints, selector, target port, readiness, DNS, controller config, certificate and upstream network.

125What does the CNI layer do?P1

The Container Network Interface implementation allocates Pod networking and programs connectivity according to the cluster model. Operations checks IP exhaustion, node plugin health, routes or overlays, network policy, MTU, conntrack and DNS when Pod-to-Pod or egress traffic fails.

126How do PersistentVolumes and PersistentVolumeClaims work?P0

A PVC requests storage characteristics and binds to a matching PV, often dynamically through a StorageClass and CSI driver. Troubleshooting covers provisioning events, access mode, topology, attach/mount, permissions, capacity, latency, snapshots and reclaim policy.

127Deployment versus StatefulSet: when would you use each?P0

A Deployment suits interchangeable replicas with replaceable identity. A StatefulSet provides stable ordinal identity and ordered behavior, commonly with per-replica volumes. StatefulSet does not itself create database correctness, replication or backup; the application must support those semantics.

128What does the Horizontal Pod Autoscaler need to work well?P1

Reliable metrics, realistic requests, an application that can scale horizontally, enough cluster capacity, sensible min/max and stabilization behavior, and load tests. Scaling on CPU alone may miss queue depth, latency or external bottlenecks; custom metrics can be more meaningful.

129Why use a PodDisruptionBudget?P0

It limits voluntary disruptions so too many replicas are not removed at once during maintenance. It does not protect against every failure and can block node drains if misconfigured. Pair it with topology distribution, sufficient replicas and tested graceful shutdown.

130How do taints, tolerations, node affinity, and pod anti-affinity help a CI platform?P1

Taints reserve worker pools; tolerations allow eligible workloads; node affinity selects required characteristics; pod anti-affinity or topology spread separates replicas. These controls isolate privileged build types, protect control services, improve fault-domain distribution and prevent incompatible placement.

131How would you apply least privilege to Kubernetes build Pods?P0

Use dedicated namespaces and service accounts, minimal RBAC, short-lived identity, restricted admission policy, non-root security contexts, limited network egress, scoped registry credentials, ephemeral workspaces and controlled runner groups. Treat builds from untrusted changes as hostile code.

132How should a Kubernetes platform upgrade be planned?P0

Review supported version skew and API removals, back up required state, inventory add-ons and admission webhooks, test in non-production, validate capacity and PDBs, upgrade control plane and nodes in the supported sequence, canary workloads, monitor, and retain a documented rollback or recovery route.

133What commands do you use for a Kubernetes network issue?P0

Use get/describe for Pods, Services, EndpointSlices and NetworkPolicies; inspect DNS resolution and routes from a controlled debug Pod; test TCP/TLS/HTTP to the exact endpoint; review CNI and kube-proxy or data-plane logs; and correlate node, namespace and recent-change scope.

134Docker hosts are running out of disk. What do you do?P0

Identify consumption by images, layers, build cache, containers, logs and volumes. Protect active workloads and stateful volumes, apply retention and log rotation, remove only unreferenced approved data, then correct build-cache policy, image lifecycle, workspace cleanup and capacity alerting.

135Why is docker system prune not a complete operational answer?P0

It can have broad impact and does not distinguish business ownership or recoverability. A safe process inventories consumers, excludes active and stateful data, supports dry-run, applies age and label rules, records deletions, handles concurrency, validates free space and has preventative retention controls.

G. Observability, monitoring, and alerting

136Monitoring versus observability: what is the difference?P0

Monitoring evaluates known health signals and conditions. Observability is the ability to infer internal state from emitted telemetry, including unfamiliar failure modes. In practice, the platform needs both: defined SLO dashboards and alerts plus searchable logs, high-quality metrics, traces and contextual metadata for investigation.

137How do metrics, logs, and traces complement each other?P0

Metrics efficiently show trends and alert conditions, logs provide discrete contextual events, and traces connect latency and errors across request paths. Correlation identifiers, consistent service metadata and synchronized time make transitions among them useful during incidents.

138What are the golden signals?P0

Latency, traffic, errors and saturation. For CI/CD platforms, translate them into API/UI latency, job or artifact volume, failed dispatch/build/upload ratios, and executor, runner, JVM, DB, storage or queue saturation. Add availability and dependency-specific indicators as needed.

139Describe Prometheus at a high level.P0

Prometheus commonly scrapes labeled time-series endpoints, stores samples locally, evaluates recording and alerting rules, and sends alerts to Alertmanager. Service discovery identifies targets. Federation, remote write or long-term systems may extend scale and retention, but cardinality and query cost still require governance.

140Why is metric-label cardinality dangerous?P0

Every unique label set becomes a time series. User IDs, build IDs, commit SHAs, URLs or unbounded error text can create explosive series counts, memory and storage pressure, slow queries and high cost. Put high-cardinality detail in logs or exemplars and aggregate metrics on bounded dimensions.

141Counter, gauge, histogram, and summary: when do you use each?P0

A counter only increases except reset and fits totals. A gauge rises or falls and fits current queue or capacity. A histogram counts observations in configured buckets and supports aggregatable quantiles. A summary calculates client-side quantiles that are generally not aggregatable across instances.

142rate(), irate(), and increase(): how do they differ?P0

rate() estimates per-second average counter growth over a range and is usually suitable for alerts and dashboards. irate() uses the last two samples and is volatile. increase() expresses the estimated total growth over the window. Choose a window large enough for scrape cadence and noise.

143What are recording rules?P1

They precompute frequently used or expensive PromQL expressions into new time series. Use consistent naming and labels, test them, manage cardinality and preserve enough source data for diagnosis. They improve dashboard and SLO-query performance but can hide mistakes if not reviewed.

144What makes an alert actionable?P0

It maps to user impact or a credible leading indicator, has a clear owner and severity, waits long enough to avoid transient noise, carries context and dashboard/runbook links, and defines the first safe action. It should not simply restate that a metric moved.

145Why use a for duration in a Prometheus alert?P1

It requires the expression to remain true before firing, filtering short transients. The duration must match signal behavior and risk: too short creates noise; too long delays detection. Missing-data behavior and scrape failures must be considered separately.

146Silence versus inhibition in Alertmanager?P1

A silence suppresses matching alerts for a defined interval, often during approved maintenance. Inhibition automatically suppresses dependent alerts when a higher-level alert is firing, such as many service alerts during a cluster outage. Both need governance so real impact is not hidden.

147What should a good CI/CD operations dashboard contain?P0

User-facing availability and latency; job arrivals, success and queue time; worker online/busy/startup; artifact throughput and latency; JVM/DB/storage/Kubernetes health; top tenants or failure categories; SLO/error budget; active incidents and recent changes. Every panel should answer an operational question.

148How do you alert when a Prometheus target disappears?P0

Use target health such as up == 0 with an appropriate duration, and use absent() or absent_over_time() when an expected series is missing entirely. Distinguish exporter failure, service failure, discovery removal and monitoring-path failure.

149What is a multi-window, multi-burn-rate SLO alert?P1

It compares error-budget consumption over a short and a long window. Fast-burn alerts catch severe outages quickly; slow-burn alerts detect sustained degradation. Requiring both windows reduces noise while keeping alerts aligned with the SLO rather than arbitrary thresholds.

150In Splunk, what are index, source, sourcetype, and host?P0

The index is the logical storage/search partition; source identifies where data came from; sourcetype describes event structure and drives parsing; host identifies the originating system. Consistent metadata and timestamp extraction are essential for reliable searches and retention controls.

151Why should Splunk transaction be used carefully?P1

transaction can be memory-intensive because it groups raw events. Prefer stats, eventstats or stream-oriented correlation when possible, using a stable correlation ID and bounded time. Use transaction only when its semantics are actually required and data volume is controlled.

152Explain stats, eventstats, and timechart in SPL.P0

stats transforms matching events into aggregates; eventstats adds aggregate fields back to each event; timechart produces time-bucketed aggregates. The candidate should also filter early, request only useful fields and avoid unbounded high-cardinality groupings.

153How do you onboard a new log source?P0

Define owner and use cases, protect sensitive fields, set source/sourcetype/index and retention, validate timestamps and multiline parsing, add environment/service metadata, estimate volume, test loss/duplication and create searches, dashboards and alerts with a support runbook.

154What is the role of AppDynamics or Dynatrace in this platform?P0

APM correlates application transactions, service dependencies, response time, errors, JVM or process health and infrastructure context. For CI/CD services it can expose slow API paths, downstream calls, thread or connection-pool stress and regressions following change.

155How would you design an APM health rule?P1

Choose a service-relevant metric and baseline or threshold, evaluation window, affected scope, severity and persistence. Connect it to a policy and notification with context. Test normal variability, deployment windows and dependency failures before paging on it.

156How do you correlate an APM trace with Splunk logs?P0

Propagate a trace or correlation ID into structured application logs and include service, environment, version and timestamp. Start from a slow or failed trace, pivot to matching events, then correlate infrastructure and recent change. Avoid putting secrets or sensitive payloads in either system.

157What does ThousandEyes add to observability?P0

It provides externally or agent-observed network and application path visibility such as reachability, DNS, HTTP/TLS, loss, latency and route changes. It helps distinguish SaaS or internet-path problems from application-platform issues and supports evidence-based carrier or vendor escalation.

158Synthetic monitoring versus real-user monitoring?P1

Synthetics run controlled tests on a schedule and detect availability from selected locations even without users. Real-user monitoring measures actual user sessions and diversity. For an internal CI/CD platform, synthetic login/API/job-dispatch probes complement server-side and user-ticket signals.

159How do you resolve an alert storm?P0

Identify the primary fault and protect responders from duplicates using routing, grouping and inhibition. Do not blindly silence everything. After recovery, remove symptom alerts that add no action, tune thresholds/windows, add dependency context and verify ownership and runbooks.

160What if the monitoring system itself is unhealthy?P0

Monitor the monitor through independent health checks: scrape success, ingestion lag, rule evaluation, notification delivery, storage and query health. Use redundant paths for critical paging and dead-man or heartbeat signals. During telemetry loss, communicate reduced detection confidence explicitly.

H. Python automation for infrastructure operations

161What infrastructure tasks would you automate with Python?P0

Inventory and API reconciliation, runner or agent health, certificate expiry, artifact/storage reporting, log and incident enrichment, config validation, upgrade prechecks, dashboard data, stale-resource cleanup with safeguards, BCP validation and ticket/runbook integration.

162Why must every HTTP request have a timeout?P0

Without explicit connect and read timeouts, a script can hang indefinitely and consume scheduler, worker or on-call time. Choose bounds by operation, surface timeout separately from HTTP status, and make the overall workflow deadline finite.

163Which failures should be retried?P0

Retry transient failures such as connection resets, selected 429/5xx responses or temporarily unavailable dependencies when the operation is safe. Use capped exponential backoff with jitter and honor server guidance. Do not retry invalid authentication, validation failures or unsafe non-idempotent writes blindly.

164What is idempotency?P0

Repeating an operation produces the same intended end state without unintended additional effects. Build automation as desired-state reconciliation, use stable identifiers and conditional updates, and support safe retry after partial failure.

165How do you handle paginated APIs?P0

Follow the documented cursor, next link or page parameters until termination, validate response shape, preserve filters, guard against repeated cursors, rate limits and partial pages, and stream or process incrementally when the result can be large.

166When would you use concurrency in an operations script?P1

For independent I/O-bound checks such as many endpoints, a bounded thread pool or async approach can reduce elapsed time. Concurrency must respect API and target limits, use per-task timeouts, isolate failures, preserve deterministic reporting and avoid a thundering herd.

167How do you handle API rate limits?P0

Minimize requests, cache stable data, paginate efficiently, honor limit and retry headers, use jittered backoff, bound concurrency, spread scheduled work and report incomplete results. Coordinate shared credentials so multiple automations do not unknowingly exhaust one quota.

168What is structured logging?P0

Emit machine-parseable events with stable fields such as timestamp, level, service, operation, target, correlation ID, duration and result. Redact secrets and sensitive payloads. Structured logs support alerting, dashboards and incident correlation better than ad hoc print statements.

169How should exceptions be handled?P0

Catch exceptions at the layer that can add context or recover. Use specific exception types, preserve the cause, distinguish expected partial failures from fatal errors, clean up resources and return a meaningful status. A broad catch that silently continues creates false success.

170How should a script use exit codes?P0

Return zero only when the promised operation succeeded. Define stable non-zero codes or at least clear categories for validation, dependency, partial and fatal failure. Write human-readable errors to stderr and machine-readable detail where the scheduler or monitor expects it.

171How do you manage configuration and secrets?P0

Use validated configuration from files, environment or a managed configuration system and secrets from an approved secret store or short-lived identity. Never hard-code or log secrets. Separate environment-specific configuration from code and fail safely when required values are absent.

172What makes a good command-line interface?P1

Clear subcommands and help, validated arguments, sensible but safe defaults, explicit target/environment, dry-run for changes, machine-readable output option, verbosity control, stable exit codes and confirmation or change reference for destructive actions.

173Why is dry-run important?P0

It shows intended changes without applying them, helping reviewers validate scope and allowing safe rehearsal. It must use the same selection logic as execution, state exactly what is not validated, and not mutate hidden state.

174How do you test code that calls an external API?P0

Separate transport from business logic, inject a client, and mock controlled responses for success, pagination, timeout, malformed JSON, 401, 429 and 5xx. Unit-test reconciliation decisions; add a small integration test against a non-production endpoint and contract assumptions.

175Why use type hints and dataclasses?P1

They make interfaces and domain records explicit, improve static checks and review, and reduce shape errors in operational code. They do not replace runtime validation of untrusted API, file or user input.

176How do you parse JSON defensively?P0

Check status and content type, catch decoding errors, validate required keys and types, tolerate documented optional fields, reject unexpected critical values and include a bounded redacted response excerpt for diagnosis. Never assume a successful HTTP code guarantees the schema.

177How do you call shell commands safely from Python?P0

Prefer a native API. When subprocess is necessary, pass an argument list without a shell, set timeout, capture bounded output, check return code, control environment and working directory, and never concatenate untrusted input into a command.

178How do you update a file atomically?P1

Write validated content to a temporary file on the same filesystem, flush and fsync when required, set permissions, then replace the target atomically. Keep a backup or version for critical config and coordinate concurrent writers.

179When is a lock required in automation?P1

Use a lock or distributed coordination when concurrent runs could mutate the same state or violate an invariant. Define lease/timeout and stale-lock recovery. Prefer idempotent server-side conditional operations because a local file lock does not coordinate multiple hosts.

180Explain a reconciliation loop.P0

Read desired and actual state, calculate a deterministic diff, apply bounded safe changes, verify, emit metrics and repeat. Handle eventual consistency, ownership and deletion policy. Kubernetes controllers and runner-fleet managers are familiar examples.

181What is a circuit breaker?P1

After repeated dependency failure it temporarily stops calls, allowing the dependency and caller to recover, then probes in a half-open state. It complements timeouts and retries; it should expose state and must not turn a critical failure into silent data loss.

182How does an automation script expose metrics?P1

For scheduled jobs, publish duration, last success timestamp, items checked/changed/failed and error category through a push-compatible mechanism or node-exporter textfile where appropriate. Long-running services can expose a scrape endpoint. Avoid target IDs as unbounded labels.

183How do you optimize a slow Python inventory script?P1

Measure first. Reduce API calls, request only needed fields, paginate and process incrementally, cache stable lookups, use bounded I/O concurrency, avoid repeated parsing, batch writes and profile CPU/memory. Preserve correctness and rate-limit behavior.

184How should scheduled automation be operated?P0

Run under a dedicated least-privilege identity with timeout, overlap prevention, centralized logs and metrics, ownership, alert on missed or failed execution, documented inputs/outputs, tested rollback and a manual safe procedure. A cron entry without service ownership is not production-ready.

185How would you package and deploy an internal Python tool?P1

Use a versioned package or immutable container, pinned and scanned dependencies, tests and review, configuration outside code, release notes and rollback, CI-produced provenance, least-privilege runtime identity and an owner/runbook. Promote the same artifact across environments.

I. Linux, networking, JVM, database, and storage diagnostics

186What does Linux load average mean?P0

It approximates runnable and uninterruptible tasks over 1, 5 and 15 minutes. Interpret it relative to CPU count, then separate CPU demand from blocked I/O using process, run-queue, iowait, pressure and latency evidence. High load is a symptom, not automatically high CPU.

187Explain user CPU, system CPU, iowait, and steal time.P0

User time is application execution; system time is kernel work; iowait indicates idle CPU while outstanding I/O exists and needs latency correlation; steal means the hypervisor scheduled another tenant instead of the VM. Each points toward a different investigation.

188How do you investigate high memory use?P0

Check available memory, working set and process RSS, page cache, swap activity, cgroup limits, kernel slab, OOM events and trend. Determine leak versus expected cache or load growth. For JVM services, correlate heap, off-heap, thread stacks and container limit.

189Disk space is available but writes fail with no space left. Why?P0

Inodes may be exhausted, a quota may be reached, reserved blocks or filesystem errors may apply, or the process may target a different mount. Check df -h, df -i, mount and quota, then find the high-file-count path safely.

190How do you identify file-descriptor exhaustion?P0

Look for too-many-open-files errors, process limits, open FD count and types, socket states and system-wide limits. Determine leak or expected concurrency, stabilize load or instances, and fix lifecycle or right-size limits with capacity evidence rather than only raising them.

191Process versus thread: what matters operationally?P1

Processes have separate address spaces and resource identity; threads share process memory and descriptors. A service can have low process count but thousands of blocked threads. Inspect both process-level resources and thread states, stacks and pools.

192How do you troubleshoot a systemd service?P0

Inspect unit status, journal, exit code and restart policy; validate config, user, permissions, environment, dependencies, ports and limits; compare recent unit or package changes; run the executable in a controlled context if safe; then validate service and user-facing health.

193What log checks come first during an incident?P0

Set the exact time window and affected scope, verify clock/time zone, search error signatures and correlation IDs, compare healthy instances, identify first error and preceding change, and quantify frequency. Preserve evidence and avoid flooding the system with broad expensive searches.

194Walk through DNS resolution.P0

The client consults local configuration and cache, then a recursive resolver follows or caches authoritative records. Troubleshoot name, record type, search domain, resolver path, TTL, split-horizon view, DNSSEC where used, network reachability and application caching.

195What happens in a TCP connection?P0

A three-way handshake establishes sequence state, followed by reliable ordered byte transfer with acknowledgments, retransmission, windows and congestion control. Diagnosis uses SYN/SYN-ACK behavior, retransmits, resets, latency, loss, port state, backlog and NAT or firewall state.

196How do you troubleshoot a TLS failure?P0

Check name resolution and TCP first, then certificate chain, hostname/SAN, validity, trust store, protocol/cipher compatibility, SNI, client certificate, proxy interception and clock. Use a controlled TLS client to inspect the handshake and never disable verification as the fix.

197How do you interpret common HTTP status classes?P0

2xx indicates accepted success semantics; 3xx redirection; 4xx a request, identity or policy issue; 5xx server or upstream failure. For 502/503/504, distinguish gateway connection failure, unavailable/no healthy capacity and upstream timeout using proxy and backend evidence.

198How can a corporate proxy affect CI/CD tools?P1

It can alter outbound routing, authentication, TLS trust/interception, body-size limits and timeout behavior. Configure explicit proxy and no-proxy scope, trust only approved CAs, test from the service identity/network, and inspect both proxy and application logs.

199What load-balancer checks matter for a stateful web platform?P0

Backend health and port, TLS termination, idle/request timeout, body limits, source headers, persistence only when required, draining during maintenance, connection distribution and health-check semantics. A green TCP check may not prove login or API readiness.

200How do you investigate JVM heap or GC pressure?P0

Correlate heap occupancy after GC, allocation rate, pause duration/frequency, GC type, promotion or humongous allocation, thread count and container memory. Capture supported GC logs and heap evidence when safe. Distinguish heap leak from off-heap, native or load-driven pressure.

201When do you take a Java thread dump?P0

When diagnosing hangs, deadlocks, blocked pools, high CPU or slow requests. Capture multiple dumps spaced apart, identify repeating runnable or blocked stacks and correlate with request/APM and pool metrics. Protect potentially sensitive data and account for collection impact.

202What does database connection-pool exhaustion look like?P0

Requests wait or time out acquiring connections while active/idle pool metrics, DB sessions and query latency reveal whether the pool is too small, connections leak, transactions are long or the database is slow. Raising pool size can overload the database and is not always the fix.

203How can storage latency affect CI/CD services?P0

It slows workspace operations, artifact upload/download, metadata access, logs and backups, causing queues and timeouts even when CPU is low. Correlate application latency with filesystem, block or NFS metrics, IOPS/throughput, queue depth, retransmits and recent storage change.

204Why is time synchronization important?P1

Authentication tokens, TLS validation, distributed logs, incident timelines, leases and monitoring all depend on accurate time. Monitor clock offset and NTP or chrony health. Large corrections can affect applications; follow platform policy rather than manually changing production clocks.

205What is your network-triage sequence?P0

Confirm scope and endpoint, then DNS, route, TCP port, TLS handshake, HTTP/application response and return path. Compare from healthy and failing locations, inspect loss/latency and firewall/proxy/load-balancer evidence, and use packet capture only with authorization and a precise filter.

J. Incident, change, BCP, capacity, security, and vendor leadership

206How do you assign incident severity?P0

Use documented business impact: affected users/services, criticality, availability or data/security risk, workaround, time sensitivity and scope. Severity is not determined by who reports it. Reassess as evidence changes and trigger the correct response, communication and escalation path.

207What do you do in the first ten minutes of a major incident?P0

Acknowledge and establish ownership, confirm impact and severity, open the incident channel/record, stop unsafe changes, assign technical and communications roles, collect a precise timeline and telemetry, choose the safest stabilization action, and set the next update time.

208What belongs in an incident update?P0

Current impact, affected scope, start time, what is known and not yet known, mitigation or work in progress, risks, dependencies or vendor involvement, and next update time. Use facts, avoid speculative root cause and tailor technical depth to the audience.

209What is incident command?P1

A designated lead coordinates priorities, roles, decisions, timeline and communication so investigators can focus. The commander need not be the deepest product expert. Clear ownership prevents duplicate changes and contradictory messages.

210Why separate incident recovery from root-cause analysis?P0

During impact, restore service safely and preserve evidence. A rushed causal conclusion can misdirect recovery. After stabilization, reconstruct the timeline and contributing conditions, test hypotheses and assign durable actions through problem management.

211What is problem management?P0

It reduces recurrence and impact by analyzing incident patterns and underlying causes, recording known errors/workarounds, prioritizing fixes and verifying corrective actions. A problem can exist without a current outage and may span product, process, capacity and vendor causes.

212Standard, normal, and emergency change: explain them.P0

A standard change is pre-authorized, low-risk and repeatable under a proven procedure. A normal change receives risk review and approval. An emergency change follows an expedited but still controlled path for urgent risk or restoration, with evidence and retrospective review.

213What are good rollback criteria?P0

Objective thresholds defined before execution: failed health checks, error/latency increase, worker loss, data-integrity risk, validation failure or elapsed-time boundary. The team also needs a feasible rollback procedure and awareness that schema or irreversible changes may require restore or forward fix.

214What should a CI/CD tool upgrade plan contain?P0

Scope and owner, version/compatibility matrix, plugin or extension impact, backups and restore proof, capacity, non-production rehearsal, security and release notes, user communication, outage and active-job handling, step plan, validations, rollback, monitoring and evidence closure.

215BCP versus disaster recovery: what is the distinction?P0

Business continuity keeps critical business services operating through disruption, including people, process and workarounds. Disaster recovery restores technology services and data. A CI/CD platform plan must identify which development and deployment capabilities are truly business-critical.

216Define RTO and RPO.P0

RTO is the targeted time to restore the service or capability after disruption. RPO is the tolerable data-loss window measured in time. They drive architecture, replication, backup frequency and exercise design, and must be validated rather than assumed.

217What makes a useful DR exercise?P0

Clear scenario and success criteria, isolated safe execution, restored data and dependencies, identity/DNS/network validation, representative transactions such as build and artifact publish, measured RTO/RPO, stakeholder communication, evidence and tracked remediation. A server boot alone is insufficient.

218What makes a runbook effective?P0

Trigger and scope, owner and prerequisites, safety and authorization notes, exact diagnostics, decision points, mitigation and rollback, validation, escalation, communication, evidence and last tested date. It should reduce cognitive load without encouraging blind commands.

219What belongs in an on-call shift handover?P0

Active incidents and impact, mitigations and next actions, degraded components, pending changes, risky alerts, vendor cases, capacity concerns, scheduled work and explicit ownership/time. Verify the receiver understands rather than only forwarding a chat transcript.

220How do you reduce on-call fatigue?P1

Remove non-actionable pages, improve routing and runbooks, automate safe diagnosis/remediation, staff sustainable rotations, review out-of-hours patterns, reduce fragile changes, train backups and treat toil and recurrent alerts as engineering work with owners.

221An SLA is at risk of breach. How do you respond?P0

Do not hide it. Reassess impact and priority, escalate resources and vendor paths, communicate risk and next milestone, pursue the safest restoration/workaround, document timeline and policy exceptions, then review why detection, capacity or response was insufficient.

222How much capacity headroom should a platform keep?P0

There is no universal percentage. Base it on growth, burstiness, scale-up lead time, failure-domain loss, maintenance needs and SLO. Define minimum safe headroom per bottleneck, alert on forecasted exhaustion and prove the system can survive expected node or zone loss.

223How do you forecast capacity?P0

Use clean historical demand and utilization, seasonality and known events, growth scenarios, saturation relationship and provisioning lead time. Forecast the actual bottleneck—runner minutes, queue time, artifact storage/IOPS, DB connections, IPs—not only CPU. Reconcile forecast with load tests.

224What should be included in a vendor support case?P0

Business impact and severity, product/version/topology, exact timestamps and timezone, reproduction or frequency, recent changes, diagnostics and logs with sensitive data removed, mitigation attempted, requested action and contact/bridge details. Keep an internal owner and decision log.

225What if the vendor says the issue is not in its product?P0

Keep the discussion evidence-based: define the failing boundary, share correlated request IDs, packet or dependency results and healthy comparison, ask for the product-specific evidence needed, reproduce jointly where possible, and escalate through agreed severity paths. Continue internal mitigation in parallel.

226How do you handle a developer team frustrated with a centralized platform?P1

Acknowledge impact, obtain a reproducible example and urgency, distinguish incident from feature or policy request, explain current action and next update, provide a safe workaround where possible, and publish root-cause or roadmap follow-up. Use aggregate feedback to improve the platform product.

227What is control evidence for an operations process?P0

Traceable proof that the designed control operated: approved change record, peer review, access authorization, automated test result, backup/restore report, alert acknowledgement, deployment audit, separation of duties or periodic access review. Evidence must be complete, protected and reproducible.

228How do you rotate a production secret safely?P0

Identify all consumers and owner, create or activate the new credential, update through an approved secret system, verify each consumer, revoke the old credential after overlap where supported, monitor authentication errors, record evidence and test emergency rollback without exposing the value.

229How do you implement least privilege for a CI/CD platform?P0

Use role-based access, separate admin/build/deploy identities, short-lived credentials, scoped runner groups and environments, protected production approvals, minimal service-account permissions, periodic review, audited break-glass and separation of duties for high-risk changes.

230What makes a good post-incident review?P0

A factual timeline, impact and detection, contributing technical and organizational conditions, what helped or hindered response, and prioritized measurable actions with owners and dates. Avoid blame, but maintain accountability. Verify action completion and whether recurrence risk actually fell.

K. GenAI, LLM, prompt engineering, and RAG fundamentals

231What is a large language model?P2

An LLM is a model trained on large text or code corpora to predict and generate token sequences. It can perform many language tasks from context, but output is probabilistic and not inherently verified, current or authorized.

232What is the Transformer idea at a high level?P2

Transformers use attention to model relationships among tokens and process context efficiently compared with recurrent architectures. Modern LLMs stack attention and feed-forward blocks at large scale; the candidate need not derive the mathematics for this role.

233What are tokens and a context window?P2

Tokens are the model input/output units, often subword pieces. The context window is the bounded amount of tokens available for instructions, retrieved material, history and output. More context can increase cost and latency and does not guarantee the model uses every detail correctly.

234What does temperature do?P2

It changes sampling randomness: lower values tend to be more repeatable and focused, while higher values increase diversity. It does not make an answer factually correct. Operational workflows usually favor constrained output, validation and human approval over creative sampling.

235What is prompt engineering?P2

Designing instructions and context so the model performs a task reliably: clear role and objective, relevant data, constraints, examples, output schema and refusal boundaries. Prompts should be versioned, tested against representative and adversarial cases, and not treated as a security boundary.

236What is hallucination?P2

A model can produce plausible but unsupported content. Reduce risk through grounded retrieval, constrained tools and output schemas, source citations, deterministic checks, confidence-aware workflows and human approval. Never let generated commands change production without controls.

237What are embeddings?P2

Embeddings represent text or other objects as numeric vectors whose geometry can support semantic similarity. They enable retrieval, clustering and classification, but model choice, normalization, metadata filters and data governance affect results.

238What is a vector database or vector index?P2

It stores vectors and metadata and supports approximate nearest-neighbor search. In RAG, it retrieves semantically similar chunks. Access control, freshness, deletion, metadata filtering, index recall, tenancy and sensitive-data exposure are operational concerns.

239Explain RAG.P2

Retrieval-augmented generation retrieves relevant external content for a query and supplies it to a generator. It can improve grounding and updateability without retraining, but poor retrieval, stale content or prompt injection can still produce unsafe or wrong answers.

240Why do chunk size and overlap matter in RAG?P2

Chunks that are too small lose context; chunks that are too large dilute relevance and consume the context window. Overlap can preserve boundaries but creates duplication. Tune by document structure and evaluate retrieval and answer quality rather than selecting a universal number.

241How do you evaluate a RAG system?P2

Measure retrieval recall/precision or relevance on a labeled set, answer groundedness and correctness, citation quality, refusal on missing evidence, latency and cost. Include access-control, freshness, adversarial prompt and sensitive-data tests, plus human review for high-risk use.

242What is prompt injection?P2

Untrusted content attempts to override instructions or cause unauthorized actions or disclosure. Treat retrieved text and tool output as data, enforce permissions outside the model, allowlist tools and parameters, isolate secrets, validate actions and require approval for high-impact operations.

243What GenAI use cases are reasonable for systems operations?P2

Runbook search, incident summarization, log-query drafting, ticket categorization, change-plan review and explanation of telemetry. Keep source links, redact sensitive data, evaluate accuracy and require human approval. Deterministic automation should execute approved remediation.

244Where should a human remain in the loop?P2

Production changes, credential or access decisions, incident declarations, destructive cleanup, external communication and any action with material business or security impact. The model may propose; authorized systems and people validate and execute.

245What operational metrics would you track for an LLM feature?P2

Availability, latency, token and monetary cost, rate-limit errors, retrieval latency and hit quality, answer acceptance/correction, groundedness evaluations, safety-policy violations, model or prompt version, cache effectiveness and fallbacks. Never log sensitive prompts indiscriminately.

Show the leading signal, clean trend and forecast, failure threshold and lead time. Explain load validation, options and trade-offs, implementation, revised alert and observed headroom. Capacity can be runner concurrency, storage, DB sessions, IP space, API quota or network throughput.

Likely follow-ups:

  • How accurate was the forecast?
  • What was the seasonal factor?
  • Why not simply add hardware?
  • How did you measure utilization after change?
B11Describe a security or access-control issue you handled.

What the panel is testing: Containment, confidentiality, evidence preservation, and process discipline.

Answer plan

Use only non-confidential detail. Explain detection, immediate containment, security-team escalation, credential or access revocation, evidence handling, impact validation, recovery and durable control. Do not claim independent investigation authority outside the organization process.

Likely follow-ups:

  • Was any secret exposed?
  • How was scope determined?
  • What logs were protected?
  • What preventive control was added?
B12Two high-priority incidents arrive at once. How do you prioritize?

What the panel is testing: Impact-based judgment and delegation.

Answer plan

Apply severity criteria, assign ownership and incident command, protect safety/security first, mobilize parallel responders, avoid one person making changes in both systems, set update cadence and escalate resource conflict. Reassess as business impact changes.

Likely follow-ups:

  • What if both are P1?
  • What work do you delegate?
  • How do you keep evidence separate?
  • Who decides business priority?
B13Are you comfortable with weekday, weekend, morning, and evening on-call?

What the panel is testing: Reliability, realistic expectations, and operational maturity.

Answer plan

Answer honestly. A strong response states comfort with a published rotation and handover, readiness to follow escalation and change controls, and commitment to fatigue-safe practices. Clarify rotation frequency and shift model as a practical question rather than appearing unwilling or promising unlimited availability.

Likely follow-ups:

  • How have you handled night incidents?
  • What makes a good handover?
  • How do you prepare before a shift?
B14How have you led without formal authority?

What the panel is testing: Influence across platform, application, network, security, and vendor teams.

Answer plan

Choose a cross-team reliability outcome. Establish shared impact, provide evidence and options, define owners and milestones, remove ambiguity, escalate only where needed and give credit. The result should show adoption or risk reduction, not merely that a meeting occurred.

Likely follow-ups:

  • Who initially disagreed?
  • How did you gain commitment?
  • What did you do when a deadline slipped?
  • How did you measure adoption?
B15How do you mentor or raise the team’s operational capability?

What the panel is testing: Technical leadership and scalable knowledge transfer.

Answer plan

Describe paired incident reviews, runbook drills, code review standards, office hours, game days, rotating ownership or a troubleshooting curriculum. Show how you assessed skill, gave feedback and reduced single-person dependency.

Likely follow-ups:

  • How did you know learning occurred?
  • How do you correct unsafe behavior?
  • What documentation remained current?
B16A control or process seems unnecessarily slow. What do you do?

What the panel is testing: Respect for controls plus continuous improvement.

Answer plan

Understand the risk and policy owner before bypassing anything. Quantify delay and failure modes, propose automation or risk-tiering, preserve approval and evidence requirements, pilot with stakeholders and measure both delivery speed and control effectiveness.

Likely follow-ups:

  • Would you ever bypass it during an outage?
  • Who accepts residual risk?
  • How do you automate evidence?
  • What is the rollback for a process change?
B17You have not administered one of the listed tools. How do you answer?

What the panel is testing: Integrity and ability to learn from architecture patterns.

Answer plan

State the exact boundary: “I have not operated UCD in production.” Then describe verified study of its server/agent/relay/artifact model and map a truthful analogous responsibility. Explain a concrete first-30-day learning and shadowing plan. Never convert awareness into claimed experience.

Likely follow-ups:

  • What is the product architecture?
  • Which operational patterns transfer?
  • How quickly have you learned a similar platform?
  • What would you validate first?
B18How do you brief a senior stakeholder during an outage?

What the panel is testing: Concise business communication under uncertainty.

Answer plan

Lead with impact, duration and what capability is unavailable. State mitigation, current risk, next decision or dependency and next update time. Avoid low-level logs unless asked, avoid unsupported root cause and make clear where confidence is limited.

Likely follow-ups:

  • What if there is no ETA?
  • How do you communicate bad news?
  • What differs for engineers?
  • Who approves an external message?
B19Your shift ends while an incident is active. What do you do?

What the panel is testing: Continuity without hero culture or abandonment.

Answer plan

Follow incident-command and shift policy. Arrange an explicit live handover with impact, timeline, hypotheses, actions attempted, access, vendor state, next decisions and owners. Remain for a controlled overlap when required, but do not create a single exhausted point of failure.

Likely follow-ups:

  • What if no replacement is available?
  • What details are essential?
  • How do you prevent conflicting actions?
B20How do you handle confidential production information in an interview or support case?

What the panel is testing: Judgment expected in an enterprise operations role.

Answer plan

Use sanitized architecture and relative metrics, never real credentials, customer data, private URLs or proprietary code. For vendor cases, follow approved secure-transfer and redaction procedures. In the interview, say what type of data was protected rather than revealing it.

Likely follow-ups:

  • How do you sanitize logs?
  • What data cannot be sent to a vendor?
  • How do you reproduce without production data?

Tool-by-tool 60-second recall

Jenkins

Controller orchestrates; agents execute through executors. Watch API/UI, queue, executor utilization, agent health, JVM/GC, disk, plugin/security and artifact dependency. Keep builds off the controller. Rehearse LTS/plugin upgrades and restore.

GitHub Actions

SaaS control plane plus hosted or self-hosted runners. Route with groups/labels. Prefer ephemeral isolated workers for risky code, externalize logs, use OIDC and minimal permissions, govern reusable workflows and Actions versions.

Artifactory

Local, remote and virtual repositories; binaries plus metadata/DB and filestore. Watch download/upload latency, errors, storage, DB, router/nodes, replication/cache and retention. Never perform blind binary deletion.

UCD

Server models and orchestrates; agents act on targets; relays cross network zones; CodeStation stores versions/artifacts; DB holds state. Validate agent/relay path, version import, deployment, inventory and DR end to end.

Harness

Control plane delegates tasks to workers near targets. Connectors define authenticated integrations; Kubernetes CI creates build Pods. Watch delegate eligibility, heartbeat, task wait, connector/TLS, namespace quota and Pod scheduling.

Kubernetes

Describe and events first. Check requests/limits, quota, taints/affinity, PVC, image pull, config/secret, previous logs and probes. Separate scheduling, startup, network, application and dependency layers.

Last 24 hours

Evening before

  1. Complete one platform-admin mock and one incident/coding mock.
  2. Review only failed P0 answers; do not begin a new broad course.
  3. Sanitize project diagrams and prepare truthful scale numbers.
  4. Print or save the one-page revision sections.
  5. Confirm venue, ID, travel, time and interview contact.

Interview morning

  1. Say the introduction once, not ten times.
  2. Write eight story labels and five numbers on a private revision page.
  3. Review incident, change and architecture frameworks.
  4. Carry notebook and pen for diagrams.
  5. Arrive early enough to settle without rushing.
  6. Do not expose current-employer confidential material.

In-room answer flow

  1. Listen to the entire question and restate the target when ambiguous.
  2. Give the direct answer in one or two sentences.
  3. Draw or structure components and data flow only when it adds clarity.
  4. Add a truthful operational example and one measured result.
  5. Cover evidence, security, failure mode, validation and prevention.
  6. Stop. Let the interviewer select the next depth.

Red flags to remove from answers

  • “I usually restart it” before impact, evidence and safe-change discussion.
  • Claiming 99.99% without defining the SLI or showing design and measurement.
  • Using CPU as the only capacity metric for a queued system.
  • Saying Kubernetes automatically makes an application highly available.
  • Putting secrets directly in YAML, scripts, logs or command history.
  • Describing only tools used by the application team, not platform administration.
  • Blaming a vendor or another team without evidence and internal ownership.
  • Inventing UCD, Harness or financial-services experience.
  • Giving production changes to an LLM or auto-remediator without authorization and deterministic controls.
